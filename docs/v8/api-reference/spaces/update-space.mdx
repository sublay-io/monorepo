---
title: "Update Space"
api: "PATCH /v8/:projectId/spaces/:spaceId"
description: "Update a space's settings, name, description, or images"
---

Updates a space. Only the space's admin can update it. Send `multipart/form-data` to upload a new avatar or banner; without files, use `application/json`. Every other field goes as a form field on a multipart request (objects and arrays as JSON strings).

## Path Parameters

<ParamField path="spaceId" type="string" required>
  UUID of the space to update.
</ParamField>

## Body Parameters

All fields are optional. Only provided fields are updated.

<ParamField body="name" type="string">
  Updated display name. 3–100 characters.
</ParamField>

<ParamField body="slug" type="string">
  Updated URL slug. Pass empty to clear.
</ParamField>

<ParamField body="description" type="string">
  Updated description.
</ParamField>

<ParamField body="readingPermission" type="string">
  `"anyone"` or `"members"`.
</ParamField>

<ParamField body="postingPermission" type="string">
  `"anyone"`, `"members"` (active members), or `"team"` (the space's active admins and moderators). Any other value, `"admins"` included, is refused with `400 space/invalid-body`.
</ParamField>

<ParamField body="visibility" type="string">
  `"public"`, `"unlisted"`, or `"private"`. Controls who can find and see the space (and the spaces under it), independent of `readingPermission`. Changes take effect immediately and are freely reversible. See [Space visibility](/v8/data-models/space#visibility).
</ParamField>

<ParamField body="requireJoinApproval" type="boolean">
  Whether joining the space needs admin approval. Applies to joins from this point on — memberships that are already pending or active are unaffected.
</ParamField>

<ParamField body="metadata" type="object">
  Updated metadata object.
</ParamField>

<ParamField body="avatarFile" type="file">
  New avatar image, replacing the current one (the old file is deleted). Requires `avatarFile.options`.
</ParamField>

<ParamField body="avatarFile.options" type="string">
  Stringified JSON describing how to process the avatar. Must include a `mode` field; see [Upload Image](/v8/api-reference/storage/upload-image) for the modes and optional fields. Not used when no `avatarFile` is sent, but still validated: invalid JSON or options get a `400`.
</ParamField>

<ParamField body="bannerFile" type="file">
  New banner image, replacing the current one (the old file is deleted). Requires `bannerFile.options`.
</ParamField>

<ParamField body="bannerFile.options" type="string">
  Stringified JSON describing how to process the banner, as `avatarFile.options`. Not used when no `bannerFile` is sent, but still validated: invalid JSON or options get a `400`.
</ParamField>

<ParamField body="removeFileIds" type="string[]">
  Files to remove from the space: its `avatarFileId` and/or `bannerFileId`, nothing else. Removing one clears that image (the pointer becomes `null` and the file is deleted). Works alone or with uploads in the same request; uploading a new avatar while listing the old one is a plain replace. On a multipart request, send it as a JSON string (`'["<fileId>"]'`). Any other id, including a file that only carries this space's `spaceId`, refuses the whole request with `400 space/invalid-remove-file-ids`.
</ParamField>

<ParamField body="actingUserId" type="string">
  Required with a service key: the user this request acts as. The request has exactly that user's permissions, so it is refused unless they are an admin of the space, and it is recorded as theirs. A user token always acts as its own user and must not send it (`400 space/acting-user-not-allowed`).
</ParamField>

## Response

Returns the updated [Space](/v8/data-models/space) object with `memberPermissions`: what the caller (or the user named by `actingUserId`) may do in the space after the update, as a [SpaceMemberPermissions](/v8/data-models/space#spacememberpermissions) object.

## Error Responses

<AccordionGroup>
  <Accordion title="Not signed in — 401 / 403">
    Returned with no JSON body: `401` when no `Authorization` header is sent, `403` when the access token is invalid or expired. Checked before any uploaded file is read, so a request with no credentials gets `401` rather than a body or acting-user error.
  </Accordion>
  <Accordion title="Invalid Id — 400">
    Returned when `spaceId` isn't a valid UUID. Checked before sign-in, permissions and the endpoint's other checks.
    ```json
    { "error": "Invalid space id: expected a UUID.", "code": "space/invalid-params", "param": "spaceId" }
    ```
  </Accordion>
  <Accordion title="Missing Acting User — 400">
    A service key sent no `actingUserId`.
    ```json
    { "error": "A service key must send actingUserId: the user this request acts as.", "code": "space/missing-user-id" }
    ```
  </Accordion>
  <Accordion title="Invalid Acting User — 400">
    `actingUserId` is not a user id.
    ```json
    { "error": "actingUserId must be a user id.", "code": "space/invalid-body", "param": "actingUserId" }
    ```
  </Accordion>
  <Accordion title="Acting User Not Allowed — 400">
    A user token sent `actingUserId`, even naming its own user. Only a service key names the user it acts as; a user token always acts as its own user.
    ```json
    { "error": "actingUserId is only accepted with a service key. A user's own token always acts as that user.", "code": "space/acting-user-not-allowed" }
    ```
  </Accordion>
  <Accordion title="Wrong Location — 400">
    `actingUserId` was sent in the query string. On this endpoint every field, `actingUserId` included, goes in the request body.
    ```json
    { "error": "`actingUserId` goes in the request body on this endpoint.", "code": "space/wrong-location", "param": "actingUserId" }
    ```
  </Accordion>
  <Accordion title="User Not Found — 404">
    Returned when a service key names an `actingUserId` that isn't a user in this project.
    ```json
    { "error": "No user with this actingUserId exists in this project.", "code": "space/user-not-found" }
    ```
  </Accordion>
  <Accordion title="Not an Admin — 403">
    The caller (or the user named by `actingUserId`) is not an admin of the space.
    ```json
    { "error": "Admin access required", "code": "space/admin-required" }
    ```
  </Accordion>
  <Accordion title="Not Found — 404">
    ```json
    { "error": "Space not found.", "code": "space/not-found" }
    ```
  </Accordion>
  <Accordion title="Slug Taken — 409">
    ```json
    { "error": "A space with this slug already exists.", "code": "space/slug-taken", "param": "slug" }
    ```
  </Accordion>
  <Accordion title="Invalid File Ids — 400">
    `removeFileIds` names a file that isn't this space's current avatar or banner. `invalidIds` lists those ids. Checked before anything is uploaded, so nothing is stored or removed.
    ```json
    { "error": "`removeFileIds` may name only this space's own avatar and banner files (its `avatarFileId` and `bannerFileId`).", "code": "space/invalid-remove-file-ids", "param": "removeFileIds", "invalidIds": ["9b2f…"] }
    ```
    A `removeFileIds` that isn't an array of file ids gets `400 space/invalid-body` instead.
  </Accordion>
  <Accordion title="Bundle Not Installed — 403">
    Returned when an avatar or banner is uploaded on a project without the files-images bundle. `missingTables` lists the tables that aren't installed and `bundleId` the bundle to install. While the bundle is still being installed, the response is `503 database/tables-provisioning` instead. See [Bundles](/v8/bundles).
    ```json
    { "error": "Space avatar/banner uploads require the files-images bundle. Enable it for this project.", "code": "database/tables-not-available", "missingTables": ["Files", "Images"], "bundleId": "files-images", "dashboardUrl": "https://…/<projectId>/database" }
    ```
  </Accordion>
  <Accordion title="Image Too Large — 413">
    The image is over 50 MB. `param` names its field: `avatarFile` or `bannerFile`.
    ```json
    { "error": "`avatarFile` is over the 50 MB per-file limit.", "code": "space/file-too-large", "param": "avatarFile" }
    ```
  </Accordion>
  <Accordion title="Invalid Image — 422">
    ```json
    { "error": "Avatar file is not a valid image.", "code": "space/invalid-image", "param": "avatarFile" }
    ```
    The file can't be read as an image. Also returned for the banner, with `param: "bannerFile"`.
    An image over 10000 px on a side gets the same code. `error` gives its size:
    ```json
    { "error": "Avatar file is 12000 x 800 px; an image can be at most 10000 px on each side.", "code": "space/invalid-image", "param": "avatarFile" }
    ```
    For `bannerFile`:
    ```json
    { "error": "Banner file is 12000 x 800 px; an image can be at most 10000 px on each side.", "code": "space/invalid-image", "param": "bannerFile" }
    ```
  </Accordion>
  <Accordion title="Missing Image Options — 400">
    ```json
    { "error": "Image options are required when uploading an avatar. Must include mode property.", "code": "space/missing-image-options", "param": "avatarFile.options" }
    ```
    `avatarFile` or `bannerFile` was uploaded without its `.options` field. `param` is `avatarFile.options` or `bannerFile.options`.
  </Accordion>
  <Accordion title="Invalid Image Options — 400">
    ```json
    { "error": "Invalid JSON in avatarFile.options field.", "code": "space/invalid-body", "param": "avatarFile.options" }
    ```
    The `.options` field isn't valid JSON. `param` names the field: `avatarFile.options` or `bannerFile.options`.
    `avatarFile.options` without `mode`, or with a `mode` that isn't one of the five (other options fields the same way, named in `error` and `param`):
    ```json
    { "error": "avatarFile.options.mode: Invalid input", "code": "space/invalid-body", "param": "avatarFile.options.mode" }
    ```
    In an aspect-ratio mode, a variant's computed side would be outside 1–10000 px. Checked once the image is read, before anything is stored. `param` names the option:
    ```json
    { "error": "`avatarFile.options.widths.s` gives a height of 0 px at the 3:1 aspect ratio. Each side of a variant must be 1–10000 px.", "code": "space/invalid-body", "param": "avatarFile.options.widths.s" }
    ```
    In `aspect-ratio-height-based` it names a `heights` option and gives a width. In `multi-aspect-ratio` it names a `sizes` option, and the ratio is the one in `aspectRatios` closest to the image, so the text reads "… at the 3:1 aspect ratio, the one in `aspectRatios` closest to this image. Each side of a variant must be 1–10000 px."
    More than 30 entries in `dimensions`, `widths`, `heights` or `sizes` (one variant each). `param` names the option:
    ```json
    { "error": "avatarFile.options.sizes: An image can have at most 30 variants.", "code": "space/invalid-body", "param": "avatarFile.options.sizes" }
    ```
    A variant name that uses a character other than letters, digits, `_`, `-` and `.`, that is longer than 64 characters, that contains `..`, or that is `original`. `param` names the option:
    ```json
    { "error": "avatarFile.options.sizes: Variant names use only letters, digits, `_`, `-` and `.`, are at most 64 characters, can't contain `..`, and can't be `original`.", "code": "space/invalid-body", "param": "avatarFile.options.sizes" }
    ```
  </Accordion>
  <Accordion title="Upload Refused — 400 / 413">
    A file was refused as the body was read: `space/unsupported-file-type` or `space/unexpected-file-field` (a file in another field, or a second file in `avatarFile` or `bannerFile`), with `param` naming the field when there is one. A body over 250 MB gets `413 request/body-too-large`; one that can't be read at all gets `request/invalid-multipart` or `request/field-too-large`. See [Upload errors](/v8/api-reference/getting-started#upload-errors).
  </Accordion>
</AccordionGroup>
