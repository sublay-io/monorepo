---
title: "Unblock User"
api: "DELETE /v8/:projectId/users/:userId/block"
description: "Unblock a user by their ID"
---

Removes the block edge from the acting user (the blocker) to the specified user (the target). The barrier lifts immediately.

Unblocking is **idempotent** — unblocking a user who isn't blocked is a success no-op. Nothing that the block tore down is restored: removed follows and connections stay gone and the two users must re-establish them from scratch. A previously frozen 1:1 conversation becomes usable again (the conversation record still exists).

<Note>
  **Requires the `moderation` bundle.** A project without the moderation bundle returns `403 database/tables-not-available`. See [Bundles](/v8/bundles).
</Note>

## Path Parameters

<ParamField path="userId" type="string" required>
  The Sublay user ID (UUID) of the user to unblock (the target).
</ParamField>

## Query Parameters

<ParamField query="actingUserId" type="string">
  Service key only, and required with one: the user this request acts as, who performs the unblock (the blocker). A user token always acts as its own user and must not send it (`400 block/acting-user-not-allowed`).
</ParamField>

## Response

On success, returns HTTP `204` with no body.

## Error Responses

<AccordionGroup>
  <Accordion title="Missing User — 400">
    A service key sent no `actingUserId`.
    ```json
    {
      "error": "Missing user ID",
      "code": "block/missing-user-id"
    }
    ```
  </Accordion>
  <Accordion title="Acting User Not Allowed — 400">
    A user token sent `actingUserId`, even naming its own user. Only a service key names the user it acts as; a user token always acts as its own user.
    ```json
    {
      "error": "actingUserId is only accepted with a service key. A user's own token always acts as that user.",
      "code": "block/acting-user-not-allowed"
    }
    ```
  </Accordion>
</AccordionGroup>
