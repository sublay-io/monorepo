---
title: "Remove Connection"
api: "DELETE /v8/:projectId/connections/:connectionId"
description: "Withdraw a pending request or disconnect an accepted connection by connection ID"
---

Removes a connection record by its ID. The behavior depends on the connection's current status:

- **Pending** — only the requester can withdraw the request (record is deleted).
- **Accepted** — either connected user can disconnect (record is deleted).

Use [Remove Connection (by user ID)](/v8/api-reference/users/connections/remove-connection) if you only have the other user's ID.

## Path Parameters

<ParamField path="connectionId" type="string" required>
  The ID (UUID) of the connection record to remove.
</ParamField>

## Query Parameters

<ParamField query="actingUserId" type="string">
  Service key only, and required with one: the user this request acts as. Must be the requester of a pending request, or either user of an accepted connection. A user token always acts as its own user and must not send it (`400 connection/acting-user-not-allowed`).
</ParamField>

## Response

On success, returns HTTP `200`:

<ResponseField name="message" type="string">
  Human-readable description: `"Connection request withdrawn successfully."` or `"Connection removed successfully."`.
</ResponseField>

## Error Responses

<AccordionGroup>
  <Accordion title="Not Found — 404">
    ```json
    {
      "error": "Connection not found or cannot be withdrawn.",
      "code": "connection/not-found"
    }
    ```
  </Accordion>
  <Accordion title="Unauthorized — 403">
    ```json
    {
      "error": "Only the requester can withdraw a pending connection request.",
      "code": "connection/unauthorized"
    }
    ```
  </Accordion>
  <Accordion title="Missing User — 400">
    A service key sent no `actingUserId`.
    ```json
    {
      "error": "A service key must send actingUserId: the user this request acts as.",
      "code": "connection/missing-user-id"
    }
    ```
  </Accordion>
  <Accordion title="Acting User Not Allowed — 400">
    A user token sent `actingUserId`, even naming its own user. Only a service key names the user it acts as; a user token always acts as its own user.
    ```json
    {
      "error": "actingUserId is only accepted with a service key. A user's own token always acts as that user.",
      "code": "connection/acting-user-not-allowed"
    }
    ```
  </Accordion>
  <Accordion title="User Not Found — 404">
    Returned when a service key names an `actingUserId` that isn't a user in this project.
    ```json
    { "error": "No user with this actingUserId exists in this project.", "code": "connection/user-not-found" }
    ```
  </Accordion>
  <Accordion title="Unsupported Parameter — 400">
    The request sent `userId`. On this route the user a service key acts as is `actingUserId`.

    With a service key:

    ```json
    {
      "error": "`userId` was renamed to `actingUserId`: send the user this service key acts as in `actingUserId`.",
      "code": "connection/unsupported-param",
      "param": "userId"
    }
    ```

    With a user token, or with no credentials:

    ```json
    {
      "error": "`userId` isn't accepted here: a user's own token always acts as that user.",
      "code": "connection/unsupported-param",
      "param": "userId"
    }
    ```
  </Accordion>
</AccordionGroup>
