---
title: "Workspaces"
description: "Full server-side workspace surface — CRUD, membership, invitations, and authority-as-a-service"
---

The `workspaces` module is the developer's **authorization-server SDK** for the [Workspaces bundle](/v8/data-models/workspace). It exposes the full surface: workspace CRUD, membership management, the invitation lifecycle, and the service-key **authority read** you use to make your own app-level decisions.

<Note>
  **Requires the `workspaces` bundle.** See [Bundles](/v8/bundles) to install it. As on every Node SDK call that acts as a user, the user the action is performed **as** goes in [`actingUserId`](/v8/node-sdk/overview#acting-on-behalf-of-a-user), and every workspace call **accepts** it. It is required on every call — see the note below. For `fetchWorkspaceAuthority`, `actingUserId` is the user whose standing is resolved.
</Note>

<Note>
  **This SDK is not required in order to manage workspaces.** All 22 endpoints are equally available to a browser or mobile app through the [`@sublay/core` hooks](/v8/sdk/workspaces/overview) and [`@sublay/js`](/v8/js-sdk/workspaces), acting as the signed-in user and subject to the same ownership / capability / rank rules. What the node SDK adds is performing an action **as some other named user** through `actingUserId`, which only a service key may send.
</Note>

<Warning>
  **Naming an `actingUserId` means *being* that user.** It is not a hint or an
  audit tag — it **binds**. Every check the named user would face runs: the
  capability gate, the owner-only gate, the rank guard, no-escalation, and the
  roster/standing fencing. If that user would be refused, so are you. There is
  no mode in which a key acts on a workspace with authority of its own.

  So an unrestricted backend action is performed **as the workspace
  owner**: the owner resolves the full capability
  vocabulary and apex rank, and the resulting webhooks carry that user id. Treat that id as a *claim*, not proof — a key may name any
  user in the project (an id that isn't one gets `404 workspace/user-not-found`).
  Two consequences bite first-time integrators —
  [`acceptWorkspaceInvite`](#acceptworkspaceinvite) requires the invite to be
  actually addressed to the named user *and* that user's email to be verified,
  and a rank tier cannot grow itself (see
  [`createWorkspaceInvite`](#createworkspaceinvite)). Full rule:
  [Acting on behalf of a user](/v8/sdk/workspaces/overview#acting-on-behalf-of-a-user).
</Warning>

<Note>
  **The actor is required on every call.** `actingUserId` is typed
  **required** on every function in this module. The server refuses a key that
  names nobody with `400 workspace/missing-user-id` on every workspace route but
  one: on [Fetch Workspace](/v8/api-reference/workspaces/fetch-workspace) it
  gets the anonymous view, which for a workspace is always a `404`.
</Note>

<Warning>
  **Absent, not falsy — and undeclared fields are refused, not ignored.**
  `actingUserId: ""` or `null` is a `400` that names the field, so
  `actingUserId: user?.id ?? ""` fails with an error about the actor rather than
  a missing-user error.

  Every workspaces endpoint also declares its fields exactly, and refuses any
  top-level field it does not declare, for every caller — in the body of a
  write, with
  `{ "error": "Unrecognized key: \"onBehalfOf\"", "code": "workspace/invalid-body" }`
  (plural `Unrecognized keys: "a", "b"` for two or more), and in the query
  string of a read or delete, with `workspace/invalid-query`. This SDK sends
  each call's fields where the server reads them: the query string on reads and
  deletes (`deleteWorkspace`, `leaveWorkspace` and `removeWorkspaceMember`
  included), the JSON body on writes. So
  `onBehalfOf`, `impersonate` and `acting_user_id` all fail at the wire rather
  than being dropped silently. A `userId` anywhere in a
  body or query is refused with a message of its own — the sole exception is the
  invitee in `createWorkspaceInvite`'s **body**, and even there a query
  `?userId=` is refused like everywhere else. A non-UUID id in a path is a
  `400 workspace/invalid-params` rather than a `500`. Full list with the
  reasoning: [Shapes the server rejects](/v8/sdk/workspaces/overview#shapes-the-server-rejects).

  One of those rules cannot bite you through this SDK: a body whose content-type
  no parser reads is refused when a key names nobody, and this SDK serializes every
  body it sends as `application/json`. It is a hazard for hand-rolled `fetch()`
  calls, not for `sublay.workspaces.*`.
</Warning>

<Warning>
  **Pass only the documented fields — the props object is sent whole.**
  `createWorkspace` and its siblings hand your object straight to the request
  body, so a convenience spread carries whatever else it holds into the request,
  and the endpoint refuses it:

  ```typescript
  // ❌ 400 — `slug` and `plan` are not fields of this endpoint.
  await sublay.workspaces.createWorkspace({ ...orgTemplate, actingUserId });

  // ✅ Name the fields.
  await sublay.workspaces.createWorkspace({
    actingUserId,
    name: orgTemplate.name,
    metadata: { slug: orgTemplate.slug, plan: orgTemplate.plan },
  });
  ```

  Your own data belongs in `metadata`, which is opaque to Sublay and accepts any
  JSON. Strictness governs **top-level** keys only, so nothing inside `metadata`
  is inspected.
</Warning>

Read the concepts first: [capabilities vs permissions](/v8/data-models/workspace-member#the-two-arrays-capabilities-vs-permissions), [rank](/v8/data-models/workspace-member#rank-semantics), [reach & ownership](/v8/data-models/workspace#reach-and-the-wall-door-rule), and the [identity-matched, no-token invite model](/v8/data-models/workspace-invitation#acceptance-model).

## Workspace lifecycle

### createWorkspace

```typescript
const workspace = await sublay.workspaces.createWorkspace({
  actingUserId: "usr_owner",      // becomes the owner
  name: "Acme Inc",
  parentWorkspaceId: null,        // omit/null → root; set → child
});
```

Root creation requires the acting user to have a **verified email**. Child creation requires the `create-sub-workspace` capability on the parent; the creator becomes the child's owner.

<Warning>
  **A service key does NOT bypass the verified-email gate.** The `actingUserId` you act as must itself be verified, or the call returns `403 workspace/email-not-verified`. This matches `acceptWorkspaceInvite` and `transferWorkspaceOwnership` — all three doors into ownership check it, so **every** workspace owner has a confirmed email. A key lets you act *as* a user; it does not make that user verified.
</Warning>

<ParamField body="actingUserId" type="string" required>The user the workspace is created as (becomes the owner).</ParamField>
<ParamField body="name" type="string" required>Display name (1–100 characters).</ParamField>
<ParamField body="metadata" type="object">Opaque developer data.</ParamField>
<ParamField body="parentWorkspaceId" type="string">Parent for child creation; absent/`null` → root.</ParamField>

### fetchManyWorkspaces

Lists a user's workspaces (paginated): by default every workspace they can open, or with `relation: "direct"` only the ones they own or are a member of. Each row carries `reasons`, why that user can open it.

```typescript
const { data, pagination } = await sublay.workspaces.fetchManyWorkspaces({
  actingUserId: "usr_owner",
  relation: "direct", // only workspaces the user owns or is a member of
  parentWorkspaceId: "any", // every level
  sortDir: "asc", // oldest first: parents before their children
  page: 1,
  limit: 20,
  include: "memberCount", // each row gains a `memberCount`
});
```

<ParamField body="actingUserId" type="string" required>The user whose workspaces to list, and whose `reasons` each row carries.</ParamField>
<ParamField body="relation" type='"reachable" | "direct"'>Which workspaces the list holds. `"reachable"` or left out (the default): every workspace the user can open — owned, a member of, under a workspace they own, or reached by a capability held on an ancestor. `"direct"`: only the workspaces they own or have a member row on.</ParamField>
<ParamField body="parentWorkspaceId" type='string | "none" | "any"'>Narrows the list by where each workspace sits in the tree, within `relation`. `"none"`: top-level workspaces only. A workspace id: the workspaces directly under that workspace; an id that matches no workspace returns an empty page, not a 404. `"any"` or left out: workspaces at every level (the default).</ParamField>
<ParamField body="sortDir" type='"desc" | "asc"'>Order by creation time. `"desc"` or left out (the default): newest first. `"asc"`: oldest first, which puts every parent before its children — see [Building a workspace switcher](/v8/sdk/workspaces/overview#building-a-workspace-switcher).</ParamField>
<ParamField body="page" type="number" />
<ParamField body="limit" type="number" />
<ParamField body="include" type="WorkspaceIncludeParam">A single value or an array, sent as a query param. The only value is `"memberCount"`: it adds a `memberCount` to **every row** — the workspace's direct member count, resolved in one grouped query over the returned page rather than one request per row. Omit it and the field is absent from each row.</ParamField>

## Membership

### fetchWorkspaceMembers

Returns the [unified roster](/v8/api-reference/workspaces/members/list-members) (`WorkspaceRosterResponse`), or `WorkspaceRosterCountsResponse` when `countOnly` is set.

<Note>
  The roster fences the authority-bearing reason fields (`rank`, `relativeRank`, `capabilities`, `permissions`) from callers who cannot manage people on the workspace — **per node**, so with `include=descendants` each `descendant-member` reason is judged against the acting user's resolved standing on *that* descendant, and authority over the parent does not unfence a **sealed** child. The fence evaluates against the `actingUserId` you pass, so a key acting as a plain member receives the same partial roster that member would. The SDK types mark the four fields optional for that reason.

  A `member` reason carries both rank coordinates: absolute `rank`, and `relativeRank` — that member's position as an offset from **the caller**, meaning the acting user when you name one. `descendant-member` reasons carry `rank` only, since their ranks belong to another node's ladder.
</Note>

```typescript
const roster = await sublay.workspaces.fetchWorkspaceMembers({
  workspaceId: "ws_abc",
  include: ["ancestorOwners", "descendants"],
  actingUserId: "usr_admin",
});

const counts = await sublay.workspaces.fetchWorkspaceMembers({
  workspaceId: "ws_abc",
  countOnly: true,
  actingUserId: "usr_admin",
});
```

<ParamField body="workspaceId" type="string" required />
<ParamField body="include" type="WorkspaceMemberIncludeParam">A single value or an array of `"ancestorOwners"`, `"reachHolders"`, `"descendants"`.</ParamField>
<ParamField body="countOnly" type="boolean" />
<ParamField body="actingUserId" type="string" required>The user to act as. Sent as a query param. Roster visibility and the authority-field fence both evaluate against them.</ParamField>

### fetchWorkspaceMemberStanding

```typescript
const standing = await sublay.workspaces.fetchWorkspaceMemberStanding({
  workspaceId: "ws_abc",
  targetUserId: "usr_pat",
  actingUserId: "usr_admin",
});
```

<ParamField body="workspaceId" type="string" required />
<ParamField body="targetUserId" type="string" required>The user whose standing to read.</ParamField>
<ParamField body="actingUserId" type="string" required>The user to act as. Sent as a query param. Roster visibility and the authority-field fence both evaluate against them (and a caller always sees their **own** access, so `actingUserId === targetUserId` is never fenced).</ParamField>

Returns `WorkspaceMemberStanding`. On its `user` field **only `id` is guaranteed** (`WorkspaceStandingUser`): the server returns the full user record when the user row still exists and falls back to `{ id }` alone when it does not — a deleted user with a lingering membership row is a reachable case. Read the rest defensively (`standing.user.username ?? "Deleted user"`).

`reasons` is an array of structured `{ type, viaWorkspaceId? }` entries — the same shape a roster entry's `reasons` carries — so you learn not just the kind of standing but which ancestor grants it. `capabilities` / `permissions` / `rank` / `relativeRank` are typed **optional** because the server omits them for callers who cannot manage people (`relativeRank` is fenced with `rank` — it is `rank` minus an anchor the caller already knows). The fence evaluates against the `actingUserId` you pass, who may well not see them.

### updateWorkspaceMember

```typescript
await sublay.workspaces.updateWorkspaceMember({
  workspaceId: "ws_abc",
  targetUserId: "usr_pat",
  actingUserId: "usr_admin",
  capabilities: ["view", "invite"],
  rank: 3,

```

Powerful fields require `edit-member-access` + rank rules + no-escalation; cosmetic fields require `edit-member-profile`.

Rank moves in **either coordinate** — `rank` (absolute) or `relativeRank` (an offset from `actingUserId`), never both. Omitting both means **rank unchanged**. See [choosing a rank](/v8/sdk/workspaces/overview#choosing-a-rank).

<ParamField body="capabilities" type="string[]" />
<ParamField body="permissions" type="string[]" />
<ParamField body="rank" type="number">Absolute. Mutually exclusive with `relativeRank`; omit both to leave rank unchanged.</ParamField>
<ParamField body="relativeRank" type="number">An offset from the **acting user** — `1` = one rung below them. Must be `>= 1`. Anchored on their member row on this workspace if they hold one, apex otherwise, so a key acting as the owner resolves `relativeRank: 1` to rank `0`. Resolved to an absolute rank at write time and frozen. No default.</ParamField>

### removeWorkspaceMemberFromSubtree

```typescript
const result = await sublay.workspaces.removeWorkspaceMemberFromSubtree({
  workspaceId: "ws_root",
  targetUserId: "usr_pat",
  actingUserId: "usr_admin",
});
// result: { removedCount, removed, skippedCount, skipped }

if (result.skippedCount > 0) {
  // NOT fully offboarded — memberships survived in branches the ACTING user
  // (`actingUserId`) cannot reach. `id`/`name` are null where they have no standing.
  console.warn("Still a member of", result.skippedCount, "workspace(s):", result.skipped);
}
```

If the target owns this workspace or **any** descendant — including sealed ones outside the acting user's reach — it is refused with `409 workspace/owns-descendants` and nothing is removed. The 409 body lists them in `ownedWorkspaces` (`{ id, name }`, both `null` where the acting user has no standing on that workspace; named entries first) with the total in `ownedCount`; an owner of each workspace (or an ancestor owner) must transfer or delete it before a retry. See [Remove From Subtree](/v8/api-reference/workspaces/members/remove-from-subtree).

<Note>
  **`skippedCount` reflects the acting user, not the key.** The sweep is partial for a **non-owner** actor, and `actingUserId` is **required** on this call — a key always names someone, and is bound by their reach and their per-node rank. Name a non-owner admin and you can get a partial sweep, exactly as that admin would; name the owner for the god-path that clears every descendant. Always assert on `skippedCount` rather than assuming `removedCount` means the user is fully offboarded.
</Note>

<ParamField body="workspaceId" type="string" required />
<ParamField body="targetUserId" type="string" required>The user to offboard.</ParamField>
<ParamField body="actingUserId" type="string" required>The acting user.</ParamField>

## Invitations

### createWorkspaceInvite

```typescript
const invite = await sublay.workspaces.createWorkspaceInvite({
  workspaceId: "ws_abc",
  email: "pat@example.com",   // OR userId / username
  capabilities: ["view"],
  permissions: ["deploy"],
  // One rung below the inviter. Omitting both rank fields means exactly this.
  relativeRank: 1,
  actingUserId: "usr_admin",  // the inviter
});
```

Requires the `invite` capability. Here `userId`/`username` (if used) address the invite **target**; the **inviter** is `actingUserId`, which is required and recorded as the invitation's `invitedBy`. Email matching against existing accounts is **case-insensitive**.

The invited grant is floored by the inviter's own standing: no-escalation on `capabilities`/`permissions`, and a rank strictly below the inviter's own. Both floors are skipped for an owner.

The invited rank is named in **either coordinate** — `rank` (absolute) or `relativeRank` (an offset from the inviter) — and they are mutually exclusive. Supplying **neither** applies `relativeRank: 1`, one rung below the inviter, which is well defined for every inviter (one with no member row here anchors at apex, so the default lands on rank `0`) and by construction never trips the rank floor.

<Note>
  **A tier cannot grow itself.** Acting as a rank-5 manager with a direct member row you can invite rank 6, 7, 8… but **never another rank 5**, and no ranked member clears the floor for rank 0. The floor binds only an inviter with a **direct member row** on the workspace — an owner or ancestor owner and a reach-holder with no direct row skip it entirely. If your product has a server-driven "add a manager" action, act as the owner for it. See [Acting on behalf of a user](/v8/sdk/workspaces/overview#acting-on-behalf-of-a-user).
</Note>

<Warning>
  **The project must have `workspaces.inviteAcceptUrl` configured**, or this call fails with `409 workspace/missing-invite-accept-url` and persists nothing. It has no default, and a service key does not exempt you. Applies even when the invitee already has an account. See [Project settings](/v8/sdk/workspaces/overview#project-settings).
</Warning>

<ParamField body="workspaceId" type="string" required />
<ParamField body="email" type="string">One of `email`/`userId`/`username`.</ParamField>
<ParamField body="userId" type="string">Invite target user id.</ParamField>
<ParamField body="username" type="string">Invite target username.</ParamField>
<ParamField body="capabilities" type="string[]" />
<ParamField body="permissions" type="string[]" />
<ParamField body="rank" type="number">Absolute. **Not required** — mutually exclusive with `relativeRank`, and omitting both applies the `relativeRank: 1` default.</ParamField>
<ParamField body="relativeRank" type="number" default="1">An offset from the inviter — `1` = one rung below them. Must be `>= 1`. Anchored on the inviter's member row on this workspace if they hold one, apex otherwise. A **snapshot**: resolved to an absolute rank here and frozen, so a later promotion or demotion of the inviter does not move the pending invite. Note the collision caveat, which is at its sharpest here: an inviter with no member row on this workspace — typically the owner — anchors at **apex**, so the default mints **rank 0** — the most senior rung — for every invitee. A backend invite flow that wants people at the *bottom* of the ladder must name an absolute `rank`, or name an `actingUserId` who actually sits in the ladder. For an in-ladder inviter the default instead puts a whole cohort on one rung, where equals cannot manage each other. See [choosing a rank](/v8/sdk/workspaces/overview#choosing-a-rank).</ParamField>
<ParamField body="title" type="string" />
<ParamField body="actingUserId" type="string" required>The **inviter** to act as. The `invite` capability, the no-escalation and rank floors run against their standing, and the invitation's `invitedBy` records them. Distinct from `userId`, which is the invitee.</ParamField>

### acceptWorkspaceInvite

## Authority-as-a-service

### fetchWorkspaceAuthority

The **service-key authority read** — the crux of the server-side surface. Resolve any user's standing on a workspace, then run your own permission check with a one-line `.includes()`.

```typescript
const authority = await sublay.workspaces.fetchWorkspaceAuthority({
  workspaceId: "ws_abc",
  actingUserId: "usr_pat",   // the user to act as; their standing is resolved
});

// { reasons: [{ type, viaWorkspaceId? }], capabilities, permissions, rank }
if (authority.permissions.includes("deploy")) {
  // your app allows the action
}
```

<ParamField body="workspaceId" type="string" required />
<ParamField body="actingUserId" type="string" required>The acting user whose resolved standing to read.</ParamField>

`reasons` entries carry `viaWorkspaceId` on `ancestor-owner` / `reach-holder`, naming the ancestor responsible — so when a user has authority you did not expect, you can tell exactly which node to go fix. `capabilities` is the fully-resolved set, and **`view` is implied by every other capability**: any user with standing carries it, while a user with no relation at all comes back with `reasons: []` and an empty capability set. There is no `relativeRank` on this read — it is an offset from the caller, and here the caller is the subject, so `rank` is the coordinate it reports.

Sublay never consumes your opaque `permissions` — there is deliberately no `?permission=` check or `can()` helper.
