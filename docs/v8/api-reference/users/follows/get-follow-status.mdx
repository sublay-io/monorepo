---
title: "Get Follow Status"
api: "GET /v8/:projectId/users/:userId/follow"
description: "Check whether the authenticated user follows a specific user"
---

Returns the follow status between the authenticated user and the specified user. If the authenticated user is following, the response includes the follow record ID and timestamp.

## Path Parameters

<ParamField path="userId" type="string" required>
  The Sublay user ID (UUID) of the user to check follow status for.
</ParamField>

## Query Parameters

<ParamField query="actingUserId" type="string">
  Service key only, and required with one: the user this request acts as, whose follow of the user in the path is checked. A user token always acts as its own user and must not send it (`400 follow/acting-user-not-allowed`).
</ParamField>

## Response

On success, returns HTTP `200`. The shape differs based on follow status:

**When following:**

<ResponseField name="isFollowing" type="boolean">
  `true` — the authenticated user follows this user.
</ResponseField>

<ResponseField name="followId" type="string">
  ID of the follow record.
</ResponseField>

<ResponseField name="followedAt" type="string">
  ISO timestamp of when the follow was created.
</ResponseField>

**When not following:**

<ResponseField name="isFollowing" type="boolean">
  `false`.
</ResponseField>

## Error Responses

<AccordionGroup>
  <Accordion title="Missing User — 400">
    A service key sent no `actingUserId`.
    ```json
    {
      "error": "Missing user ID",
      "code": "follow/missing-user-id"
    }
    ```
  </Accordion>
  <Accordion title="Acting User Not Allowed — 400">
    A user token sent `actingUserId`, even naming its own user. Only a service key names the user it acts as; a user token always acts as its own user.
    ```json
    {
      "error": "actingUserId is only accepted with a service key. A user's own token always acts as that user.",
      "code": "follow/acting-user-not-allowed"
    }
    ```
  </Accordion>
</AccordionGroup>
