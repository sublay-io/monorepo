---
title: "Fetch Notifications"
api: "GET /v8/:projectId/app-notifications"
description: "Get a paginated list of app notifications for the authenticated user"
---

Returns a paginated list of app notifications for the currently authenticated user, ordered newest first. Notifications are scoped to the calling user — a user cannot read another user's notifications.

<Note>
  This endpoint requires an authenticated user. Include a valid `Authorization: Bearer <accessToken>` header, or use a service key and name the user in `actingUserId`.
</Note>

## Query Parameters

<ParamField query="page" type="number" default="1">
  Page number (1-indexed).
</ParamField>

<ParamField query="limit" type="number" default="5">
  Number of results per page. Maximum `50`.
</ParamField>

<ParamField query="actingUserId" type="string">
  Service key only, and required with one: the user this request acts as. Their notifications are listed. A user token always acts as its own user and must not send it (`400 app-notification/acting-user-not-allowed`).
</ParamField>

## Response

Returns a paginated envelope containing an array of notification objects.

<ResponseField name="data" type="array">
  List of app notification objects.
  <Expandable title="AppNotification properties">
    <ResponseField name="id" type="string">
      Unique notification ID (UUID).
    </ResponseField>
    <ResponseField name="projectId" type="string">
      ID of the project this notification belongs to.
    </ResponseField>
    <ResponseField name="userId" type="string">
      ID of the user this notification belongs to.
    </ResponseField>
    <ResponseField name="type" type="string">
      Notification type string (e.g., `"new-follower"`, `"comment-reply"`). Defined by your webhook integration.
    </ResponseField>
    <ResponseField name="action" type="string">
      Deep-link action string used by the client to route the user when the notification is tapped.
    </ResponseField>
    <ResponseField name="isRead" type="boolean">
      Whether the user has marked this notification as read.
    </ResponseField>
    <ResponseField name="metadata" type="object">
      Arbitrary key-value data attached to the notification. Contents depend on the notification type.
    </ResponseField>
    <ResponseField name="createdAt" type="string">
      ISO 8601 timestamp when the notification was created.
    </ResponseField>
    <ResponseField name="updatedAt" type="string">
      ISO 8601 timestamp when the notification was last updated.
    </ResponseField>
  </Expandable>
</ResponseField>

<ResponseField name="pagination" type="object">
  Pagination metadata.
  <Expandable title="properties">
    <ResponseField name="page" type="number">Current page number.</ResponseField>
    <ResponseField name="pageSize" type="number">Number of results per page.</ResponseField>
    <ResponseField name="totalPages" type="number">Total number of pages.</ResponseField>
    <ResponseField name="totalItems" type="number">Total number of notifications.</ResponseField>
    <ResponseField name="hasMore" type="boolean">Whether more pages exist after this one.</ResponseField>
  </Expandable>
</ResponseField>

## Error Responses

<AccordionGroup>
  <Accordion title="Missing token — 401">
    No `Authorization` header was sent. The body is `text/plain`, not JSON:

    ```text
    Unauthorized
    ```
  </Accordion>
  <Accordion title="Expired or invalid token — 403">
    The header was sent but the token failed verification. Refresh the access
    token and retry. The body is `text/plain`, not JSON:

    ```text
    Forbidden
    ```
  </Accordion>
  <Accordion title="Invalid Query — 400">
    ```json
    {
      "error": "...",
      "code": "app-notification/invalid-query"
    }
    ```
  </Accordion>
  <Accordion title="Missing User — 400">
    A service key sent no `actingUserId`.
    ```json
    {
      "error": "Missing user ID",
      "code": "app-notification/missing-user-id"
    }
    ```
  </Accordion>
  <Accordion title="Acting User Not Allowed — 400">
    A user token sent `actingUserId`, even naming its own user. Only a service key names the user it acts as; a user token always acts as its own user.
    ```json
    {
      "error": "actingUserId is only accepted with a service key. A user's own token always acts as that user.",
      "code": "app-notification/acting-user-not-allowed"
    }
    ```
  </Accordion>
  <Accordion title="Unsupported Parameter — 400">
    The request sent `userId`. On this route the user a service key acts as is `actingUserId`.
    ```json
    {
      "error": "`userId` was renamed to `actingUserId`: send the user this service key acts as in `actingUserId`.",
      "code": "app-notification/unsupported-param",
      "param": "userId"
    }
    ```
  </Accordion>
</AccordionGroup>
