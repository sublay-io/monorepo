---
title: "List My Invites"
api: "GET /v8/:projectId/me/workspace-invites"
description: "The authenticated user's live pending invites"
---

Returns the authenticated user's **live** pending invites (`status = 'pending' AND expiresAt > now`), matched by **`userId`** (no email-string matching at query time — invitations bind to `userId` at invite time or via the signup-attach step).

<Note>
  **Surfacing is NOT verification-gated** — a user sees pending invites right after signup (which nudges them to verify). The verified-email check applies when the user **acts** on an invite — [accept](/v8/api-reference/workspaces/invitations/accept-invite) *and* [decline](/v8/api-reference/workspaces/invitations/decline-invite).
</Note>

## Query Parameters

<ParamField query="actingUserId" type="string" required>
  Service keys only — the user to act as, whose invites are read. **Required for a key:** this is an *inbox* read, so a key that names nobody is refused with `400 workspace/missing-user-id`.

  A user token always acts as its own user and must not send it (`400 workspace/acting-user-not-allowed`). See [Acting on behalf of a user](/v8/sdk/workspaces/overview#acting-on-behalf-of-a-user).
</ParamField>

## Response

```json
{ "data": [ /* MyWorkspaceInvitation[] — see below */ ] }
```

Each item is a `MyWorkspaceInvitation`: a [WorkspaceInvitation](/v8/data-models/workspace-invitation) object with one difference from every other invite read — `invitedBy` is a populated `{ id, name, username, avatar, reputation }` object instead of a bare user id, and a sibling `workspace: { id, name }` is included. The invitee has no other reach on the workspace they're invited to or on the inviter, so both are embedded here to make this endpoint self-sufficient for rendering an invite — see the [note on the data model page](/v8/data-models/workspace-invitation#properties) for the full enriched shape.

## Error Responses

<AccordionGroup>
  <Accordion title="Missing Acting User — 400">
    ```json
    { "error": "A service key must send actingUserId: the user this request acts as.", "code": "workspace/missing-user-id" }
    ```
    A service key called this route without naming an `actingUserId`. An inbox belongs to a person; there is no app-level inbox to return.
  </Accordion>
  <Accordion title="Acting User Not Allowed — 400">
    ```json
    { "error": "actingUserId is only accepted with a service key. A user's own token always acts as that user.", "code": "workspace/acting-user-not-allowed" }
    ```
    A user token sent `actingUserId`, even naming its own user. Only a service key names the user it acts as; a user token always acts as its own user.
  </Accordion>
  <Accordion title="User Not Found — 404">
    ```json
    { "error": "No user with this actingUserId exists in this project.", "code": "workspace/user-not-found" }
    ```
    Returned when a service key names an `actingUserId` that isn't a user in this project.
  </Accordion>
</AccordionGroup>
