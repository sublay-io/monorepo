---
title: "Decline Invite"
api: "POST /v8/:projectId/workspace-invites/:inviteId/decline"
description: "Decline an invitation — identity-matched and verification-gated"
---

Declines an invitation. Identity-matched (the caller must be the invite's target) **and** verification-gated — a **verified email is required**, exactly as it is to [accept](/v8/api-reference/workspaces/invitations/accept-invite). Without that gate, someone who signed up with another person's address and never verified it could burn the real target's invite by moving it to the terminal `declined` state. This is **not** a key-bypass gate: a service key acting as a named `actingUserId` still requires *that* user to be verified.

Marks the invite `declined` and fires `workspace.invite.declined`.

## Path Parameters

<ParamField path="inviteId" type="string" required>
  The invitation UUID.
</ParamField>

## Body Parameters

<ParamField body="actingUserId" type="string" required>
  Service keys only — the declining user (must be the invite's target). **Required for a key:** a decline is an act by the invitee, so a key that names nobody is refused with `400 workspace/missing-user-id`.

  A user token always acts as its own user and must not send it (`400 workspace/acting-user-not-allowed`). See [Acting on behalf of a user](/v8/sdk/workspaces/overview#acting-on-behalf-of-a-user).
</ParamField>

## Response

```json
{ "success": true }
```

## Error Responses

<AccordionGroup>
  <Accordion title="Email Not Verified — 403">
    ```json
    { "error": "A verified email is required to decline an invitation.", "code": "workspace/email-not-verified" }
    ```
  </Accordion>
  <Accordion title="Not the Target — 404">
    A caller who is not the invitation's target receives the **same** `404` as a
    non-existent invitation.
    ```json
    { "error": "Invitation not found.", "code": "workspace/invite-not-found" }
    ```
  </Accordion>
  <Accordion title="Invite Terminal — 409">
    ```json
    { "error": "This invitation is no longer pending.", "code": "workspace/invite-terminal" }
    ```
  </Accordion>
  <Accordion title="Missing Acting User — 400">
    ```json
    { "error": "A service key must send actingUserId: the user this request acts as.", "code": "workspace/missing-user-id" }
    ```
    A service key called this route without naming an `actingUserId`. A decline is an act by the invitee; there is nobody to attribute it to.
  </Accordion>
  <Accordion title="Acting User Not Allowed — 400">
    ```json
    { "error": "actingUserId is only accepted with a service key. A user's own token always acts as that user.", "code": "workspace/acting-user-not-allowed" }
    ```
    A user token sent `actingUserId`, even naming its own user. Only a service key names the user it acts as; a user token always acts as its own user.
  </Accordion>
  <Accordion title="User Not Found — 404">
    ```json
    { "error": "No user with this actingUserId exists in this project.", "code": "workspace/user-not-found" }
    ```
    Returned when a service key names an `actingUserId` that isn't a user in this project.
  </Accordion>
  <Accordion title="Invalid Path Parameter — 400">
    ```json
    { "error": "Invalid invitation id: expected a UUID.", "code": "workspace/invalid-params" }
    ```
    Every path id on the workspaces bundle is checked for UUID shape before the route runs, so a malformed one is a plain `400` rather than a `500` from the database.
  </Accordion>
</AccordionGroup>
