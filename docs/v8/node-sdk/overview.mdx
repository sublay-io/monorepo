The `@sublay/node` SDK gives you full programmatic access to the Sublay API from any Node.js environment. It is designed for **server-side use only** — backend endpoints, Next.js server actions, webhook handlers, cron jobs, and scripts.

<Note>
  This SDK requires a **secret API key** and must never be used in client-side
  code or shipped to the browser.
</Note>

## Installation

```bash
npm install @sublay/node
```

## Initialization

Create a single `SublayClient` instance at startup and reuse it throughout your application.

```typescript
import { SublayClient } from "@sublay/node";

const sublay = await SublayClient.init({
  projectId: process.env.SUBLAY_PROJECT_ID!,
  apiKey: process.env.SUBLAY_API_KEY!,
});
```

### Configuration

<ParamField body="projectId" type="string" required>
  Your Sublay project ID, found in the dashboard under **Settings → General**.
</ParamField>

<ParamField body="apiKey" type="string" required>
  Your secret API key from the dashboard. Keep this in an environment variable —
  never commit it to source control.
</ParamField>

## Modules

Once initialized, all functionality is accessed through module namespaces on the client:

```typescript
sublay.auth              // Authentication — sign up, sign in, tokens, passwords
sublay.users             // User profiles, follow/connection actions
sublay.entities          // Content entities — CRUD, reactions, drafts
sublay.comments          // Comments — CRUD, reactions
sublay.collections       // Saved-content collections
sublay.follows           // Follow graph — followers, following, counts
sublay.connections       // Mutual connections and requests
sublay.spaces            // Spaces — management, members, moderation, rules
sublay.events            // Events — RSVPs, hosts, invites, guest list
sublay.chat              // Conversations, messages, members, reactions, read state
sublay.search            // Search and AI Q&A
sublay.reports           // Content reports and the moderation queue
sublay.appNotifications  // In-app notification feed
sublay.storage           // File and image uploads, read, delete
```

## Acting on behalf of a user

Your service key authenticates as the project, not as any single end user. So functions that operate **on a user's behalf** take `actingUserId`: the user the service key acts as (saving to a collection, reading a notification feed, filing a report, listing connections, moderating a space). The request runs with that user's permissions — their role in a space, their hosting of an event, their membership of a conversation — and is recorded as theirs.

`userId` only ever names a user the request is **about**: a target, such as the user to follow, block or add to a conversation, or a filter, such as the author filter on `fetchManyEntities`. So a call that acts on one user toward another carries both, for example `createFollow({ userId: target, actingUserId: actor })`.

Where a method requires an acting user and you leave `actingUserId` out, the server answers `400 <resource>/missing-user-id`. Reads shaped by who is looking (the `entities`, `comments` and `spaces` reads and reaction lists, `spaces.fetchSpaceMembers`, `fetchSpaceTeam` and `fetchChildSpaces`, the `events` reads and `fetchEventRsvps`, `reputation.listGrants`, the `users` profile and suggestion reads, the follower, following and connection lists and their counts, `users.fetchCommentsByUserId`, `search.searchUsers`, `search.searchContent` and `search.askContent`) take it optionally: with it you get exactly that user's view, without it the anonymous one (for `listGrants`, that of a signed-in user in no conversation). `entities.updateEntity`, `deleteEntity` and `publishDraft`, `comments.updateComment` and `deleteComment`, and `storage.deleteFile` act as the record's owner: pass the author as `actingUserId` when the record has one, and leave it out only for an app-owned record. `entities.createEntity` and the `storage` uploads without `actingUserId` create an app-owned record; a draft needs `actingUserId`. `spaces.deleteSpace` and every `workspaces` function require `actingUserId` and run with exactly that user's role or standing. `users.updateUser` requires `actingUserId`, and it must be the user being updated: the update behaves exactly as that user's own token. `users.deleteUser`, `push.send`, `reputation.mintGrant`, `entities.incrementEntityViews` and the `tables` table and column functions (`createTable`, `dropTable`, `addColumn`, `dropColumn`) act as your app and take no `actingUserId`. Endpoints that need the user's own access token (password change, account deletion, OAuth identities, push device registration) refuse service keys, so the SDK has no functions for them. The SDK's types send it under the right name; a raw `userId` in its place is refused by most endpoints with `400 <resource>/unsupported-param`. See [Authentication → Acting as a user](/v8/authentication#acting-as-a-user).

<Note>
  `oauth` is intentionally not exposed by this SDK (it's a browser redirect flow).
</Note>

## Paginated Responses

Functions that return lists use a shared `PaginatedResponse<T>` shape:

```typescript
{
  data: T[];
  pagination: {
    page: number;
    pageSize: number;
    totalPages: number;
    totalItems: number;
    hasMore: boolean;
  };
}
```

Pass `page` and `limit` to any list function to control pagination.
