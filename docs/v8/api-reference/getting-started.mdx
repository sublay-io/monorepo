The Sublay REST API is a project-scoped HTTP API. All endpoints follow the same base structure and share common conventions for authentication, pagination, and error reporting.

## Base URL

All API requests are made to:

```
https://api.sublay.io/v8/:projectId
```

Replace `:projectId` with the UUID of your Sublay project, which you can find in the [Sublay dashboard](https://dash.sublay.io).

So every endpoint takes the form:

```
https://api.sublay.io/v8/:projectId/<endpoint>
```

The project is read from the path only. Don't send `projectId` in the query string or the body, or an `x-sublay-project-id` header: each is refused with `400 project/wrong-location`. The one exception is a custom-table column named `projectId`, which stays writable in the row bodies of [Insert Row](/v8/api-reference/custom-tables/insert-row) and [Update Row](/v8/api-reference/custom-tables/update-row).

## Request Format

Most endpoints accept `application/json`. Endpoints that support file uploads accept `multipart/form-data`. The `Content-Type` header should be set accordingly.

Where each field goes is decided by the method: the path holds the resource, GET and DELETE take every other field in the query string and no body, and POST, PATCH and PUT take every other field in the body, `actingUserId` included. Each field is read from one place; sent elsewhere, it is refused with a `400` that names the right place:

| Code | When |
|---|---|
| `<area>/body-not-allowed` | A GET or DELETE has a body. |
| `<area>/wrong-location` | A POST, PATCH or PUT has a body field (or `actingUserId`) in its query string. |
| `project/wrong-location` | `projectId` anywhere but the path, or a project-id header. |
| `<area>/unsupported-route` | A route v8 moved; `error` names the one to call. |

See [Where each input goes](/v8/authentication#where-each-input-goes).

```http
POST /v8/:projectId/auth/sign-in
Content-Type: application/json

{
  "email": "user@example.com",
  "password": "secret"
}
```

## Ids

Every Sublay record id (`spaceId`, `entityId`, `userId`, …) is a UUID. Ids are accepted in either case and the server lowercases them; record ids in responses are lowercase.

An id that isn't a UUID is refused with `400`:

- **In the URL path:** checked before sign-in, permissions or any lookup (only a missing bundle, `403 database/tables-not-available`, is reported first). Code `<area>/invalid-params`, where `<area>` is the endpoint's area (`space`, `entity`, `chat`, …):

  ```json
  {
    "error": "Invalid space id: expected a UUID.",
    "code": "space/invalid-params"
  }
  ```

- **In the query string or body:** code `<area>/invalid-query` or `<area>/invalid-body`, with `error` naming the field.

`foreignId` and `sourceId` are your own strings, not Sublay ids, so they accept any text.

## Authentication

Protected endpoints require a `Bearer` token in the `Authorization` header:

```http
GET /v8/:projectId/app-notifications
Authorization: Bearer <accessToken>
```

See [Authentication](/v8/api-reference/authentication) for full details on obtaining and refreshing tokens.

## Pagination

Endpoints that return lists use cursor-free offset pagination. Pass `page` and `limit` as query parameters:

| Parameter | Default | Max | Description |
|-----------|---------|-----|-------------|
| `page` | `1` | — | Page number (1-indexed) |
| `limit` | varies | varies | Results per page (endpoint-specific) |

Paginated responses always return the same envelope:

```json
{
  "data": [...],
  "pagination": {
    "page": 1,
    "pageSize": 20,
    "totalPages": 5,
    "totalItems": 97,
    "hasMore": true
  }
}
```

## Error Format

All error responses follow a consistent structure:

```json
{
  "error": "Human-readable error message.",
  "code": "feature/error-slug"
}
```

Some errors include an additional `field` key (e.g., validation errors on a specific input field):

```json
{
  "error": "Username already taken",
  "field": "username",
  "code": "DUPLICATE_USERNAME"
}
```

### Common HTTP Status Codes

| Status | Meaning |
|--------|---------|
| `200` | Success |
| `201` | Resource created |
| `400` | Bad request — invalid input or missing required fields |
| `401` | Unauthorized — no `Authorization` header, or a request the endpoint requires a user for |
| `403` | Forbidden — token expired or invalid, or a valid token without the required permission |
| `404` | Not found |
| `409` | Conflict — duplicate resource (e.g., email already in use) |
| `429` | Rate limit exceeded |
| `500` | Internal server error |

<Note>
  An **expired token returns `403`, not `401`** — see
  [Authentication](/v8/api-reference/authentication) for why that distinction
  matters when writing your own refresh logic.
</Note>

## Rate Limiting

Each endpoint has its own rate limit, applied per project and per IP. When a limit is exceeded, the API returns `429 Too Many Requests`. Limits are noted per endpoint in this reference.
