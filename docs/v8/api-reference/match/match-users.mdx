---
title: "Match Users"
api: "POST /v8/:projectId/match/users"
description: "Match people by activity-derived interest facets"
---

Ranks other users against an asker's interests, using **activity-derived interest facets** — clusters of what each user has actually engaged with over time, not a static profile. The endpoint returns a structured match breakdown (who, how strongly, and on which facets), optionally with sample content that illustrates each overlap.

Matching runs in two modes:

- **`passive`** — match against the *asker's own* interest facets. Answers "who is like me?" No free-text; the asker's top facets are the query.
- **`directed`** — match against a free-text `query` topic. Answers "who is into biotech?" The query is embedded and ranked against candidate facets.

<Note>
  Requires a **paid plan**, the **`ai-search`** bundle, the **`interest-matching`** bundle, and `interestMatching.enabled` set on the project. See the [Interest Matching](/v8/interest-matching) guide for setup.
</Note>

## Authentication

Every match is run for one user, the **asker**: the signed-in user, or — with a service key — the user named in `actingUserId`, which a key must send (`400 match/missing-user-id` without it). A missing token is rejected with a bare `401`; an invalid or expired token is rejected with `403` (refresh and retry). Both modes act on behalf of the asker:

- **`passive`** ranks candidates against the asker's own facets — the asker *is* the query.
- **`directed`** ranks candidates against a free-text `query`, still on behalf of the asker.

A key acting as a user gets exactly the matches that user's own token would get.

<Warning>
  The rate limit is per IP address: 30 requests per minute in `passive` mode and 10 per minute in `directed` mode. A backend that runs matches for many users from one server shares that budget across all of them.
</Warning>

## Body Parameters

<ParamField body="actingUserId" type="string">
  Service key only, and required with one: the user to find matches for. A user token always acts as its own user and must not send it, and neither may a request with no credentials (`400 match/acting-user-not-allowed`).
</ParamField>

<ParamField body="mode" type="string" required>
  `"passive"` or `"directed"`.
</ParamField>

<ParamField body="query" type="string">
  The free-text topic to match against. **Required in `directed` mode; rejected in `passive` mode.**
</ParamField>

<ParamField body="limit" type="number" default="20">
  Maximum number of matched users to return. Maximum `50`.
</ParamField>

<ParamField body="spaceId" type="string">
  Restrict candidates to users active in this space. Without `includeChildSpaces`, a space the asker can't read (see [Spaces the asker can't read](#spaces-the-asker-cant-read)), or one that doesn't exist, gives `{ "results": [] }`, not an error.
</ParamField>

<ParamField body="includeChildSpaces" type="boolean" default="false">
  Only applies with `spaceId`. When `true`, candidates active anywhere in the space's subtree are eligible, counting only the spaces in it the asker can read. A sub-space the asker can read counts even when they can't read the named space itself; activity in a space they can't read never counts. Ignored without `spaceId`.
</ParamField>

<ParamField body="includeSampleContent" type="boolean" default="false">
  Gate 2 of the two-gate sample exposure. When `true` **and** the project setting `interestMatching.exposeSampleContent` is on, each matched facet includes a few illustrative content snippets from the candidate. Requesting samples while the project setting is off returns `403 match/sample-content-disabled`.
</ParamField>

<ParamField body="excludeSelf" type="boolean" default="true">
  Exclude the asker from the results.
</ParamField>

## Response

Returns the `{ results: [...] }` envelope (a deliberate divergence from `search/*`, which return bare arrays). Results are ordered by descending `score`.

```json
{
  "results": [
    {
      "user": { "id": "usr_...", "name": "..." },
      "score": 3.14,
      "matchedFacets": [
        {
          "similarity": 0.62,
          "askerFacet": { "id": "fac_...", "hotness": 4.2 },
          "candidateFacet": { "id": "fac_...", "hotness": 3.8 },
          "sampleContent": [
            {
              "sourceType": "entity",
              "recordId": "ent_...",
              "content": "…",
              "similarity": 0.71
            }
          ]
        }
      ]
    }
  ]
}
```

**Breakdown fields**

- `score` — the aggregate match score. In `passive` mode this is additive over the top matched facet-pairs (two moderate overlaps can outrank one very strong overlap); in `directed` mode it is the single best facet's `similarity · weight(hotness)`.
- `matchedFacets[].similarity` — cosine similarity of the facet pair.
- `matchedFacets[].askerFacet` — the asker's side of the pair. Present in `passive` mode; **omitted in `directed` mode** (there is no asker facet — the query is the anchor) and for the cold-start bio fallback.
- `matchedFacets[].candidateFacet` — the candidate's facet: its `id` and lazily-decayed `hotness`.
- `matchedFacets[].sampleContent` — present **only** when both sample gates are satisfied. Never contains moderation-removed, soft-deleted, or private-DM content, or entities and comments from a space the asker can't read. A chat message is included only from a group or space chat the asker can read: one they're an active member of, or one they left after the message was sent. A space chat counts only while the asker is an active member of its space and can see it.

The always-returned breakdown (users, scores, facet ids, similarities, hotness) carries **no readable content** — raw content appears only behind the two gates.

## Spaces the asker can't read

Match shows nothing from spaces the asker can't read. The asker can read a space when they can see it and either are an active member of it, or its `readingPermission` is `"anyone"` and they can read the space above it (see [Who can read content](/v8/data-models/space#who-can-read-content)). A comment counts as being in its entity's space; content in no space is always readable.

- Without `includeChildSpaces`, a `spaceId` the asker can't read matches nobody.
- With `includeChildSpaces`, only the spaces in the subtree the asker can read count. A readable sub-space still counts when the named space can't be read; the named space's own activity then doesn't.
- Sample content leaves out entities and comments from spaces the asker can't read.

Interest facets are learned from all of a user's content, including content in private and members-only spaces. So a candidate can be ranked on interests that come from activity in spaces the asker can't see. Match never shows that content: the breakdown carries no content, and samples follow the rules above.

## Cold-start fallback

In `passive` mode, if the asker has no facet above the significance threshold, the endpoint falls back to the asker's **bio embedding** (from `UserEmbeddings`) as a single pseudo-facet, so a brand-new user can still get matches. Cold-start matches omit `askerFacet` on the breakdown.

## Candidate exclusions

Candidates are excluded when they are: the asker (unless `excludeSelf: false`), users with a block between them and the asker in either direction (with the `moderation` bundle), users with an **active** suspension (a future-dated suspension does *not* count as active), and — for a space-scoped match — users **banned** in that space.

## Error Responses

<AccordionGroup>
  <Accordion title="Missing User ID — 400">
    A service key called this endpoint without `actingUserId`.

    ```json
    { "error": "A service key must send actingUserId: the user this request acts as.", "code": "match/missing-user-id" }
    ```
  </Accordion>
  <Accordion title="Acting User Not Allowed — 400">
    A user token, or a request with no credentials, sent `actingUserId`, even naming its own user. Only a service key names the user it acts as; a user token always acts as its own user.

    ```json
    { "error": "actingUserId is only accepted with a service key. A user's own token always acts as that user.", "code": "match/acting-user-not-allowed" }
    ```
  </Accordion>
  <Accordion title="User Not Found — 404">
    Returned when a service key names an `actingUserId` that isn't a user in this project.

    ```json
    { "error": "No user with this actingUserId exists in this project.", "code": "match/user-not-found" }
    ```
  </Accordion>
  <Accordion title="Plan Required — 403">
    ```json
    { "error": "Interest matching requires a paid plan", "code": "project/plan-required" }
    ```
  </Accordion>
  <Accordion title="Interest Matching Disabled — 403">
    ```json
    { "error": "Interest matching is not enabled for this project", "code": "project/interest-matching-disabled" }
    ```
  </Accordion>
  <Accordion title="Sample Content Disabled — 403">
    ```json
    { "error": "Sample content is not enabled for this project", "code": "match/sample-content-disabled" }
    ```
  </Accordion>
  <Accordion title="Tables Not Available — 403">
    The `interest-matching` bundle is not installed.
    ```json
    { "code": "database/tables-not-available", "missingTables": ["UserInterestFacets"] }
    ```
  </Accordion>
</AccordionGroup>
