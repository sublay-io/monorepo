---
title: "Read Authority"
api: "GET /v8/:projectId/workspaces/:id/authority/me"
description: "The resolved standing of a user on a workspace — permissions as a service"
---

Returns the caller's **resolved standing** on a workspace: `{ reasons, capabilities, permissions, rank }`, computed via the [authority resolver](/v8/data-models/workspace#reach-and-the-wall-door-rule) (fast-path + bounded ancestor climb). This is the endpoint your authorization server reads (via the [node SDK](/v8/node-sdk/workspaces)) to make its own app-level decisions.

`reasons` is an array of **structured entries** — `{ type, viaWorkspaceId? }` — distinguishing **`owner` / `ancestor-owner` / `member` / `reach-holder`**, so you always know *why* a user has what they have **and which workspace grants it**. It is the same object shape a [roster](/v8/api-reference/workspaces/members/list-members) entry's `reasons` carries. `viaWorkspaceId` names the granting ancestor and is present on `ancestor-owner` / `reach-holder` only (`owner` / `member` are grants on the workspace itself). A user reaching in from several ancestors carries **one entry per granting ancestor**.

This read is inherently a **self** read (or a privileged-key read of a named user), so `capabilities` / `permissions` / `rank` are always returned in full here — unlike the [member-standing read](/v8/api-reference/workspaces/members/fetch-member-standing), which fences them. (The fence exists to stop a caller reconstructing *someone else's* rank; there is nobody else in this payload.)

<Note>
  There is **no** convenience `?permission=` check and **no** `can()` middleware. Sublay never consumes your opaque `permissions`, so a permission check is a one-line `.includes()` on the returned record:

  ```ts
  const authority = await sublay.workspaces.fetchWorkspaceAuthority({ workspaceId, actingUserId });
  if (authority.permissions.includes("deploy")) { /* allow */ }
  ```
</Note>

## Path Parameters

<ParamField path="id" type="string" required>
  The workspace UUID.
</ParamField>

## Query Parameters

<ParamField query="actingUserId" type="string" required>
  Service keys only — the user to act as, whose standing is resolved. **Required for a key:** there is no such thing as "the app's standing", so a key that names nobody is refused with `400 workspace/missing-user-id`.

  A user token always acts as its own user and must not send it (`400 workspace/acting-user-not-allowed`). See [Acting on behalf of a user](/v8/sdk/workspaces/overview#acting-on-behalf-of-a-user).
</ParamField>

## Response

```json
{
  "reasons": [
    { "type": "member" },
    { "type": "ancestor-owner", "viaWorkspaceId": "ws_root" }
  ],
  "capabilities": ["view", "invite", "remove-member"],
  "permissions": ["deploy"],
  "rank": 5
}
```

- `reasons` — structured standings; `viaWorkspaceId` is present on `ancestor-owner` / `reach-holder` only.
- `capabilities` — the fully-resolved set (direct + reach + ownership). **`view` is implied by every other capability** — any user with standing on the workspace resolves with `view`, including a member whose stored `capabilities` array is empty. A user with no relation at all resolves to an empty set.
- `permissions` — **per-node** (the direct membership on this workspace only; may be empty). Does not cascade.
- `rank` — the direct-membership rank, or `null` for owners / ancestor-owners / reach-only holders.
- There is **no `relativeRank`** on this read. It is an offset from the caller, and here the caller *is* the subject — so it could only ever be `0`, a constant dressed as a coordinate. `rank` is the position this endpoint reports. `relativeRank` is meaningful on the [roster](/v8/api-reference/workspaces/members/list-members) and [member-standing](/v8/api-reference/workspaces/members/fetch-member-standing) reads, where the subject is somebody else.

## Error Responses

<AccordionGroup>
  <Accordion title="Missing Acting User — 400">
    ```json
    { "error": "A service key must send actingUserId: the user this request acts as.", "code": "workspace/missing-user-id" }
    ```
    A service key called this route without naming an `actingUserId`. The read resolves *a user's* standing, so there is nobody to resolve it for.
  </Accordion>
  <Accordion title="Acting User Not Allowed — 400">
    ```json
    { "error": "actingUserId is only accepted with a service key. A user's own token always acts as that user.", "code": "workspace/acting-user-not-allowed" }
    ```
    A user token sent `actingUserId`, even naming its own user. Only a service key names the user it acts as; a user token always acts as its own user.
  </Accordion>
  <Accordion title="User Not Found — 404">
    ```json
    { "error": "No user with this actingUserId exists in this project.", "code": "workspace/user-not-found" }
    ```
    Returned when a service key names an `actingUserId` that isn't a user in this project.
  </Accordion>
  <Accordion title="Invalid Path Parameter — 400">
    ```json
    { "error": "Invalid workspace id: expected a UUID.", "code": "workspace/invalid-params" }
    ```
    Every path id on the workspaces bundle is checked for UUID shape before the route runs, so a malformed one is a plain `400` rather than a `500` from the database.
  </Accordion>
</AccordionGroup>
