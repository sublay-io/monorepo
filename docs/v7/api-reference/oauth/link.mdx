---
title: "Link OAuth Provider"
api: "POST /v7/:projectId/oauth/link"
description: "Link a new OAuth provider to the current authenticated user"
---

Initiates an OAuth 2.0 flow to link an additional provider to the currently authenticated user's account. Requires a valid access token. The flow and callback behavior are identical to the [Authorize OAuth](/v7/api-reference/oauth/authorize) endpoint.

The authenticated user's ID is taken from the access token — it cannot be specified in the request body.

## Headers

<ParamField header="Authorization" type="string" required>
  `Bearer {accessToken}` — a valid access token for the user linking the provider.
</ParamField>

## Body Parameters

<ParamField body="provider" type="string" required>
  The OAuth provider to link. Must be one of: `"google"`, `"github"`, `"apple"`,
  `"facebook"`.
</ParamField>

<ParamField body="redirectAfterAuth" type="string" required>
  The URL to redirect the user to after authorization. Must be a valid URL and
  must be in the provider's configured allowed redirect URIs.
</ParamField>

## Response

<ResponseField name="authorizationUrl" type="string">
  The URL to send the user's browser to. It is a one-time Sublay URL; it
  expires after 10 minutes if it isn't opened. Once opened, the user has 10
  minutes for each step, and at most 30 minutes from this call.
</ResponseField>

Before going to the provider, Sublay shows the user a page naming the account the provider will be connected to (its verified email, or else its username), with **Continue** and **Cancel**. Continue goes on to the provider; Cancel returns to `redirectAfterAuth` with `error=access_denied`. The page only works in the browser that opened `authorizationUrl`, where it can be reloaded; anywhere else it shows that the link has expired, and so does an older link page once a newer one was opened in the same browser. The page is in English.

<Note>
  Open `authorizationUrl` as-is, in the browser (or auth session) that should
  end up signed in. It points to Sublay first, which ties the sign-in to that
  browser and then sends it on to the provider. A sign-in that returns to a
  different browser is refused with `error=state_mismatch`, and so is the
  older of two sign-ins started at the same time in one browser (in any app
  that uses Sublay).
</Note>

## Callback

After the user authorizes with the provider, they are redirected to `redirectAfterAuth` with one of:

**On success** — Tokens in the URL fragment (new tokens are issued for the linked account):
```
https://yourapp.com/callback#accessToken=...&refreshToken=...
```

**On error** — Error details in query parameters:
```
https://yourapp.com/callback?error=...&error_description=...
```

## Error Responses

<AccordionGroup>
  <Accordion title="Provider Not Configured — 400">
    ```json
    {
      "error": "OAuth provider 'github' is not configured or not enabled for this project",
      "code": "oauth/provider-not-configured"
    }
    ```
  </Accordion>
  <Accordion title="Invalid Redirect URI — 400">
    ```json
    {
      "error": "redirectAfterAuth is not in the allowed redirect URIs for this project",
      "code": "oauth/invalid-redirect-uri"
    }
    ```
  </Accordion>
  <Accordion title="Session Ended — 401">
    ```json
    { "error": "This session has ended. Sign in again.", "code": "auth/session-ended" }
    ```
    The access token is still valid, but its session no longer exists (signed out, password reset, or the account was claimed by a provider sign-in after its email went unverified). Adding a provider needs a live session, so sign in again.
  </Accordion>
</AccordionGroup>
