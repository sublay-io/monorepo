---
title: "Update Event"
api: "PATCH /v8/:projectId/events/:eventId"
description: "Edit an event's mutable fields and curate its files (host-only)"
---

Updates an event. **Host-only**: the caller must be the owner or in `hostIds`, and, for an event in a space, an active member of that space who isn't banned in it or a space above it. The space's admins and moderators can't edit events they don't host. A service key acts as the host it names in `actingUserId`. Every provided field is updated; omitted fields are left untouched. Type-conditional location validation is re-applied when `type` is present.

`hostIds`, `status`, and `spaceId` are **not** editable here — manage hosts via the [host endpoints](/v8/api-reference/events/add-host), cancel via [Cancel Event](/v8/api-reference/events/cancel-event); the space is immutable.

Files can be curated in one request: a new `coverFile` **replaces** the existing cover, `images` and `files` are **appended** after the event's existing files, and `removeFileIds` deletes existing event files by File ID. Any file operation requires the `files-images` bundle.

When a time field (`startTime`/`endTime`/`timezone`) or a location field (`location`/`url`/`venueName`/`address`) actually changes, an `event-updated` notification is fanned out to the `going`/`maybe` RSVP holders who can still see the event (best-effort, requires the `notifications` bundle).

## Path Parameters

<ParamField path="eventId" type="string" required>
  UUID of the event to update.
</ParamField>

## Body Parameters

<ParamField body="title" type="string">Event title. 1–300 characters.</ParamField>
<ParamField body="description" type="string">New description.</ParamField>
<ParamField body="startTime" type="string">New ISO start datetime.</ParamField>
<ParamField body="endTime" type="string">New ISO end datetime.</ParamField>
<ParamField body="timezone" type="string">New IANA timezone.</ParamField>
<ParamField body="type" type="string">`"online"`, `"physical"`, or `"hybrid"`. Re-triggers location validation.</ParamField>
<ParamField body="url" type="string">Join/stream URL.</ParamField>
<ParamField body="venueName" type="string">Venue name.</ParamField>
<ParamField body="address" type="string">Street address.</ParamField>
<ParamField body="location" type="{ latitude: number; longitude: number }">New coordinates. On multipart requests, send as a JSON string.</ParamField>
<ParamField body="visibility" type="string">`"public"`, `"members"`, or `"invite"`.</ParamField>
<ParamField body="capacity" type="number">New capacity (positive integer).</ParamField>
<ParamField body="allowMaybe" type="boolean">Whether `"maybe"` RSVPs are allowed.</ParamField>
<ParamField body="guestListVisible" type="boolean">Whether everyone who can see the event can view the guest list. When `false`, only hosts who are active members of the event's space and not banned in it or a space above it and the space's admins and moderators can.</ParamField>
<ParamField body="metadata" type="object">Arbitrary key-value data. Up to 1 MB.</ParamField>

<ParamField body="removeFileIds" type="string[]">
  Files to remove from the event: files in its `files` and/or the current cover (`coverImageId`). Removing the cover clears it (`coverImageId` becomes `null`). Each file and its blobs are deleted. Works alone or with uploads in the same request; uploading a new cover while listing the old one is a plain replace. On a multipart request, send it as a JSON string (`'["<fileId>"]'`). Any id that isn't one of this event's files refuses the whole request with `400 event/invalid-remove-file-ids`.
</ParamField>

<ParamField body="coverFile" type="file">
  New cover image (replaces the current cover; the old cover file is deleted). Multipart file field. Requires `coverFile.options`. Adding a cover doesn't move the event's other files.
</ParamField>

<ParamField body="coverFile.options" type="string">
  JSON-stringified image-processing options for the new cover (`mode` is required). The same options as [Upload Image](/v8/api-reference/storage/upload-image)'s `file.options`.
</ParamField>

<ParamField body="images" type="file[]">
  Images to append to the event's files, processed into sizes per `images.options`. Multipart file field. Requires `images.options`. A request takes at most 20 files over all its file fields together.
</ParamField>

<ParamField body="images.options" type="string">
  JSON-stringified image-processing options for the appended images (`mode` is required). The same options as [Upload Image](/v8/api-reference/storage/upload-image)'s `file.options`.
</ParamField>

<ParamField body="files" type="file[]">
  Files to append to the event's files, stored as uploaded. Multipart file field. Each file's `type` comes from its MIME type; an image sent here isn't processed, so it has no `image` data.
</ParamField>

<ParamField body="files.options" type="string">
  Optional JSON-stringified file options: `pathParts` (string[]) customizes the storage path.
</ParamField>

New files come after the event's existing ones, images first and then files, each in upload order. An `images.options` or `files.options` sent without its files is ignored.

<ParamField body="include" type="string | string[]">
  What the response adds: `files`, the event's files as they now are (the cover first, then its images and files), images with their variants, along with the host's `user.avatarFile` and `user.bannerFile`, as [Fetch Event](/v8/api-reference/events/fetch-event) returns them. A comma-separated value or an array; in a multipart body also a JSON-string array such as `'["files"]'`. Matching ignores case. In the body like every other field (JSON, or a multipart field), never the query. Without it the response has no `files`, even when the update uploaded or removed files. Without the files-images bundle it adds nothing.
</ParamField>

<ParamField body="actingUserId" type="string">
  Required with a service key: the user this request acts as. It has exactly that user's powers, so it is refused unless they are a host of the event with active membership of its space, and it is recorded as theirs. A user token always acts as its own user and must not send it (`400 event/acting-user-not-allowed`).
</ParamField>

## Response

Returns the updated [Event](/v8/data-models/event) object. With `include: "files"` it also carries `files` (the cover first, then its images and files, images with their variants) and the host's avatar and banner files. To show a file change without fetching the event again, send `include: "files"` with it.

## Error Responses

<AccordionGroup>
  <Accordion title="Not signed in — 401 / 403">
    Returned with no JSON body: `401` when no `Authorization` header is sent, `403` when the access token is invalid or expired. Checked before any uploaded file is read, so a request with no credentials gets `401` rather than a body or acting-user error.
  </Accordion>
  <Accordion title="Missing Acting User — 400">
    A service key sent no `actingUserId`.
    ```json
    { "error": "A service key must send actingUserId: the user this request acts as.", "code": "event/missing-user-id" }
    ```
  </Accordion>
  <Accordion title="Invalid Acting User — 400">
    `actingUserId` is not a user id.
    ```json
    { "error": "actingUserId must be a user id.", "code": "event/invalid-body", "param": "actingUserId" }
    ```
  </Accordion>
  <Accordion title="Acting User Not Allowed — 400">
    A user token sent `actingUserId`, even naming its own user. Only a service key names the user it acts as; a user token always acts as its own user.
    ```json
    { "error": "actingUserId is only accepted with a service key. A user's own token always acts as that user.", "code": "event/acting-user-not-allowed" }
    ```
  </Accordion>
  <Accordion title="Wrong Location — 400">
    `actingUserId` was sent in the query string. On this endpoint every field goes in the request body.
    ```json
    {
      "error": "`actingUserId` goes in the request body on this endpoint.",
      "code": "event/wrong-location",
      "param": "actingUserId"
    }
    ```
  </Accordion>
  <Accordion title="Invalid Include — 400">
    `include` names a value this endpoint doesn't add. The only value is `files`.
    ```json
    { "error": "include: Unknown include `user`. Allowed: files.", "code": "event/invalid-body", "param": "include" }
    ```
  </Accordion>
  <Accordion title="Include in the Query — 400">
    `include` was sent in the query string. On this endpoint it goes in the request body, with the other fields.
    ```json
    { "error": "`include` goes in the request body on this endpoint.", "code": "event/wrong-location", "param": "include" }
    ```
  </Accordion>
  <Accordion title="Unsupported Parameter — 400">
    The request sent `removeImageIds`, `cover.options` or `gallery.options`. Files are removed with `removeFileIds`, the cover is uploaded as `coverFile` with its options in `coverFile.options`, and the event's images as `images` with their options in `images.options`.

    ```json
    {
      "error": "`removeImageIds` isn't supported in v8. Send the ids of the files to remove as `removeFileIds`.",
      "code": "event/unsupported-param",
      "param": "removeImageIds"
    }
    ```

    ```json
    {
      "error": "`cover.options` isn't supported in v8. Send the cover image as the `coverFile` file, with its options as `coverFile.options`.",
      "code": "event/unsupported-param",
      "param": "cover.options"
    }
    ```

    ```json
    {
      "error": "`gallery.options` isn't supported in v8. Send gallery images as the `images` files, with their options as `images.options`.",
      "code": "event/unsupported-param",
      "param": "gallery.options"
    }
    ```
  </Accordion>
  <Accordion title="User Not Found — 404">
    Returned when a service key names an `actingUserId` that isn't a user in this project.
    ```json
    { "error": "No user with this actingUserId exists in this project.", "code": "event/user-not-found" }
    ```
  </Accordion>
  <Accordion title="Not Found — 404">
    The event doesn't exist, or the caller can't [see it](/v8/data-models/event#visibility) and isn't one of its hosts.
    ```json
    { "error": "Event not found", "code": "event/not-found" }
    ```
  </Accordion>
  <Accordion title="Forbidden (not a host) — 403">
    ```json
    { "error": "Only a host of this event may update it.", "code": "event/forbidden" }
    ```
  </Accordion>
  <Accordion title="Host Not an Active Member — 403">
    The caller is a host, but the event is in a space they aren't an active member of, or they are banned in it or a space above it. One body for every case.
    ```json
    { "error": "Hosts must be active members of this event's space, and not banned from it or a space above it, to do this.", "code": "event/not-space-member" }
    ```
  </Accordion>
  <Accordion title="Bundle Not Installed — 403">
    Returned when a cover, images or files are uploaded or `removeFileIds` is sent on a project without the files-images bundle. `missingTables` lists the tables that aren't installed and `bundleId` the bundle to install. While the bundle is still being installed, the response is `503 database/tables-provisioning` instead. See [Bundles](/v8/bundles).
    ```json
    { "error": "Event cover images and files require the files-images bundle. Enable it for this project.", "code": "database/tables-not-available", "missingTables": ["Files", "Images"], "bundleId": "files-images", "dashboardUrl": "https://…/<projectId>/database" }
    ```
  </Accordion>
  <Accordion title="Invalid File Ids — 400">
    `removeFileIds` names a file that isn't one of this event's files. `invalidIds` lists those ids. Checked before anything is uploaded, so nothing is stored or removed.
    ```json
    { "error": "`removeFileIds` may name only this event's own files: its cover (`coverImageId`) and the files in its `files`.", "code": "event/invalid-remove-file-ids", "param": "removeFileIds", "invalidIds": ["9b2f…"] }
    ```
    A `removeFileIds` that isn't an array of file ids gets `400 event/invalid-body` instead.
  </Accordion>
  <Accordion title="Image Too Large — 413">
    ```json
    { "error": "`coverFile` is over the 50 MB per-file limit.", "code": "event/file-too-large", "param": "coverFile" }
    ```
    A file is over 50 MB. `param` names its field.
  </Accordion>
  <Accordion title="Invalid Image — 422">
    ```json
    { "error": "Cover file is not a valid image.", "code": "event/invalid-image", "param": "coverFile" }
    ```
    The cover can't be read as an image. A file in `images` that can't be read gets the same code with `param: "images"`:
    ```json
    { "error": "File \"photo.jpg\" is not a valid image.", "code": "event/invalid-image", "param": "images" }
    ```
    An image over 10000 px on a side gets the same code. `error` gives its size:
    ```json
    { "error": "Cover file is 12000 x 800 px; an image can be at most 10000 px on each side.", "code": "event/invalid-image", "param": "coverFile" }
    ```
    A file in `images`:
    ```json
    { "error": "File \"photo.jpg\" is 12000 x 800 px; an image can be at most 10000 px on each side.", "code": "event/invalid-image", "param": "images" }
    ```
  </Accordion>
  <Accordion title="Missing Image Options — 400">
    A cover or `images` were uploaded without their options. `param` is `coverFile.options` or `images.options`.
    ```json
    { "error": "Image options are required when uploading a cover image. Must include mode property.", "code": "event/missing-image-options", "param": "coverFile.options" }
    ```
    For `images`:
    ```json
    { "error": "`images.options` is required when `images` are uploaded. Must include mode property.", "code": "event/missing-image-options", "param": "images.options" }
    ```
  </Accordion>
  <Accordion title="Invalid Image Options — 400">
    `coverFile.options` without `mode`, or with a `mode` that isn't one of the five (other options fields the same way, named in `error` and `param`):
    ```json
    { "error": "coverFile.options.mode: Invalid input", "code": "event/invalid-body", "param": "coverFile.options.mode" }
    ```
    In an aspect-ratio mode, a variant's computed side would be outside 1–10000 px. Checked once the image is read, before anything is stored. `param` names the option:
    ```json
    { "error": "`coverFile.options.widths.s` gives a height of 0 px at the 3:1 aspect ratio. Each side of a variant must be 1–10000 px.", "code": "event/invalid-body", "param": "coverFile.options.widths.s" }
    ```
    In `aspect-ratio-height-based` it names a `heights` option and gives a width. In `multi-aspect-ratio` it names a `sizes` option, and the ratio is the one in `aspectRatios` closest to the image, so the text reads "… at the 3:1 aspect ratio, the one in `aspectRatios` closest to this image. Each side of a variant must be 1–10000 px."
    More than 30 entries in `dimensions`, `widths`, `heights` or `sizes` (one variant each). `param` names the option:
    ```json
    { "error": "coverFile.options.sizes: An image can have at most 30 variants.", "code": "event/invalid-body", "param": "coverFile.options.sizes" }
    ```
    A variant name that is empty or `original`, or that contains `/`, `\` or `..`. `param` names the option:
    ```json
    { "error": "coverFile.options.sizes: Variant names can't be empty, `original`, or contain `/`, `\\` or `..`.", "code": "event/invalid-body", "param": "coverFile.options.sizes" }
    ```
  </Accordion>
  <Accordion title="Storage Quota Reached — 429">
    ```json
    {
      "error": "Quota reached for storageFileBytes. Current: …, Action size: …, Limit: …",
      "code": "project/quota-reached",
      "details": { "current": 0, "actionSize": 0, "limit": 0, "metric": "storageFileBytes" }
    }
    ```
    The uploaded files would take the project past its plan's file-storage limit. The event is unchanged and nothing is stored.
  </Accordion>
  <Accordion title="Upload Refused — 400 / 413">
    A file was refused as the body was read: `event/unsupported-file-type` or `event/unexpected-file-field` (a file in another field, the old `cover` and `gallery` included, or a second file in `coverFile`), with `param` naming the field when there is one, or `413 event/too-many-files` for more than 20 files in the request. A body over 250 MB gets `413 request/body-too-large`; one that can't be read at all gets `request/invalid-multipart` or `request/field-too-large`. See [Upload errors](/v8/api-reference/getting-started#upload-errors).
  </Accordion>
</AccordionGroup>
