---
title: "Sign Up"
api: "POST /v8/:projectId/auth/sign-up"
description: "Create a new user account with email and password"
---

Registers a new user within the specified project. On success, returns an access token, refresh token, and the created user object. The endpoint also accepts optional profile data and image file uploads for the avatar and banner.

When the project requires email verification before sign-in (Dashboard → Settings → SDK → **Require email verification before sign-in**), sign-up works differently: it returns `202` with no session, emails a confirmation link or code, and answers the same way whether or not the email already has an account. See [With email verification required](#with-email-verification-required).

<Note>
  This endpoint accepts `multipart/form-data` when uploading avatar or banner
  images. Send `application/json` for text-only registration.
</Note>

## Body Parameters

<ParamField body="email" type="string" required>
  User's email address. Must be a valid email format. Automatically lowercased.
</ParamField>

<ParamField body="password" type="string" required>
  User's password.
</ParamField>

<ParamField body="name" type="string">
  Display name.
</ParamField>

<ParamField body="username" type="string">
  Unique username within the project. Automatically lowercased. Fails with 409
  if already taken.
</ParamField>

<ParamField body="avatar" type="string">
  URL of the user's avatar image. Ignored if `avatarFile` is also provided.
</ParamField>

<ParamField body="bio" type="string">
  Short bio text.
</ParamField>

<ParamField body="location" type="object">
  Geographic location.
  <Expandable title="properties">
    <ParamField body="latitude" type="number" required>
      Latitude between -90 and 90.
    </ParamField>
    <ParamField body="longitude" type="number" required>
      Longitude between -180 and 180.
    </ParamField>
  </Expandable>
</ParamField>

<ParamField body="birthdate" type="string">
  ISO 8601 datetime string representing the user's date of birth.
</ParamField>

<ParamField body="metadata" type="object">
  Public custom key-value data attached to the user.
</ParamField>

<ParamField body="secureMetadata" type="object">
  Custom key-value data. No API response returns it, to this user or anyone else; your backend receives it in webhooks. The user can write it themselves, so don't store anything your app needs to trust here.
</ParamField>

<ParamField body="avatarFile" type="file">
  Avatar image file (multipart). Maximum 50 MB. Must be a valid image format.
  Requires `avatarFile.options` to also be present.
</ParamField>

<ParamField body="avatarFile.options" type="string">
  Stringified JSON describing how to process the avatar. Must include a `mode` field; see [Upload Image](/v8/api-reference/storage/upload-image) for the modes and optional fields. Not used when no `avatarFile` is sent, but still validated: invalid JSON or options get a `400`.
</ParamField>

<ParamField body="bannerFile" type="file">
  Banner image file (multipart). Maximum 50 MB. Must be a valid image format.
  Requires `bannerFile.options` to also be present.
</ParamField>

<ParamField body="bannerFile.options" type="string">
  Stringified JSON describing how to process the banner, as `avatarFile.options`. Not used when no `bannerFile` is sent, but still validated: invalid JSON or options get a `400`.
</ParamField>

<ParamField body="emailVerification" type="object">
  How the confirmation email is sent when the project requires email verification before sign-in. Ignored when the setting is off. In a `multipart/form-data` request, send it as a JSON string.
  <Expandable title="properties">
    <ParamField body="mode" type='"link" | "code"' default='"link"'>
      `"link"` emails a **Confirm my email** button (see [Verify Email Link](/v8/api-reference/auth/verify-email-link)). `"code"` emails a 6-digit code the user types into your app; confirm it with [Verify Email](/v8/api-reference/auth/verify-email) and the `verificationId` from the response.
    </ParamField>
    <ParamField body="redirectUrl" type="string">
      Where the confirmation link sends the user after they confirm, with `verified=true` added to its query. Link mode only. Must be an `https` address on one of your project's Verified Domains (or `localhost`), the same rule as [Send Verification Email](/v8/api-reference/auth/send-verification-email); anything else is refused with `400 auth/redirect-url-not-allowed` before anything is created.
    </ParamField>
  </Expandable>
</ParamField>

## Response

On success, returns HTTP `201` with:

<ResponseField name="success" type="boolean">
  `true` on successful registration.
</ResponseField>

<ResponseField name="accessToken" type="string">
  Short-lived JWT access token. Expires in 30 minutes.
</ResponseField>

<ResponseField name="refreshToken" type="string">
  Long-lived JWT refresh token. Expires in 30 days.
</ResponseField>

<ResponseField name="user" type="object">
  The created user's profile.
  <Expandable title="properties">
    <ResponseField name="id" type="string">Unique user ID (UUID).</ResponseField>
    <ResponseField name="foreignId" type="string | null">External user ID, if set.</ResponseField>
    <ResponseField name="role" type="string">User role (e.g., `"visitor"`).</ResponseField>
    <ResponseField name="email" type="string | null">User's email address.</ResponseField>
    <ResponseField name="name" type="string | null">Display name.</ResponseField>
    <ResponseField name="username" type="string | null">Username.</ResponseField>
    <ResponseField name="avatar" type="string | null">Avatar URL.</ResponseField>
    <ResponseField name="bio" type="string | null">Bio text.</ResponseField>
    <ResponseField name="metadata" type="object | null">Public custom data.</ResponseField>
    <ResponseField name="reputation" type="number | null">Reputation score.</ResponseField>
    <ResponseField name="isVerified" type="boolean | null">Whether the user is verified.</ResponseField>
    <ResponseField name="isActive" type="boolean | null">Whether the account is active.</ResponseField>
    <ResponseField name="lastActive" type="string | null">ISO timestamp of last activity.</ResponseField>
    <ResponseField name="suspensions" type="array">Active suspensions on the account.</ResponseField>
    <ResponseField name="avatarFile" type="object | null">Processed avatar file with variants.</ResponseField>
    <ResponseField name="bannerFile" type="object | null">Processed banner file with variants.</ResponseField>
    <ResponseField name="authMethods" type="string[]">List of auth methods (e.g., `["password"]`).</ResponseField>
    <ResponseField name="createdAt" type="string">ISO timestamp of account creation.</ResponseField>
  </Expandable>
</ResponseField>

## With email verification required

When the project requires email verification before sign-in, every sign-up that passes validation returns HTTP `202` with:

```json
{
  "success": true,
  "emailVerificationRequired": true,
  "verificationId": "9f2c…"
}
```

<ResponseField name="success" type="boolean">
  Always `true`.
</ResponseField>

<ResponseField name="emailVerificationRequired" type="boolean">
  Always `true`. No `user`, `accessToken` or `refreshToken` is returned: the user signs in after confirming their email.
</ResponseField>

<ResponseField name="verificationId" type="string">
  Present when `emailVerification.mode` is `"code"`. Keep it with the sign-up screen (in memory is enough) and send it with the code to [Verify Email](/v8/api-reference/auth/verify-email). If it's lost, sign in again with the same email and password: the refused sign-in returns the `verificationId` of the code already sent (or of a new one, if the last email is more than 10 minutes old).
</ResponseField>

What happens behind the same answer:

- **New email** — the account is created (unconfirmed) and a confirmation email is sent. The link or code lasts 24 hours.
- **Email that already has an account** — nothing is created and nothing changes. Any uploaded avatar or banner is discarded. The address is sent an email saying someone tried to sign up with it, pointing to sign-in or password reset. In code mode the response still carries a `verificationId`, which confirms nothing.

The confirmation emails sent to one address are limited to one every 10 minutes and five a day; past that, the response is the same but no email is sent.

Validation still runs first, in the same order: an invalid body, an image error, a `user.created` validation webhook that refuses, or a taken username still returns its error. Usernames are public through the username check, so a taken username is still reported.

<Note>
  The setting stops sign-up from telling a new email from a registered one, but not every way of finding out. A sign-in with the password just used at sign-up answers "confirm your email first" (`403 auth/email-not-verified`) for an account that sign-up created and "incorrect password" (`401 auth/invalid-credentials`) for one that already existed. A sign-up that sent a `username` shows it too: the username is taken afterwards only if sign-up created the account. With the setting off, sign-up's `409` tells anyone whether an email is registered.
</Note>

## Error Responses

<AccordionGroup>
  <Accordion title="Email Already In Use — 409">
    ```json
    {
      "error": "Email already in use",
      "code": "auth/email-taken",
      "param": "email"
    }
    ```
    Only when the project doesn't require email verification before sign-in. It tells the caller the email is registered.
  </Accordion>
  <Accordion title="Redirect URL Not Allowed — 400">
    ```json
    {
      "error": "...",
      "code": "auth/redirect-url-not-allowed",
      "param": "emailVerification.redirectUrl"
    }
    ```
    `emailVerification.redirectUrl` isn't an `https` address on one of the project's Verified Domains (or `localhost`). Only checked when the project requires email verification before sign-in. Nothing is created and no email is sent.
  </Accordion>
  <Accordion title="Username Already Taken — 409">
    ```json
    {
      "error": "Username already taken",
      "code": "auth/username-taken",
      "param": "username"
    }
    ```
  </Accordion>
  <Accordion title="Invalid Body — 400">
    ```json
    {
      "error": "...",
      "code": "auth/invalid-body"
    }
    ```
  </Accordion>
  <Accordion title="File Too Large — 413">
    The image is over 50 MB. `param` names its field: `avatarFile` or `bannerFile`.
    ```json
    { "error": "`avatarFile` is over the 50 MB per-file limit.", "code": "auth/file-too-large", "param": "avatarFile" }
    ```
  </Accordion>
  <Accordion title="Invalid Image — 422">
    ```json
    {
      "error": "Avatar file is not a valid image.",
      "code": "auth/invalid-image",
      "param": "avatarFile"
    }
    ```
    Returned when the uploaded file cannot be parsed as an image. Also returned for the banner file with `"Banner file is not a valid image."` and `param: "bannerFile"`.
  </Accordion>
  <Accordion title="Missing Image Options — 400">
    ```json
    {
      "error": "Image options are required when uploading an avatar. Must include mode property.",
      "code": "auth/missing-image-options",
      "param": "avatarFile.options"
    }
    ```
    Returned when `avatarFile` or `bannerFile` is uploaded without the corresponding `.options` field. `param` is `avatarFile.options` or `bannerFile.options`.
  </Accordion>
  <Accordion title="Invalid Image Options — 400">
    ```json
    {
      "error": "Invalid JSON in avatarFile.options field.",
      "code": "auth/invalid-body",
      "param": "avatarFile.options"
    }
    ```
    The `.options` field isn't valid JSON. `param` names the field: `avatarFile.options` or `bannerFile.options`.
  </Accordion>
  <Accordion title="Upload Refused — 400 / 413">
    A file was refused as the body was read: `auth/unsupported-file-type` or `auth/unexpected-file-field` (a file in another field, or a second file in `avatarFile` or `bannerFile`), with `param` naming the field when there is one. A body over 250 MB gets `413 request/body-too-large`; one that can't be read at all gets `request/invalid-multipart` or `request/field-too-large`. See [Upload errors](/v8/api-reference/getting-started#upload-errors).
  </Accordion>
  <Accordion title="Bundle Not Installed — 403">
    Returned when `avatarFile` or `bannerFile` is uploaded on a project without the files-images bundle. `missingTables` lists the tables that aren't installed and `bundleId` the bundle to install. While the bundle is still being installed, the response is `503 database/tables-provisioning` instead. See [Bundles](/v8/bundles).
    ```json
    { "error": "Avatar and banner uploads require the files-images bundle, which is not installed for this project.", "code": "database/tables-not-available", "missingTables": ["Files", "Images"], "bundleId": "files-images", "dashboardUrl": "https://…/<projectId>/database" }
    ```
  </Accordion>
  <Accordion title="Rejected by Validation Webhook — 400">
    ```json
    {
      "error": "User validation failed",
      "code": "auth/webhook-validation-failed"
    }
    ```
    Returned when your `user.created` [validation webhook](/v8/webhooks) rejects the new user. `error` carries the `message` your webhook returned (`User validation failed` when it returned none). No user is created.
  </Accordion>
  <Accordion title="Duplicate User Field — 409">
    ```json
    {
      "error": "A user with this <field> already exists in this project",
      "code": "auth/duplicate-field",
      "param": "<field>"
    }
    ```
    A uniqueness conflict the checks above didn't catch (for example, two
    sign-ups racing for the same value). `param` names the field. The code is
    `auth/username-taken`, `auth/email-taken` or `auth/foreign-id-taken` when
    the field is one of those, `auth/duplicate-field` for any other.
  </Accordion>
  <Accordion title="Storage Quota Reached — 429">
    ```json
    {
      "error": "Quota reached for storageFileBytes. Current: …, Action size: …, Limit: …",
      "code": "project/quota-reached",
      "details": { "current": 0, "actionSize": 0, "limit": 0, "metric": "storageFileBytes" }
    }
    ```
    Returned when an uploaded avatar or banner would take the project past its
    plan's file-storage limit. No user is created.
  </Accordion>
  <Accordion title="Server Error — 500">
    ```json
    {
      "error": "Internal server error",
      "code": "auth/server-error"
    }
    ```
  </Accordion>
</AccordionGroup>

**Rate limit:** 5 requests per 5 minutes per IP. Exceeding it returns `429` `request/rate-limited`, with `Too many sign up attempts, please wait 5 minutes` as `error` — distinct from the quota `429` above (`project/quota-reached`).
