## Overview

`useFetchManyChatMessages` returns a function that fetches a single page of conversation messages and resolves to the raw response. It stores nothing — no Redux, no socket subscription — so you own the resulting state.

This is the low-level fetcher shared by [`useLiveChatMessages`](/v8/hooks/chat/messages/use-live-chat-messages) (the live store-backed view) and [`useFetchManyChatMessagesWrapper`](/v8/hooks/chat/messages/use-fetch-many-chat-messages-wrapper) (a batteries-included paginated list). Use it directly when you need full control; most apps will prefer the wrapper.

<Note>Because results never enter the live store, this is the right tool for **filtered** or read-only queries (e.g. only messages that have replies) that should not be polluted by live socket traffic. It is a point-in-time query — call it again to refresh.</Note>

## Usage Example

```tsx
import { useFetchManyChatMessages } from "@sublay/react-js";
import { useState, useEffect } from "react";

function MessagesWithReplies({ conversationId }: { conversationId: string }) {
  const fetchMessages = useFetchManyChatMessages();
  const [messages, setMessages] = useState([]);

  useEffect(() => {
    fetchMessages({ conversationId, filters: { hasReplies: true } }).then((res) =>
      setMessages(res.data)
    );
  }, [conversationId]);

  return (
    <ul>
      {messages.map((m) => <li key={m.id}>{m.content}</li>)}
    </ul>
  );
}
```

## Parameters

<ParamField path="conversationId" type="string" required>
  The ID of the conversation to query.
</ParamField>

<ParamField path="parentMessageId" type="string | null">
  Restrict to thread replies of this message.
</ParamField>

<ParamField path="before" type="string | null">
  A message id: the `limit` messages just before it. Pass the oldest message you hold to load older ones. It must be a message of this conversation at the same thread level (`parentMessageId`), or the request fails with `400 chat/invalid-cursor`. Mutually exclusive with `after`. See [List Messages › Paging](/v8/api-reference/chat/messages/list-messages#paging).
</ParamField>

<ParamField path="after" type="string | null">
  A message id: the `limit` messages just after it. Pass the newest message you hold to load newer ones. Same rules as `before`. Mutually exclusive with `before`.
</ParamField>

<ParamField path="limit" type="number">
  Page size (1–100). Defaults to `50`.
</ParamField>

<ParamField path="sortDir" type='"asc" | "desc"'>
  The order of the page by creation time. Defaults to `"desc"` for the main stream and `"asc"` for a thread. With `before` or `after`, the anchor decides which messages are in the page; `sortDir` only orders them.
</ParamField>

<ParamField path="include" type="ChatMessageListIncludeParam">
  Fields to add to each message, as a single value or an array:
  - `"files"` — the `files` field.
  - `"grants"` — the [reputation-grant summary](/v8/data-models/reputation-grant#grantsummary) at `message.grants`: `{ total, count, viewerTotal }` over positive grants. Populated by the `reputation` bundle; on a project without it the summary comes back zero-filled rather than missing.
</ParamField>

<SpaceReputationParams variant="context" field="path" />

<ParamField path="filters" type="MessageFilters">
  Optional filters. `filters.hasReplies` (boolean): when `true`, returns only messages that have thread replies (`threadReplyCount > 0`); when `false`, only messages with none. Filters by thread replies, not quotings.

  <Note>Threads are one level deep, so `hasReplies: true` together with `parentMessageId` always returns an empty list — the response's `notice` field explains why.</Note>
</ParamField>

## Returns

A `Promise` resolving to:

<ResponseField name="data" type="ChatMessage[]">
  Messages for the requested page, in `sortDir` order. When `spaceReputation` is requested, each embedded sender carries an added `spaceReputation` number. See [ChatMessage](/v8/data-models/chat-message) and [Reputation](/v8/data-models/reputation).
</ResponseField>

<ResponseField name="pagination" type="{ hasMore: boolean }">
  `hasMore`: whether more messages exist past this page in the direction of travel — older with `before`, newer with `after`; with neither, older for `"desc"` and newer for `"asc"`. To continue, pass the id of the last message in `data` as `before` (for `"desc"`) or `after` (for `"asc"`).
</ResponseField>

<ResponseField name="notice" type="string">
  Present only when a filter combination can't return results — e.g. `hasReplies: true` together with `parentMessageId`. Explains why the list is empty.
</ResponseField>
