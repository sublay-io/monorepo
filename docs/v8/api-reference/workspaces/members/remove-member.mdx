---
title: "Remove Member"
api: "DELETE /v8/:projectId/workspaces/:id/members/:userId"
description: "Remove a member (rank-bounded; sole-owner protected)"
---

Removes a member from a workspace. Requires the `remove-member` capability and is **rank-bounded** (act only on strictly-lower ranks). Fires `workspace.member.removed`.

<Note>
  Owners have no member row, so removal targets member rows only. **Sole-owner protection:** the owner cannot be removed while sole owner — they must transfer ownership first.
</Note>

## Path Parameters

<ParamField path="id" type="string" required>
  The workspace UUID.
</ParamField>

<ParamField path="userId" type="string" required>
  The member to remove.
</ParamField>

## Body Parameters

<ParamField body="actingUserId" type="string" required>
  Service keys only — the **acting** user (sent in the body so the act-as-user path works on `DELETE`; the path `:userId` is the target). **Required for a key:** a key that names nobody is refused with `400 workspace/missing-user-id`. The `remove-member` capability and the rank bound are enforced against the named user — act as the **owner** for an unrestricted removal.

  A user token always acts as its own user and must not send it (`400 workspace/acting-user-not-allowed`). See [Acting on behalf of a user](/v8/sdk/workspaces/overview#acting-on-behalf-of-a-user).
</ParamField>

## Response

`204 No Content` on success.

## Error Responses

<AccordionGroup>
  <Accordion title="Insufficient Rank — 403">
    ```json
    { "error": "You may only remove members ranked strictly below you.", "code": "workspace/insufficient-rank" }
    ```
  </Accordion>
  <Accordion title="Sole Owner — 409">
    ```json
    { "error": "The workspace owner cannot be removed. Transfer ownership first.", "code": "workspace/sole-owner" }
    ```
  </Accordion>
  <Accordion title="Missing Acting User — 400">
    ```json
    { "error": "A service key must send actingUserId: the user this request acts as.", "code": "workspace/missing-user-id" }
    ```
    A service key called this route without naming an `actingUserId`. Removal is rank-bounded against the remover's own standing, so it must be performed *as* somebody — act as the owner for an unrestricted removal.
  </Accordion>
  <Accordion title="Acting User Not Allowed — 400">
    ```json
    { "error": "actingUserId is only accepted with a service key. A user's own token always acts as that user.", "code": "workspace/acting-user-not-allowed" }
    ```
    A user token sent `actingUserId`, even naming its own user. Only a service key names the user it acts as; a user token always acts as its own user.
  </Accordion>
  <Accordion title="Invalid Path Parameter — 400">
    ```json
    { "error": "Invalid workspace id: expected a UUID.", "code": "workspace/invalid-params" }
    ```
    Every path id on the workspaces bundle is checked for UUID shape before the route runs, so a malformed one is a plain `400` rather than a `500` from the database.
  </Accordion>
</AccordionGroup>
