The Sublay REST API is a project-scoped HTTP API. All endpoints follow the same base structure and share common conventions for authentication, pagination, and error reporting.

## Base URL

All API requests are made to:

```
https://api.sublay.io/v8/:projectId
```

Replace `:projectId` with the UUID of your Sublay project, which you can find in the [Sublay dashboard](https://dash.sublay.io).

So every endpoint takes the form:

```
https://api.sublay.io/v8/:projectId/<endpoint>
```

The project is read from the path only. Don't send `projectId` in the query string or the body, or an `x-sublay-project-id` header: each is refused with `400 project/wrong-location`. The exception is a custom-table column named `projectId`, which stays writable in the row bodies of [Insert Row](/v8/api-reference/custom-tables/insert-row), [Bulk Insert Rows](/v8/api-reference/custom-tables/bulk-insert-rows) (inside each entry of `rows`) and [Update Row](/v8/api-reference/custom-tables/update-row).

## Request Format

Most endpoints accept `application/json`. Endpoints that support file uploads accept `multipart/form-data`. The `Content-Type` header should be set accordingly.

Where each field goes is decided by the method: the path holds the resource, GET and DELETE take every other field in the query string and no body, and POST, PATCH and PUT take every other field in the body, `actingUserId` included. Each field is read from one place; sent elsewhere, it is refused with a `400` that names the right place:

| Code | When |
|---|---|
| `<area>/body-not-allowed` | A GET or DELETE has a body. |
| `<area>/wrong-location` | A POST, PATCH or PUT has a body field (or `actingUserId`) in its query string. |
| `project/wrong-location` | `projectId` anywhere but the path, or a project-id header. |
| `<area>/unsupported-route` | A route v8 moved; `error` names the one to call. |

See [Where each input goes](/v8/authentication#where-each-input-goes).

```http
POST /v8/:projectId/auth/sign-in
Content-Type: application/json

{
  "email": "user@example.com",
  "password": "secret"
}
```

## Ids

Every Sublay record id (`spaceId`, `entityId`, `userId`, …) is a UUID. Ids are accepted in either case and the server lowercases them; record ids in responses are lowercase.

An id that isn't a UUID is refused with `400`:

- **In the URL path:** checked before sign-in, permissions or any lookup (only a missing bundle, `403 database/tables-not-available`, is reported first). Code `<area>/invalid-params`, where `<area>` is the endpoint's area (`space`, `entity`, `chat`, …):

  ```json
  {
    "error": "Invalid space id: expected a UUID.",
    "code": "space/invalid-params", "param": "spaceId"
  }
  ```

- **In the query string or body:** code `<area>/invalid-query` or `<area>/invalid-body`, with `error` naming the field.

`foreignId` and `sourceId` are your own strings, not Sublay ids, so they accept any text, except that `sourceId` can't be `none`, `null` or `undefined`: list filters use `none` for "no source" (see [Saying "no value"](/v8/authentication#saying-no-value)).

## Authentication

Protected endpoints require a `Bearer` token in the `Authorization` header:

```http
GET /v8/:projectId/app-notifications
Authorization: Bearer <accessToken>
```

See [Authentication](/v8/api-reference/authentication) for full details on obtaining and refreshing tokens.

## Pagination

Endpoints that return lists use cursor-free offset pagination. Pass `page` and `limit` as query parameters:

| Parameter | Default | Max | Description |
|-----------|---------|-----|-------------|
| `page` | `1` | — | Page number (1-indexed) |
| `limit` | varies | varies | Results per page (endpoint-specific) |

Paginated responses always return the same envelope:

```json
{
  "data": [...],
  "pagination": {
    "page": 1,
    "pageSize": 20,
    "totalPages": 5,
    "totalItems": 97,
    "hasMore": true
  }
}
```

## Error Format

Every error is JSON with the same two keys:

```json
{
  "error": "Human-readable error message.",
  "code": "feature/error-slug"
}
```

- `error` is text for people. Show it or log it, but don't branch on it: it can change.
- `code` is stable, in the form `<area>/<kebab-case-slug>` (`entity/not-found`, `auth/email-taken`). Branch on this.

Some errors add keys:

- `param` names the failing input when the error is about one: a validation `400` (`<area>/invalid-body`, `<area>/invalid-query`, `<area>/invalid-params`), an id that isn't a UUID, a field another user already holds, a missing image-options field. It is the input's dot path, as you sent it (`email`, `metadata.title`, `images.options`). It is left out when the error is about the request as a whole.

  ```json
  {
    "error": "Username already taken",
    "code": "auth/username-taken",
    "param": "username"
  }
  ```

- A `500`'s code is `<area>/server-error`. The underlying failure is recorded in Sublay's server logs, not returned in the response.
- Some endpoints add keys of their own (`missingTables` on a missing bundle, `verificationId` on an unverified sign-in); each endpoint's page lists them.

The one exception: an access token that is missing, expired or invalid gets a bare `401 Unauthorized` / `403 Forbidden` with no JSON body. See [Authentication](/v8/api-reference/authentication).

### Request errors

These can come from any endpoint, because they are about the HTTP request itself rather than the resource:

| Status | Code | When |
|--------|------|------|
| `400` | `request/invalid-json` | The body is sent as JSON but doesn't parse. |
| `404` | `request/route-not-found` | No endpoint matches the method and path. |
| `413` | `request/body-too-large` | The JSON body is over the size limit. |
| `400` / `415` | `request/invalid-body` | The body can't be read for another reason: `415` for a charset or content encoding the server can't read, `400` otherwise (for example an aborted request). |
| `429` | `request/rate-limited` | The endpoint's rate limit for your IP is exceeded. See [Rate Limiting](#rate-limiting). |
| `500` | `request/server-error` | An unexpected failure outside any endpoint's own handling. |

### Upload errors

Endpoints that take a file in a `multipart/form-data` body answer a refused upload with a code in the endpoint's area (`entity`, `event`, `space`, `user`, `auth`, `chat`, `storage`). These are checked as the body is read, before the endpoint's own checks:

| Status | Code | When |
|--------|------|------|
| `413` | `<area>/file-too-large` | A file is over the 100 MB upload limit. `param` names its field. |
| `400` | `<area>/unsupported-file-type` | A file isn't JPEG, PNG, WebP or PDF. |
| `400` | `<area>/unexpected-file-field` | A file is in a field the endpoint doesn't take, or a field has more files than it takes. `param` names the field. |
| `413` | `<area>/field-too-large` | A text field in the multipart body is too large. `param` names the field. |
| `400` | `<area>/invalid-multipart` | The multipart body is malformed. |

Endpoints that process images add their own, lower limits and checks (for example `413 <area>/file-too-large` for an image over 50 MB, `422 <area>/invalid-image`); each endpoint's page lists them.

### Common HTTP Status Codes

| Status | Meaning |
|--------|---------|
| `200` | Success |
| `201` | Resource created |
| `400` | Bad request — invalid input or missing required fields |
| `401` | Unauthorized — no `Authorization` header, or a request the endpoint requires a user for |
| `403` | Forbidden — token expired or invalid, or a valid token without the required permission |
| `404` | Not found |
| `409` | Conflict — the value is already taken (`auth/email-taken`, `auth/username-taken`, `<area>/foreign-id-taken`) |
| `413` | Payload too large — a body over the size limit (`request/body-too-large`) or a file over the upload limit (`<area>/file-too-large`) |
| `429` | Too many requests — the endpoint's rate limit (`request/rate-limited`) or the project's plan quota (`project/quota-reached`) |
| `500` | Internal server error — `<area>/server-error` |

<Note>
  An **expired token returns `403`, not `401`** — see
  [Authentication](/v8/api-reference/authentication) for why that distinction
  matters when writing your own refresh logic.
</Note>

## Rate Limiting

Each endpoint has its own rate limit, counted per client IP. When a limit is exceeded, the API returns `429` with code `request/rate-limited` and the endpoint's own message as `error`:

```json
{
  "error": "Too many sign in attempts, please wait 5 minutes",
  "code": "request/rate-limited"
}
```

The response carries the standard rate-limit headers. Limits are noted per endpoint in this reference.
