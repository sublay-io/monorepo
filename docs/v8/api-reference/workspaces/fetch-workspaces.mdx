---
title: "List Workspaces"
api: "GET /v8/:projectId/workspaces"
description: "List the workspaces the caller can open, or only the ones they own or are a member of"
---

Returns a paginated list of the caller's workspaces. By default that is **every workspace the caller can open** — every workspace [Fetch Workspace](/v8/api-reference/workspaces/fetch-workspace) would return for them. With `relation=direct` it is only the workspaces they own or have a member row on. Every row carries `reasons`: why the caller can open it.

## Query Parameters

<ParamField query="relation" type="string">
  Which workspaces the list holds:
  - `reachable` (the default): every workspace the caller can open. That is a workspace they own, one they have a member row on, one under a workspace they own (at any depth, whatever the [inherit flags](/v8/data-models/workspace#reach-and-the-wall-door-rule) say), and one a capability they hold on an ancestor reaches through an unbroken chain of `inheritsFromParent: true`.
  - `direct`: only the workspaces the caller owns or has a member row on.

  Left out or sent empty: `reachable`. Values match exactly. `null` and `undefined` are refused with `400 workspace/unsupported-param` (see [Saying "no value"](/v8/authentication#saying-no-value)); any other value returns `400 workspace/invalid-query`.
</ParamField>

<ParamField query="sortDir" type="string">
  The order, by creation time: `desc` (the default) newest first, `asc` oldest first. Rows created at the same moment are ordered by id in the same direction, so the order is the same on every request and pages neither repeat nor skip a row.

  A workspace can't be moved to another parent, so a sub-workspace is always newer than its parent: `asc` lists every parent before its children. See [Building a workspace switcher](/v8/sdk/workspaces/overview#building-a-workspace-switcher).

  Left out or sent empty: `desc`. Case is ignored (`DESC` works). `null` and `undefined` are refused with `400 workspace/unsupported-param`; any other value returns `400 workspace/invalid-query`.
</ParamField>

<ParamField query="page" type="number">
  Page number for pagination.
</ParamField>

<ParamField query="limit" type="number">
  Page size.
</ParamField>

<ParamField query="parentWorkspaceId" type="string">
  Narrows the list by where each workspace sits in the tree:
  - `none`: top-level workspaces only (workspaces with no parent).
  - A workspace id: the caller's workspaces directly under that workspace. An id that matches no workspace returns an empty page, not a 404.
  - `any`, left out, or sent empty: workspaces at every level. This is the default.

  The filter applies within `relation`: a workspace id lists the direct sub-workspaces of that workspace that are in the caller's list, and `none` lists the top-level workspaces in it. So `none` leaves out a sub-workspace the caller is a member of even when they aren't in its parent; `any` includes it. It works with `page`, `limit` (the pagination counts reflect the filter) and `include`. `null` and `undefined` are refused with `400 workspace/unsupported-param` (see [Saying "no value"](/v8/authentication#saying-no-value)). `none` and `any` match exactly (`ANY` is refused). Any other value that isn't a workspace id returns `400 workspace/invalid-query`.
</ParamField>

<ParamField query="include" type="string">
  Include flags, as a comma-separated value or repeated params. The only value is `memberCount`: it adds a `memberCount` to **every row** — the workspace's **direct** member count, the same number [Fetch Workspace](/v8/api-reference/workspaces/fetch-workspace) returns for one workspace, counting neither descendants nor reach-holders.

  It is resolved with a single grouped query over the page that was returned, so a workspace switcher showing counts costs one request rather than one per row. Omit the flag and the field is **absent** from each row — not `null`, not `0`. Matching ignores case; an unknown value returns `400 workspace/invalid-query`.
</ParamField>

<ParamField query="actingUserId" type="string" required>
  Service keys only — the user to act as, whose workspaces are listed and whose `reasons` each row carries. **Required for a key:** the list is defined as *somebody's* workspaces, so a key that names nobody is refused with `400 workspace/missing-user-id`.

  A user token always acts as its own user and must not send it (`400 workspace/acting-user-not-allowed`). See [Acting on behalf of a user](/v8/sdk/workspaces/overview#acting-on-behalf-of-a-user).
</ParamField>

## Response

Returns a paginated response of [Workspace](/v8/data-models/workspace) objects, each with `reasons`.

<ResponseField name="data[].reasons" type="{ type, viaWorkspaceId? }[]">
  The caller's full standing on the workspace, one entry per grant: `owner`, `member`, `ancestor-owner` (with the ancestor they own as `viaWorkspaceId`) and `reach-holder` (with the ancestor whose capability reaches here). These are the same entries, in the same order, that the [authority read](/v8/api-reference/workspaces/fetch-authority) returns for that workspace. They describe all of the caller's standing even under `relation=direct`: `relation` picks the rows, not the reasons, so a workspace the caller is a member of and also owns an ancestor of carries both `member` and `ancestor-owner`.
</ResponseField>

```
GET /v8/:projectId/workspaces?parentWorkspaceId=none&page=1&limit=10&include=memberCount
```

```json
{
  "data": [
    {
      "id": "0f1c7a6e-9d4b-4f2a-8c31-5b6e2a7d1c04",
      "name": "Acme HQ",
      "metadata": {},
      "ownerId": "3a9e5c11-72d8-4a6b-9f10-8c2d4e7b5a33",
      "parentWorkspaceId": null,
      "depth": 0,
      "inheritsFromParent": false,
      "createdAt": "2026-01-14T09:12:44.001Z",
      "updatedAt": "2026-01-14T09:12:44.001Z",
      "memberCount": 12,
      "reasons": [{ "type": "member" }]
    }
  ],
  "pagination": { "page": 1, "pageSize": 10, "totalPages": 1, "totalItems": 1, "hasMore": false }
}
```

`memberCount` appears only when `include=memberCount` was sent. `limit` defaults to `20` when omitted, and `page` to `1`.

## Error Responses

<AccordionGroup>
  <Accordion title="Missing Acting User — 400">
    ```json
    { "error": "A service key must send actingUserId: the user this request acts as.", "code": "workspace/missing-user-id" }
    ```
    A service key called this route without naming an `actingUserId`. The listing is scoped to a user's own memberships and owned workspaces, so there is nobody to scope it to.
  </Accordion>
  <Accordion title="Acting User Not Allowed — 400">
    ```json
    { "error": "actingUserId is only accepted with a service key. A user's own token always acts as that user.", "code": "workspace/acting-user-not-allowed" }
    ```
    A user token sent `actingUserId`, even naming its own user. Only a service key names the user it acts as; a user token always acts as its own user.
  </Accordion>
  <Accordion title="Body Not Allowed — 400">
    ```json
    { "error": "A GET request takes no body: send its fields in the query string. Received: `actingUserId`.", "code": "workspace/body-not-allowed", "params": ["actingUserId"] }
    ```
    A `GET` takes every field, `actingUserId` included, in the query string, so any request body is refused: a JSON object with keys, a non-empty array, or a non-JSON payload such as multipart (then `params` is omitted). An absent body and `{}` pass.
  </Accordion>
  <Accordion title="User Not Found — 404">
    ```json
    { "error": "No user with this actingUserId exists in this project.", "code": "workspace/user-not-found" }
    ```
    Returned when a service key names an `actingUserId` that isn't a user in this project.
  </Accordion>
  <Accordion title="Unsupported parentWorkspaceId, relation or sortDir value — 400">
    ```json
    { "error": "`parentWorkspaceId=null` isn't supported. Use `parentWorkspaceId=none` for top-level workspaces, or `parentWorkspaceId=any` for every level (the default).", "code": "workspace/unsupported-param", "param": "parentWorkspaceId" }
    ```
    `null` and `undefined` as the value of `parentWorkspaceId`, `relation` or `sortDir` are rejected with the values to use instead, and `param` names the parameter. To use a default, leave the parameter out.
  </Accordion>
  <Accordion title="Unknown relation or sortDir — 400">
    Returned with code `workspace/invalid-query` for a `relation` other than `direct` or `reachable`, or a `sortDir` other than `asc` or `desc`. `relation` values match exactly (`Direct` is refused); `sortDir` ignores case.
  </Accordion>
  <Accordion title="Unknown Include — 400">
    ```json
    { "error": "include: Unknown include `members`. Allowed: memberCount.", "code": "workspace/invalid-query" }
    ```
    An `include` value outside `memberCount`. Matching ignores case.
  </Accordion>
  <Accordion title="Undeclared Query Parameter — 400">
    ```json
    { "error": "Unrecognized key: \"sort\"", "code": "workspace/invalid-query" }
    ```
    This route declares `page`, `limit`, `relation`, `parentWorkspaceId`, `sortDir`, `include` and `actingUserId`, and refuses anything else rather than ignoring it. Two or more at once are named together: `Unrecognized keys: "sort", "order"`. The two exceptions across the bundle are the cache-busters `_` and `_t`, which are dropped before the request is read. See [Shapes the server rejects](/v8/sdk/workspaces/overview#shapes-the-server-rejects).
  </Accordion>
</AccordionGroup>
