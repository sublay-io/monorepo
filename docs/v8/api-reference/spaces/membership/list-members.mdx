Returns a paginated list of space members with embedded user details.

## Path Parameters

<ParamField path="spaceId" type="string" required>
  UUID of the space.
</ParamField>

## Query Parameters

<ParamField query="actingUserId" type="string">
  Service key only: the user to list as. The page is exactly what that user's own access token would get (their membership, so a members-only space's list is open to them only as an active member). Leave it out for the anonymous view: a members-only space's list returns `403`. A user token always acts as its own user and must not send it, and neither may a request with no credentials (`400 space/acting-user-not-allowed`).
</ParamField>

<ParamField query="page" type="number">
  Page number. Defaults to `1`.
</ParamField>

<ParamField query="limit" type="number">
  Results per page.
</ParamField>

<ParamField query="status" type="string">
  Filter by status: `"pending"`, `"active"`, `"banned"`, or `"rejected"`.
</ParamField>

<ParamField query="role" type="string">
  Filter by role: `"admin"`, `"moderator"`, or `"member"`.
</ParamField>

### Space-scoped reputation

This endpoint has a space in context, so it accepts the opt-in reputation params. They add a `spaceReputation` field to each returned member's `user`, alongside the always-present `reputation` total. Requires the `reputation` bundle. See the [Reputation data model](/v8/data-models/reputation) for the full contract.

## Error Responses

<AccordionGroup>
  <Accordion title="Invalid Id — 400">
    Returned when `spaceId` isn't a valid UUID. Checked before sign-in, permissions and the endpoint's other checks.
    ```json
    { "error": "Invalid space id: expected a UUID.", "code": "space/invalid-params" }
    ```
  </Accordion>
  <Accordion title="Members Only — 403">
    The space has `readingPermission: "members"` and the caller is not an active member (no membership, or one that is pending, banned or rejected).
    ```json
    { "error": "This space requires membership. You must be a member to view members.", "code": "space/members-access-denied" }
    ```
  </Accordion>
  <Accordion title="Acting User Not Allowed — 400">
    A user token, or a request with no credentials, sent `actingUserId`, even naming its own user. Only a service key names the user it acts as; a user token always acts as its own user.

    ```json
    { "error": "actingUserId is only accepted with a service key. A user's own token always acts as that user.", "code": "space/acting-user-not-allowed" }
    ```
  </Accordion>
  <Accordion title="User Not Found — 404">
    Returned when a service key names an `actingUserId` that isn't a user in this project.

    ```json
    { "error": "No user with this actingUserId exists in this project.", "code": "space/user-not-found" }
    ```
  </Accordion>
  <Accordion title="Space Not Found — 404">
    The space doesn't exist, or the viewer can't see it (a private space they aren't an active member of, or a space under one). Both answer the same way, before any permission check. See [Space visibility](/v8/data-models/space#visibility).
    ```json
    { "error": "Space not found.", "code": "space/not-found" }
    ```
  </Accordion>
</AccordionGroup>
