The Sublay REST API is a project-scoped HTTP API. All endpoints follow the same base structure and share common conventions for authentication, pagination, and error reporting.

## Base URL

All API requests are made to:

```
https://api.sublay.io/v8/:projectId
```

Replace `:projectId` with the UUID of your Sublay project, which you can find in the [Sublay dashboard](https://dash.sublay.io).

So every endpoint takes the form:

```
https://api.sublay.io/v8/:projectId/<endpoint>
```

The project is read from the path only. Don't send `projectId` in the query string or the body, or an `x-sublay-project-id` header: each is refused with `400 project/wrong-location`. The exception is a custom-table column named `projectId`, which stays writable in the row bodies of [Insert Row](/v8/api-reference/custom-tables/insert-row), [Bulk Insert Rows](/v8/api-reference/custom-tables/bulk-insert-rows) (inside each entry of `rows`) and [Update Row](/v8/api-reference/custom-tables/update-row).

## Request Format

Most endpoints accept `application/json`. Endpoints that support file uploads accept `multipart/form-data`. The `Content-Type` header should be set accordingly.

Where each field goes is decided by the method: the path holds the resource, GET and DELETE take every other field in the query string and no body, and POST, PATCH and PUT take every other field in the body, `actingUserId` included. Each field is read from one place; sent elsewhere, it is refused with a `400` that names the right place:

| Code | When |
|---|---|
| `<area>/body-not-allowed` | A GET or DELETE has a body. |
| `<area>/wrong-location` | A POST, PATCH or PUT has a body field (or `actingUserId`) in its query string. |
| `project/wrong-location` | `projectId` anywhere but the path, or a project-id header. |
| `<area>/unsupported-route` | A route v8 moved; `error` names the one to call. |

See [Where each input goes](/v8/authentication#where-each-input-goes).

```http
POST /v8/:projectId/auth/sign-in
Content-Type: application/json

{
  "email": "user@example.com",
  "password": "secret"
}
```

## Ids

Every Sublay record id (`spaceId`, `entityId`, `userId`, …) is a UUID. Ids are accepted in either case and the server lowercases them; record ids in responses are lowercase.

An id that isn't a UUID is refused with `400`:

- **In the URL path:** checked before sign-in, permissions or any lookup (only a missing bundle, `403 database/tables-not-available`, is reported first). Code `<area>/invalid-params`, where `<area>` is the endpoint's area (`space`, `entity`, `chat`, …):

  ```json
  {
    "error": "Invalid space id: expected a UUID.",
    "code": "space/invalid-params", "param": "spaceId"
  }
  ```

- **In the query string or body:** code `<area>/invalid-query` or `<area>/invalid-body`, with `error` naming the field.

`foreignId` and `sourceId` are your own strings, not Sublay ids, so they accept any text, except that `sourceId` can't be `none`, `null` or `undefined`: list filters use `none` for "no source" (see [Saying "no value"](/v8/authentication#saying-no-value)).

## Authentication

Protected endpoints require a `Bearer` token in the `Authorization` header:

```http
GET /v8/:projectId/app-notifications
Authorization: Bearer <accessToken>
```

See [Authentication](/v8/api-reference/authentication) for full details on obtaining and refreshing tokens.

## Pagination

Endpoints that return pages of records use offset pagination. Pass `page` and `limit` as query parameters:

| Parameter | Default | Allowed | Description |
|-----------|---------|---------|-------------|
| `page` | `1` | A whole number from `1` to `9007199254740991` | Page number (1-indexed) |
| `limit` | Endpoint-specific | A whole number from `1` to `100` | Results per page |

The maximum `limit` is `100` on every page-numbered endpoint. Each endpoint's page gives its default.

Both values are written as plain digits. A request is refused with `400 <area>/invalid-query` in the endpoint's own area, with `param` naming the field (`page` or `limit`), when it sends:

- a `limit` above `100`. It is never lowered to `100` for you; the message names the maximum.
- a `page` above `9007199254740991` (`"page: Page must be at most 9007199254740991"`).
- `0`, a negative number, a decimal (`1.5`), an exponent (`1e1`), trailing text (`5abc`), surrounding spaces or an empty value.

```json
{
  "error": "limit: Limit must be at most 100",
  "code": "entity/invalid-query",
  "param": "limit"
}
```

Paginated responses always return the same envelope:

```json
{
  "data": [...],
  "pagination": {
    "page": 1,
    "pageSize": 20,
    "totalPages": 5,
    "totalItems": 97,
    "hasMore": true
  }
}
```

To read a whole list, request pages in turn (`page=1`, `page=2`, …) until `pagination.hasMore` is `false`; a paginated endpoint never returns all its records in one response.

Chat conversations, chat messages and comments page by cursor instead, with the same `data` and a `pagination.hasMore`. Comments and chat conversations take an opaque `cursor`: pass the previous page's `pagination.nextCursor` back unchanged. Chat messages page before or after a message: pass the id of the first or last message you hold as `before` or `after`. Their pages describe the details.

## Error Format

Every error is JSON with the same two keys:

```json
{
  "error": "Human-readable error message.",
  "code": "feature/error-slug"
}
```

- `error` is text for people. Show it or log it, but don't branch on it: it can change.
- `code` is stable, in the form `<area>/<kebab-case-slug>` (`entity/not-found`, `auth/email-taken`). Branch on this.

Some errors add keys:

- `param` names the failing input when the error is about one: a validation `400` (`<area>/invalid-body`, `<area>/invalid-query`, `<area>/invalid-params`), including a key the endpoint doesn't take and a malformed or misspelled `actingUserId`; an id that isn't a UUID, the project id in the path included (`project/invalid-id`); a value another record already holds (`<area>/foreign-id-taken`, `<area>/username-taken`, `auth/email-taken`, `space/slug-taken`); a referenced record that can't be used (`chat/invalid-parent`, `chat/invalid-quote`, `collection/invalid-parent`); a single value the endpoint refuses (`chat/invalid-emoji`, `auth/redirect-url-not-allowed`); an image-options field that is missing or isn't valid JSON; a refused file (`<area>/file-too-large`, `<area>/unsupported-file-type`, `<area>/unexpected-file-field`, `<area>/invalid-image`). It is the input's dot path, as you sent it (`email`, `metadata.title`, `images.options`, `images`). A validation rule that checks several fields together names the field it's about, or leaves `param` out when no single field is. It is left out when the error is about the request as a whole: a body sent with a content type the server doesn't read, or a query string with more parameters than the server reads.

  ```json
  {
    "error": "Username already taken",
    "code": "auth/username-taken",
    "param": "username"
  }
  ```

- A `500`'s code is `<area>/server-error`, with two exceptions on [sign-out](/v8/api-reference/auth/sign-out): `auth/device-deregistration-failed` and `auth/sign-out-failed`. The underlying failure is recorded in Sublay's server logs, not returned in the response.
- Some errors add keys of their own (`missingTables`, `bundleId` and `dashboardUrl` on a missing bundle, `verificationId` on an unverified sign-in); each endpoint's page lists them.

Two exceptions:

- An access token that is missing, expired or invalid gets a bare `401 Unauthorized` / `403 Forbidden` with no JSON body. See [Authentication](/v8/api-reference/authentication).
- The pages Sublay hosts for your users to open in a browser answer their errors as pages, not JSON: the [email verification link](/v8/api-reference/auth/verify-email-link) (its `429` is a plain sentence) and the password reset page.

### Request errors

These can come from any endpoint, because they are about the HTTP request itself rather than the resource. For a body the rule is: a `request/` code means the body couldn't be read at all; once it is read, anything wrong with its content gets the endpoint's own area code (`<area>/invalid-body`, the upload errors below).

| Status | Code | When |
|--------|------|------|
| `400` | `request/invalid-json` | The body is sent as JSON but doesn't parse, or parses to a value that isn't an object or an array (`"text"`, `42`, `null`). |
| `413` | `request/body-too-large` | The JSON body is over the 100 KB limit, or a `multipart/form-data` body is over the 250 MB limit. |
| `400` | `request/invalid-multipart` | The `multipart/form-data` body is malformed. `param` names the field when the fault is in one. |
| `413` | `request/field-too-large` | A text field in a multipart body is too large. `param` names the field. |
| `400` / `415` | `request/unreadable-body` | The body can't be read for another reason: `415` for a charset or content encoding the server can't read, `400` otherwise (for example an aborted request). |
| `403` | `request/origin-not-allowed` | The request comes from a browser origin that isn't in the project's allowed domains. The response carries no CORS headers, so the browser hides it from the page (the request fails as a CORS error); the code is visible to server-side callers and tools such as curl. |
| `404` | `request/route-not-found` | No endpoint matches the method and path. |
| `429` | `request/rate-limited` | The endpoint's rate limit for your IP is exceeded. See [Rate Limiting](#rate-limiting). |
| `500` | `request/server-error` | An unexpected failure outside any endpoint's own handling. |

### Upload errors

Endpoints that take a file in a `multipart/form-data` body answer a refused file with a code in the endpoint's area (`entity`, `event`, `comment`, `space`, `user`, `auth`, `chat`, `storage`):

| Status | Code | When |
|--------|------|------|
| `413` | `<area>/file-too-large` | A file is over the 50 MB limit. `param` names its field. |
| `413` | `<area>/too-many-files` | The request carries more than 20 files, counting all its file fields together. |
| `413` | `request/body-too-large` | The whole body is over 250 MB. |
| `400` | `<area>/unsupported-file-type` | A file isn't JPEG, PNG, WebP or PDF. `param` names its field. |
| `400` | `<area>/unexpected-file-field` | A file is in a field the endpoint doesn't take, or a field has more files than it takes. `param` names the field. |

The limits are per request, the same on every endpoint: at most 50 MB per file, 20 files in total, and 250 MB for the whole body. A field that holds a list of files takes up to 20 of them; a field that holds one file (`avatarFile`, `bannerFile`, `coverFile`) takes one. They don't cap how many files a record holds: an update can add more. A record's files are sent in the same fields everywhere: one image in a slot (`avatarFile`, `bannerFile`, `coverFile`) with its options in `<field>.options`, and a list as `images` (processed into sizes, `images.options` required) and `files` (stored as uploaded, `files.options` optional). An update that holds files takes `removeFileIds`. Endpoints that process images add their own checks (for example `422 <area>/invalid-image` for a file that isn't a valid image, with `param` naming its field, and `400 <area>/missing-image-options` for images sent without their options); an id in `removeFileIds` that isn't the record's own file gets `400 <area>/invalid-remove-file-ids`, and uploads that would take the project past its plan's file-storage limit get `429 project/quota-reached`. Each endpoint's page lists them.

### File link errors

Loading a file through its link (an `originalPath` or `publicPath`, which is how `<img>` and image components load it) needs no credentials: the link itself is the proof. A link that doesn't work answers:

| Status | Code | When |
|--------|------|------|
| `403` | `files/invalid-link` | The link was changed, cut short, or never came from Sublay. Use it exactly as it was returned. |
| `403` | `files/link-expired` | The link is past its File's `linksExpireAt`. Get a fresh one by reading the record again, or from [Refresh File Links](/v8/api-reference/storage/refresh-file-links). |
| `404` | `files/not-found` | The file is no longer stored. |
| `429` | `project/quota-reached` | The project is over its plan's monthly download (egress) limit. |

### Same situation, same answer

The same situation gets the same status and the same kind of code on every endpoint, so you can handle each one once:

| Situation | Status | Code |
|-----------|--------|------|
| The caller can see it but may not do this: not the author or owner, not an admin of the group, a role or capability that doesn't allow it | `403` | `<area>/forbidden` (`entity/forbidden`, `chat/forbidden`, `workspace/forbidden`). When the refusal is about one specific role the action needs, the code names it: `space/admin-required`, `space/moderator-required`, `space/creator-required`, `space/membership-required`, `workspace/insufficient-rank` |
| Something the caller can't see: a private space they aren't in, a workspace they have no relation to (on a read or a write), a connection or connection request between two other users | `404` | The same code and text as when it doesn't exist (`space/not-found`, `workspace/not-found`, `connection/not-found`), so a response never confirms that it exists |
| The caller can see it but isn't a member: posting in, leaving or managing a conversation they aren't an active member of, leaving or editing their membership of a workspace they only reach from above | `403` | `<area>/not-a-member` or `<area>/not-member` |
| A request, invitation or membership that is no longer pending: already approved, accepted, declined, revoked or expired | `409` | `<area>/not-pending` (`space/not-pending`, `connection/not-pending`, `workspace/not-pending`) |
| The request would leave nobody in charge: the last admin leaving, being demoted or being banned, the creator leaving, the sole owner leaving or being removed | `409` | `space/last-admin`, `space/creator-cannot-leave`, `chat/last-admin`, `event/last-host`, `workspace/sole-owner` |
| A user named in the request doesn't exist | `404` | `<area>/user-not-found`. One exception: the user to start a conversation with or add to one (creating a direct or group conversation, adding a member) answers `400 chat/invalid-member` when they don't exist (when starting a direct conversation, also when a block stands between you) |
| A list's filters are missing, combined or half-filled | `400` | `<area>/invalid-query`, with `param` naming the field to fix |
| Your validation webhook rejected the request | `400` | `<area>/webhook-validation-failed`, with your webhook's message as `error` |
| The feature, or one part of the request, needs a bundle that isn't installed | `403` | `database/tables-not-available`, with `missingTables`, `bundleId` and `dashboardUrl`; `503 database/tables-provisioning` while the bundle is being installed. See [Bundles](/v8/bundles#what-happens-if-a-bundle-isnt-installed) |

### Common HTTP Status Codes

| Status | Meaning |
|--------|---------|
| `200` | Success |
| `201` | Resource created |
| `400` | Bad request — invalid input or missing required fields |
| `401` | Unauthorized — no `Authorization` header, or a request the endpoint requires a user for |
| `403` | Forbidden — token expired or invalid, a caller who may not do this (`<area>/forbidden`, or a code naming the role the action needs), a feature whose bundle isn't installed (`database/tables-not-available`), or a browser origin outside the project's allowed domains (`request/origin-not-allowed`) |
| `404` | Not found — it doesn't exist, or the caller can't see it (the two answer alike) |
| `409` | Conflict — the value is already taken (`auth/email-taken`, `<area>/username-taken`, `<area>/foreign-id-taken`), the request is no longer pending (`<area>/not-pending`), or the change would leave nobody in charge (`space/last-admin`, `chat/last-admin`, `workspace/sole-owner`) |
| `413` | Payload too large — a body over the size limit (`request/body-too-large`), a file over the upload limit (`<area>/file-too-large`), or more files than a request takes (`<area>/too-many-files`) |
| `429` | Too many requests — the endpoint's rate limit (`request/rate-limited`) or the project's plan quota (`project/quota-reached`) |
| `500` | Internal server error — `<area>/server-error` |

<Note>
  An **expired token returns `403`, not `401`** — see
  [Authentication](/v8/api-reference/authentication) for why that distinction
  matters when writing your own refresh logic.
</Note>

## Rate Limiting

Each endpoint has its own rate limit, counted per client IP. When a limit is exceeded, the API returns `429` with code `request/rate-limited` and the endpoint's own message as `error`:

```json
{
  "error": "Too many sign in attempts, please wait 5 minutes",
  "code": "request/rate-limited"
}
```

The response carries the standard rate-limit headers. Limits are noted per endpoint in this reference.
