---
title: "Verify Email Link"
api: "GET /v7/:projectId/auth/verify-email-link"
description: "The page a verification email's link opens: confirm to verify"
---

The page a verification email's link opens (emails sent with `mode: "link"`). Opening it doesn't verify anything: it shows a Sublay page asking the user to confirm — "Only confirm if you created an account with {your app's name}" — with a **Confirm my email** button. Clicking it verifies the email (`isVerified` becomes `true`) and invalidates the token.

The confirm step exists because work email scanners open every link in incoming mail. If opening the link verified the account, a scanner could verify an account someone else created with that person's email.

You don't call this endpoint from your app: it's the target of the button in the email.

## Query Parameters

<ParamField query="token" type="string" required>
  The verification token embedded in the link by the server.
</ParamField>

## Behaviour

| Outcome | `redirectUrl` was given | No `redirectUrl` |
|---------|------------------------|------------------|
| Link opened | Confirm page | Confirm page |
| Confirmed | Success page, then on to `{redirectUrl}` with `verified=true` added to its query after 5 seconds (or at once with **Continue now**) | Success page |
| Invalid / expired token | Hosted error page | Hosted error page |
| Server error | Hosted error page | Hosted error page |

The destination is the `redirectUrl` you passed to [Send Verification Email](/v7/api-reference/auth/send-verification-email), stored with the token when the email was sent. The link itself carries no destination, so it can't be edited to send someone elsewhere. Only `http` and `https` addresses are followed. A failed verification always shows the hosted page.
