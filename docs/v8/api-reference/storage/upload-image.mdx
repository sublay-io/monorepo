---
title: "Upload Image"
api: "POST /v8/:projectId/storage/images"
description: "Upload an image with server-side processing and named variant generation"
---

Uploads an image, processes it, and stores the original plus all requested variants. Returns the [File](/v8/data-models/file) with its image data and the proxy URL of every variant.

The uploaded file isn't attached to anything: it has no entity, comment, space or event. A file that belongs to a record is sent with that record's own request (for example, the `images` and `files` of [Create Entity](/v8/api-reference/entities/create-entity) or [Create Comment](/v8/api-reference/comments/create-comment), or the cover of [Update Event](/v8/api-reference/events/update-event)).

This endpoint accepts `multipart/form-data`. Requires an authenticated user.

**Rate limit**: 20 requests per 5 minutes.

## Body Parameters

<ParamField body="file" type="file" required>
  The image file to upload: JPEG, PNG or WebP. Maximum 50 MB, and from 1 × 1 to 10000 × 10000 px.
</ParamField>

<ParamField body="file.options" type="string" required>
  Stringified JSON: the image-processing options, one object. These are the same options, with the same rules, as an inline `<field>.options` (for example `avatarFile.options` on [Update User](/v8/api-reference/users/update-user) or `images.options` on [Create Entity](/v8/api-reference/entities/create-entity)). Must include `mode`. A request without `file.options` gets `400 storage/missing-image-options`; options that aren't valid JSON or valid image options (`mode` missing included) get `400 storage/invalid-body`.

  ```json
  { "mode": "original-aspect", "sizes": { "small": 64, "large": 512 }, "pathParts": ["avatars", "user-123"] }
  ```

  <Expandable title="file.options fields">
    <ParamField body="mode" type="string" required>
      Processing mode. One of: `exact-dimensions`, `aspect-ratio-width-based`, `aspect-ratio-height-based`, `original-aspect`, `multi-aspect-ratio`.
    </ParamField>

    <ParamField body="dimensions" type="object">
      Required for `exact-dimensions` mode. An object mapping variant names to `{ width, height }` pairs, each from 1 to 10000 px; at most 30 entries (one variant each).

      ```json
      { "thumbnail": { "width": 64, "height": 64 }, "card": { "width": 400, "height": 300 } }
      ```
    </ParamField>

    <ParamField body="aspectRatio" type="object">
      Required for `aspect-ratio-width-based` and `aspect-ratio-height-based` modes. `{ width, height }` ratio, positive whole numbers. A side computed from the ratio must also be 1–10000 px; one outside that range gets `400 storage/invalid-body` (see Errors).
    </ParamField>

    <ParamField body="widths" type="object">
      Required for `aspect-ratio-width-based` mode. An object mapping variant names to pixel widths, each from 1 to 10000; at most 30 entries (one variant each).
    </ParamField>

    <ParamField body="heights" type="object">
      Required for `aspect-ratio-height-based` mode. An object mapping variant names to pixel heights, each from 1 to 10000; at most 30 entries (one variant each).
    </ParamField>

    <ParamField body="sizes" type="object">
      Required for `original-aspect` and `multi-aspect-ratio` modes. An object mapping variant names to longest-edge pixel sizes, each from 1 to 10000; at most 30 entries (one variant each). In `multi-aspect-ratio` the server uses the one ratio in `aspectRatios` closest to the image, so the variants are one per `sizes` entry.
    </ParamField>

    <ParamField body="aspectRatios" type="array">
      Required for `multi-aspect-ratio` mode. 1 to 10 `{ width, height }` aspect ratio objects. Each variant's computed width and height must be 1–10000 px; a side outside that range gets `400 storage/invalid-body` (see Errors).
    </ParamField>

    <ParamField body="fit" type="string">
      How each variant fits its requested size. Defaults to `inside`. Valid values depend on the mode:
      - `exact-dimensions`, `aspect-ratio-width-based`, `aspect-ratio-height-based`, `multi-aspect-ratio`: `cover`, `contain`, `inside`, or `outside`
      - `original-aspect`: `inside` or `outside` only (`cover`/`contain` are not valid for this mode)
    </ParamField>

    <ParamField body="quality" type="number">
      Output quality (1–100). Applies to JPEG and WebP. Defaults to `85`.
    </ParamField>

    <ParamField body="format" type="string">
      Output format: `webp`, `jpeg`, `png`, or `original`. Defaults to `webp`. `original` keeps the upload's format when it is JPEG, PNG or WebP, and stores anything else (an AVIF or HEIC, for example) as WebP.
    </ParamField>

    <ParamField body="stripExif" type="boolean">
      Remove EXIF metadata from output. Defaults to `true`.
    </ParamField>

    <ParamField body="originalMaxSize" type="number">
      The longest side, in px, the stored original is shrunk to (50–10000). Defaults to `3840`. An original already within it keeps its size. The File's `originalSize` and its image's `originalWidth` and `originalHeight` describe the stored original. A larger original takes more storage, which counts toward the project's file-storage limit.
    </ParamField>

    <ParamField body="pathParts" type="string[]">
      Folder segments for the stored image. The new file's id is always added after them, so the image and its sizes are stored under `<pathParts>/<fileId>/`. Example: `["avatars", "user-123"]` → `avatars/user-123/<fileId>/<filename>`, the file name taking the stored format's extension (`photo.png` stored as WebP is `photo.webp`). Defaults to `["images"]`. A part that is, or contains, a `.` or `..` folder (also written `%2e%2e`), or that contains `?`, `#` or an encoded slash (`%2f`, `%5c`), is refused with `400 storage/invalid-body` and `param` `file.options.pathParts`.
    </ParamField>
  </Expandable>
</ParamField>

<ParamField body="metadata" type="string">
  Stringified JSON object of custom key-value data stored on the file. The server adds `originalName` and `uploadedAt` alongside, replacing any values of yours under those keys. Anything other than a JSON object is refused with `400 storage/invalid-body`.
</ParamField>

<ParamField body="actingUserId" type="string">
  Service key only: the user this request acts as, who owns the uploaded file; the upload runs under that user's own checks. Leave it out to upload an app-owned file with no owning user. A user that doesn't exist returns `404 storage/user-not-found`. A user token always acts as its own user and must not send it (`400 storage/acting-user-not-allowed`).
</ParamField>

## Response

`201 Created` with the [File](/v8/data-models/file), the same shape [Fetch File](/v8/api-reference/storage/fetch-file) returns, its `image` data included. `originalSize`, `originalMimeType` and the image's `originalWidth` and `originalHeight` describe the stored original: the image in its output `format`, shrunk to `originalMaxSize`.

  "chatMessageId": null,

## Error Responses

<AccordionGroup>
  <Accordion title="Not signed in — 401 / 403">
    Returned with no JSON body: `401` when no `Authorization` header is sent, `403` when the access token is invalid or expired. Checked before any uploaded file is read, so a request with no credentials gets `401` rather than a body or acting-user error.
  </Accordion>
  <Accordion title="Acting User Not Allowed — 400">
    A user token sent `actingUserId`, even naming its own user. Only a service key names the user it acts as; a user token always acts as its own user.
    ```json
    { "error": "actingUserId is only accepted with a service key. A user's own token always acts as that user.", "code": "storage/acting-user-not-allowed" }
    ```
  </Accordion>
  <Accordion title="Unsupported Parameter — 400">
    The request sent an image option as its own field: `mode`, `dimensions`, `aspectRatio`, `widths`, `heights`, `sizes`, `aspectRatios`, `fit`, `quality`, `format`, `stripExif` or `pathParts`. They go inside `file.options`. Refused even next to a valid `file.options`, and nothing is stored. `param` names the field:

    ```json
    {
      "error": "`mode` isn't supported in v8. Send it inside `file.options`, the image options as one JSON object.",
      "code": "storage/unsupported-param",
      "param": "mode"
    }
    ```

    The request sent `entityId`, `commentId`, `spaceId` or `eventId`. A file uploaded here isn't attached to anything, so these fields are refused rather than ignored, and nothing is stored. `param` names the field:

    ```json
    {
      "error": "`entityId` isn't accepted: a file uploaded here isn't attached to anything.",
      "code": "storage/unsupported-param",
      "param": "entityId"
    }
    ```

    The request sent `userId`. On this route the user a service key acts as is `actingUserId`.

    With a service key:

    ```json
    {
      "error": "`userId` was renamed to `actingUserId`: send the user this service key acts as in `actingUserId`.",
      "code": "storage/unsupported-param",
      "param": "userId"
    }
    ```

    With a user token:

    ```json
    {
      "error": "`userId` isn't accepted here: a user's own token always acts as that user.",
      "code": "storage/unsupported-param",
      "param": "userId"
    }
    ```
  </Accordion>
  <Accordion title="Invalid Body — 400">
    `file.options` or `metadata` was refused. Nothing is stored. `error` names the field first, and `param` names it alone.

    `file.options` without `mode`, or with a `mode` that isn't one of the five:

    ```json
    { "error": "file.options.mode: Invalid input", "code": "storage/invalid-body", "param": "file.options.mode" }
    ```

    `file.options` isn't valid JSON:

    ```json
    { "error": "file.options: Must be a valid JSON string", "code": "storage/invalid-body", "param": "file.options" }
    ```

    A folder in `pathParts` is refused:

    ```json
    { "error": "file.options.pathParts: pathParts can't contain '.' or '..' segments, '?', '#' or encoded slashes", "code": "storage/invalid-body", "param": "file.options.pathParts" }
    ```

    In an aspect-ratio mode, a variant's computed side would be outside 1–10000 px. Checked once the image is read, before anything is processed or stored. `param` names the option:

    ```json
    { "error": "`file.options.widths.s` gives a height of 0 px at the 3:1 aspect ratio. Each side of a variant must be 1–10000 px.", "code": "storage/invalid-body", "param": "file.options.widths.s" }
    ```

    In `aspect-ratio-height-based` it names a `heights` option and gives a width. In `multi-aspect-ratio` it names a `sizes` option, and the ratio is the one in `aspectRatios` closest to this image: "`file.options.sizes.s` gives a height of 0 px at the 3:1 aspect ratio, the one in \`aspectRatios\` closest to this image. Each side of a variant must be 1–10000 px."

    More than 30 entries in `dimensions`, `widths`, `heights` or `sizes`. `param` names the option:

    ```json
    { "error": "file.options.sizes: An image can have at most 30 variants.", "code": "storage/invalid-body", "param": "file.options.sizes" }
    ```

    Any other value outside its rules (a size outside 1–10000, an `originalMaxSize` outside 50–10000, a `fit` the mode doesn't take, `metadata` that isn't a JSON object) gets the same code, with `param` naming the value.
  </Accordion>
  <Accordion title="No File — 400 Bad Request">
    ```json
    { "error": "No file provided", "code": "storage/no-file", "param": "file" }
    ```
  </Accordion>
  <Accordion title="File Too Large — 413">
    ```json
    { "error": "`file` is over the 50 MB per-file limit.", "code": "storage/file-too-large", "param": "file" }
    ```
  </Accordion>
  <Accordion title="Invalid Image — 422">
    The file can't be read as a JPEG, PNG or WebP image:

    ```json
    { "error": "Invalid image file", "code": "storage/invalid-image", "param": "file" }
    ```

    The image is over 10000 px on a side. `error` gives its size:

    ```json
    { "error": "The image is 12000 x 800 px; an image can be at most 10000 px on each side.", "code": "storage/invalid-image", "param": "file" }
    ```
  </Accordion>
  <Accordion title="Missing Image Options — 400">
    The request sent no `file.options`. Checked after the image itself is checked, and nothing is stored.

    ```json
    {
      "error": "Image options are required when uploading an image. Must include mode property.",
      "code": "storage/missing-image-options",
      "param": "file.options"
    }
    ```
  </Accordion>
  <Accordion title="User Not Found — 404">
    Returned when a service key names an `actingUserId` that isn't a user in this project. Checked before the upload.

    ```json
    { "error": "No user with this actingUserId exists in this project.", "code": "storage/user-not-found" }
    ```
  </Accordion>
  <Accordion title="Upload Refused — 400 / 413">
    A file was refused as the body was read: `storage/unsupported-file-type` or `storage/unexpected-file-field`, with `param` naming the field when there is one. A body over 250 MB gets `413 request/body-too-large`; one that can't be read at all gets `request/invalid-multipart` or `request/field-too-large`. See [Upload errors](/v8/api-reference/getting-started#upload-errors).
  </Accordion>
  <Accordion title="Server Error — 500">
    ```json
    { "error": "Failed to upload image", "code": "storage/server-error" }
    ```
  </Accordion>
</AccordionGroup>
