---
title: "Create Space"
api: "POST /v8/:projectId/spaces"
description: "Create a new community space"
---

Creates a new space. Its creator — the signed-in user, or the user a service key names in `actingUserId` — is automatically added as an admin. A space always has a creator, so a service key must name one. Supports optional avatar and banner image upload via multipart form data.

**Authentication required.** A request with no credentials returns `401`.

## Body Parameters

<ParamField body="name" type="string">
  Display name for the space. Must be 3–100 characters.
</ParamField>

<ParamField body="slug" type="string">
  Optional URL slug. Must be unique per project. Supports Unicode letters, numbers, hyphens, and underscores.
</ParamField>

<ParamField body="description" type="string">
  Optional description. Up to 1,000 characters.
</ParamField>

<ParamField body="readingPermission" type="string">
  Who can read content: `"anyone"` or `"members"`. Defaults to `"anyone"`.
</ParamField>

<ParamField body="postingPermission" type="string">
  Who can post entities: `"anyone"`, `"members"` (active members), or `"team"` (the space's active admins and moderators). Defaults to `"members"`. Any other value, `"admins"` included, is refused with `400 space/invalid-body`.
</ParamField>

<ParamField body="visibility" type="string">
  Who can find and see the space: `"public"`, `"unlisted"`, or `"private"`. Defaults to `"public"`. Independent of `readingPermission`, which governs content. `"unlisted"` keeps the space out of the directory and search, and out of sub-space lists for non-members, but reachable by id, short id or slug; `"private"` makes it seen only by its active members (everyone else gets `404`), and it can't be joined: members are [added](/v8/api-reference/spaces/membership/add-member) by its moderators and admins. See [Space visibility](/v8/data-models/space#visibility).
</ParamField>

<ParamField body="requireJoinApproval" type="boolean">
  Whether new joins require approval. Defaults to `true`.
</ParamField>

<ParamField body="metadata" type="object">
  Optional arbitrary key-value data. Up to 1 MB.
</ParamField>

<ParamField body="parentSpaceId" type="string | null">
  Optional UUID of a parent space. The caller must be an admin of the parent space; when a service key creates the space for a user (`actingUserId`), that user must be. For a top-level space, send `null` or leave it out; the string `"none"` is refused with `400 space/unsupported-param` (see [Saying "no value"](/v8/authentication#saying-no-value)).
</ParamField>

<ParamField body="avatarFile" type="file">
  Optional avatar image. Multipart form field. Requires `avatarFile.options` when provided.
</ParamField>

<ParamField body="bannerFile" type="file">
  Optional banner image. Multipart form field. Requires `bannerFile.options` when provided.
</ParamField>

<ParamField body="actingUserId" type="string">
  Service key only, and required with one: the user this request acts as, who creates the space and becomes its admin, held to their own permissions. Leaving it out returns `400 space/missing-user-id`. A user token always acts as its own user and must not send it (`400 space/acting-user-not-allowed`).
</ParamField>

## Response

Returns the created [Space](/v8/data-models/space) object with `membersCount`, `childSpacesCount`, optional file associations, and `memberPermissions`: what the creator may do in the new space, as a [SpaceMemberPermissions](/v8/data-models/space#spacememberpermissions) object.

## Error Responses

<AccordionGroup>
  <Accordion title="Not signed in — 401 / 403">
    Returned with no JSON body: `401` when no `Authorization` header is sent, `403` when the access token is invalid or expired. Checked before any uploaded file is read, so a request with no credentials gets `401` rather than a body or acting-user error.
  </Accordion>
  <Accordion title="Missing User ID — 400">
    A service key sent no `actingUserId`. A space needs a creator.
    ```json
    { "error": "A service key must send actingUserId: the user this request acts as.", "code": "space/missing-user-id" }
    ```
  </Accordion>
  <Accordion title="Acting User Not Allowed — 400">
    A user token sent `actingUserId`, even naming its own user. Only a service key names the user it acts as; a user token always acts as its own user.
    ```json
    { "error": "actingUserId is only accepted with a service key. A user's own token always acts as that user.", "code": "space/acting-user-not-allowed" }
    ```
  </Accordion>
  <Accordion title="Wrong Location — 400">
    `actingUserId` was sent in the query string. On this endpoint every field, `actingUserId` included, goes in the request body.
    ```json
    { "error": "`actingUserId` goes in the request body on this endpoint.", "code": "space/wrong-location", "param": "actingUserId" }
    ```
  </Accordion>
  <Accordion title="User Not Found — 404">
    Returned when a service key names an `actingUserId` that isn't a user in this project.
    ```json
    { "error": "No user with this actingUserId exists in this project.", "code": "space/user-not-found" }
    ```
  </Accordion>
  <Accordion title="Unsupported Parameter — 400">
    The request sent `userId`. On this route the user a service key acts as is `actingUserId`.

    With a service key:

    ```json
    {
      "error": "`userId` was renamed to `actingUserId`: send the user this service key acts as in `actingUserId`.",
      "code": "space/unsupported-param",
      "param": "userId"
    }
    ```

    With a user token:

    ```json
    {
      "error": "`userId` isn't accepted here: a user's own token always acts as that user.",
      "code": "space/unsupported-param",
      "param": "userId"
    }
    ```
  </Accordion>
  <Accordion title="Slug Taken — 409">
    ```json
    { "error": "A space with this slug already exists.", "code": "space/slug-taken", "param": "slug" }
    ```
  </Accordion>
  <Accordion title="Parent Not Found — 404">
    The parent space doesn't exist, or the caller can't see it (see [Space visibility](/v8/data-models/space#visibility)). Checked before the parent-admin check.
    ```json
    { "error": "Parent space not found.", "code": "space/parent-not-found" }
    ```
  </Accordion>
  <Accordion title="Parent Admin Required — 403">
    ```json
    { "error": "Only admins of the parent space can create child spaces.", "code": "space/parent-admin-required" }
    ```
  </Accordion>
  <Accordion title="Banned — 403">
    The creator was banned in the parent space (or above) while the child space was being created.
    ```json
    { "error": "You are banned from a parent of this space.", "code": "space/banned" }
    ```
  </Accordion>
  <Accordion title="Max Depth Exceeded — 400">
    ```json
    { "error": "Maximum nesting depth (10) exceeded.", "code": "space/max-depth-exceeded" }
    ```
  </Accordion>
  <Accordion title="Bundle Not Installed — 403">
    Returned when an avatar or banner is uploaded on a project without the files-images bundle. `missingTables` lists the tables that aren't installed and `bundleId` the bundle to install. While the bundle is still being installed, the response is `503 database/tables-provisioning` instead. See [Bundles](/v8/bundles).
    ```json
    { "error": "Space avatar/banner uploads require the files-images bundle. Enable it for this project.", "code": "database/tables-not-available", "missingTables": ["Files", "Images"], "bundleId": "files-images", "dashboardUrl": "https://…/<projectId>/database" }
    ```
  </Accordion>
  <Accordion title="Image Too Large — 413">
    ```json
    { "error": "Avatar image exceeds 50MB limit.", "code": "space/file-too-large", "param": "avatarFile" }
    ```
    Also returned with `"Banner image exceeds 50MB limit."` and `param: "bannerFile"` for the banner.
  </Accordion>
  <Accordion title="Invalid Image — 422">
    ```json
    { "error": "Avatar file is not a valid image: ...", "code": "space/invalid-image", "param": "avatarFile" }
    ```
    The file can't be read as an image. Also returned for the banner, with `param: "bannerFile"`.
  </Accordion>
  <Accordion title="Missing Image Options — 400">
    ```json
    { "error": "Image options are required when uploading an avatar. Must include mode property.", "code": "space/missing-image-options", "param": "avatarFile.options" }
    ```
    `avatarFile` or `bannerFile` was uploaded without its `.options` field. `param` is `avatarFile.options` or `bannerFile.options`.
  </Accordion>
  <Accordion title="Invalid Image Options — 400">
    ```json
    { "error": "Invalid JSON in avatarFile.options field.", "code": "space/invalid-body", "param": "avatarFile.options" }
    ```
    The `.options` field isn't valid JSON. `param` names the field: `avatarFile.options` or `bannerFile.options`.
  </Accordion>
  <Accordion title="Upload Refused — 400 / 413">
    A file was refused as the body was read: `space/unsupported-file-type` or `space/unexpected-file-field`, with `param` naming the field when there is one. A body that can't be read at all gets `request/invalid-multipart` or `request/field-too-large` instead. See [Upload errors](/v8/api-reference/getting-started#upload-errors).
  </Accordion>
</AccordionGroup>
