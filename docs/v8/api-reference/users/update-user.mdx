---
title: "Update User"
api: "PATCH /v8/:projectId/users/:userId"
description: "Update a user's profile fields, including avatar and banner images"
---

Updates one or more profile fields for the specified user. A user edits only their own profile. A service key edits a user by acting as that user: it must send `actingUserId` naming the user in the path, and the request then behaves exactly as that user's own token would.

Uploads a new avatar or banner with `multipart/form-data`: the image is processed into the sizes you ask for, and the file it replaces is deleted once the update is saved. `removeFileIds` removes the avatar or banner without a replacement.

<Note>
  Send `application/json` for text-only updates. Use `multipart/form-data`
  when uploading image files.
</Note>

## Authentication

Requires a user access token whose user matches `:userId`, or a service key that sends `actingUserId` set to `:userId`.

## Path Parameters

<ParamField path="userId" type="string" required>
  The Sublay user ID (UUID) to update.
</ParamField>

## Body Parameters

<ParamField body="actingUserId" type="string">
  Service key only, and required with one: the user this request acts as. It must be the user in the path (`:userId`). Not an update field. A user token always acts as its own user and must not send it (`400 user/acting-user-not-allowed`). With `multipart/form-data`, send it as a form field.
</ParamField>

All other fields are optional. Only the fields provided are updated.

<ParamField body="name" type="string">
  Display name.
</ParamField>

<ParamField body="username" type="string">
  New username. Automatically lowercased and sanitized. Returns
  `409 user/username-taken` (with `param: "username"`) if another user already
  holds it.
</ParamField>

<ParamField body="avatar" type="string">
  URL of the user's avatar image, stored as given. Separate from `avatarFile`, which uploads an image file and sets `avatarFileId`.
</ParamField>

<ParamField body="bio" type="string">
  Short bio text.
</ParamField>

<ParamField body="birthdate" type="string">
  ISO 8601 datetime string for the user's date of birth (e.g. `"1990-06-15T00:00:00.000Z"`).
</ParamField>

<ParamField body="location" type="object">
  Geographic location stored as a PostGIS point.
  <Expandable title="properties">
    <ParamField body="latitude" type="number" required>
      Latitude between -90 and 90.
    </ParamField>
    <ParamField body="longitude" type="number" required>
      Longitude between -180 and 180.
    </ParamField>
  </Expandable>
</ParamField>

<ParamField body="metadata" type="object">
  Public custom key-value data. Replaces the existing value.
</ParamField>

<ParamField body="secureMetadata" type="object">
  Custom key-value data. No API response returns it, to this user or anyone else; your backend receives it in webhooks. The user can write it themselves, so don't store anything your app needs to trust here. Replaces the
  existing value.
</ParamField>

<ParamField body="avatarFile" type="file">
  Avatar image file (multipart), replacing the current one. Maximum 50 MB. Must be a valid image.
  Requires `avatarFile.options` to be present in the same request.
</ParamField>

<ParamField body="avatarFile.options" type="string">
  Stringified JSON describing how to process the avatar. Must include a `mode` field; see [Upload Image](/v8/api-reference/storage/upload-image) for the modes and optional fields. Not used when no `avatarFile` is sent, but still validated: invalid JSON or options get a `400`.
</ParamField>

<ParamField body="bannerFile" type="file">
  Banner image file (multipart), replacing the current one. Maximum 50 MB. Must be a valid image.
  Requires `bannerFile.options` to be present in the same request.
</ParamField>

<ParamField body="bannerFile.options" type="string">
  Stringified JSON describing how to process the banner, as `avatarFile.options`. Not used when no `bannerFile` is sent, but still validated: invalid JSON or options get a `400`.
</ParamField>

<ParamField body="removeFileIds" type="string[]">
  Files to remove from the user: their `avatarFileId` and/or `bannerFileId`, nothing else. Removing one clears that image (the pointer becomes `null` and the file is deleted). Works alone or with uploads in the same request; uploading a new avatar while listing the old one is a plain replace. On a multipart request, send it as a JSON string (`'["<fileId>"]'`). Any other id refuses the whole request with `400 user/invalid-remove-file-ids`.
</ParamField>

## Response

On success, returns HTTP `200` with the updated user's authenticated profile:

<ResponseField name="id" type="string">
  Unique user ID (UUID).
</ResponseField>

<ResponseField name="foreignId" type="string | null">
  External identifier from your system.
</ResponseField>

<ResponseField name="role" type="string">
  User role (e.g., `"visitor"`).
</ResponseField>

<ResponseField name="email" type="string | null">
  User's email address.
</ResponseField>

<ResponseField name="name" type="string | null">
  Updated display name.
</ResponseField>

<ResponseField name="username" type="string | null">
  Updated username.
</ResponseField>

<ResponseField name="avatar" type="string | null">
  Avatar URL.
</ResponseField>

<ResponseField name="bio" type="string | null">
  Bio text.
</ResponseField>

<ResponseField name="metadata" type="object | null">
  Public custom key-value data.
</ResponseField>

<ResponseField name="reputation" type="number | null">
  Reputation score.
</ResponseField>

<ResponseField name="isVerified" type="boolean | null">
  Whether the user's email has been verified.
</ResponseField>

<ResponseField name="isActive" type="boolean | null">
  Whether the user account is active.
</ResponseField>

<ResponseField name="lastActive" type="string | null">
  ISO timestamp of the user's last activity.
</ResponseField>

<ResponseField name="suspensions" type="array">
  Active suspensions on the account.
</ResponseField>

<ResponseField name="avatarFile" type="object | null">
  Processed avatar image with variants.
</ResponseField>

<ResponseField name="bannerFile" type="object | null">
  Processed banner image with variants.
</ResponseField>

<ResponseField name="authMethods" type="string[]">
  Active auth methods (e.g., `["password", "google"]`).
</ResponseField>

<ResponseField name="createdAt" type="string">
  ISO timestamp of account creation.
</ResponseField>

<Note>
  When `name`, `username`, or `bio` changes, the user's semantic search
  embedding is automatically updated asynchronously.
</Note>

## Error Responses

<AccordionGroup>
  <Accordion title="Not signed in — 401 / 403">
    Returned with no JSON body: `401` when no `Authorization` header is sent, `403` when the access token is invalid or expired. Checked before any uploaded file is read, so a request with no credentials gets `401` rather than a body or acting-user error. A valid token for a different user gets `403 user/forbidden` instead (Signed In as Another User, below).
  </Accordion>
  <Accordion title="Signed In as Another User — 403">
    A valid user token, signed in as a user other than `:userId`, tried to update that user. Returned with a JSON body, unlike the invalid-token `403` above.

    ```json
    {
      "error": "Not authorized to update this user.",
      "code": "user/forbidden"
    }
    ```
  </Accordion>
  <Accordion title="User Not Found — 404">
    The user in the path no longer exists, for example a user token that outlived its user.

    ```json
    {
      "error": "User not found",
      "code": "user/not-found"
    }
    ```
  </Accordion>
  <Accordion title="File Too Large — 413">
    The image is over 50 MB. `param` names its field: `avatarFile` or `bannerFile`.
    ```json
    { "error": "`avatarFile` is over the 50 MB per-file limit.", "code": "user/file-too-large", "param": "avatarFile" }
    ```
  </Accordion>
  <Accordion title="Invalid Image — 422">
    ```json
    {
      "error": "Avatar file is not a valid image.",
      "code": "user/invalid-image",
      "param": "avatarFile"
    }
    ```
    The file can't be read as an image. Also returned for the banner, with `"Banner file is not a valid image."` and `param: "bannerFile"`.
    An image over 10000 px on a side gets the same code. `error` gives its size:
    ```json
    { "error": "Avatar file is 12000 x 800 px; an image can be at most 10000 px on each side.", "code": "user/invalid-image", "param": "avatarFile" }
    ```
    For `bannerFile`:
    ```json
    { "error": "Banner file is 12000 x 800 px; an image can be at most 10000 px on each side.", "code": "user/invalid-image", "param": "bannerFile" }
    ```
  </Accordion>
  <Accordion title="Missing Image Options — 400">
    ```json
    {
      "error": "Image options are required when uploading an avatar. Must include mode property.",
      "code": "user/missing-image-options",
      "param": "avatarFile.options"
    }
    ```
    `avatarFile` or `bannerFile` was uploaded without its `.options` field. `param` is `avatarFile.options` or `bannerFile.options`.
  </Accordion>
  <Accordion title="Invalid Image Options — 400">
    ```json
    {
      "error": "Invalid JSON in avatarFile.options field.",
      "code": "user/invalid-body",
      "param": "avatarFile.options"
    }
    ```
    The `.options` field isn't valid JSON. `param` names the field: `avatarFile.options` or `bannerFile.options`.
    `avatarFile.options` without `mode`, or with a `mode` that isn't one of the five (other options fields the same way, named in `error` and `param`):
    ```json
    { "error": "avatarFile.options.mode: Invalid input", "code": "user/invalid-body", "param": "avatarFile.options.mode" }
    ```
    In an aspect-ratio mode, a variant's computed side would be outside 1–10000 px. Checked once the image is read, before anything is stored. `param` names the option:
    ```json
    { "error": "`avatarFile.options.widths.s` gives a height of 0 px at the 3:1 aspect ratio. Each side of a variant must be 1–10000 px.", "code": "user/invalid-body", "param": "avatarFile.options.widths.s" }
    ```
    In `aspect-ratio-height-based` it names a `heights` option and gives a width. In `multi-aspect-ratio` it names a `sizes` option, and the ratio is the one in `aspectRatios` closest to the image, so the text reads "… at the 3:1 aspect ratio, the one in `aspectRatios` closest to this image. Each side of a variant must be 1–10000 px."
  </Accordion>
  <Accordion title="Username Taken — 409">
    Another user already holds the `username` sent. Nothing is changed, and any file uploaded with the request is removed.

    ```json
    {
      "error": "A user with this username already exists in this project",
      "code": "user/username-taken",
      "param": "username"
    }
    ```
  </Accordion>
  <Accordion title="Rejected by Validation Webhook — 400">
    ```json
    {
      "error": "User validation failed",
      "code": "user/webhook-validation-failed"
    }
    ```
    Returned when your `user.updated` [validation webhook](/v8/webhooks) rejects the update. `error` carries the `message` your webhook returned (`User validation failed` when it returned none). Nothing is changed.
  </Accordion>
  <Accordion title="Invalid Params — 400">
    ```json
    {
      "error": "Invalid user id: expected a UUID.",
      "code": "user/invalid-params",
      "param": "userId"
    }
    ```
  </Accordion>
  <Accordion title="Missing User ID — 400">
    A service key sent no `actingUserId`.

    ```json
    { "error": "A service key must send actingUserId: the user this request acts as.", "code": "user/missing-user-id" }
    ```
  </Accordion>
  <Accordion title="Not the User in the Path — 403">
    A service key sent an `actingUserId` other than `:userId`.

    ```json
    {
      "error": "actingUserId must be the user in the path: a service key updates a user by acting as that user.",
      "code": "user/forbidden"
    }
    ```
  </Accordion>
  <Accordion title="Acting User Not Allowed — 400">
    A user token sent `actingUserId`, even naming its own user. Only a service key names the user it acts as; a user token always acts as its own user.

    ```json
    {
      "error": "actingUserId is only accepted with a service key. A user's own token always acts as that user.",
      "code": "user/acting-user-not-allowed"
    }
    ```
  </Accordion>
  <Accordion title="Acting User Not Found — 404">
    Returned when a service key names an `actingUserId` that isn't a user in this project, so also when it names a `:userId` that doesn't exist.

    ```json
    { "error": "No user with this actingUserId exists in this project.", "code": "user/user-not-found" }
    ```
  </Accordion>
  <Accordion title="Invalid File Ids — 400">
    `removeFileIds` names a file that isn't this user's current avatar or banner. `invalidIds` lists those ids. Checked before anything is uploaded, so nothing is stored or removed.
    ```json
    { "error": "`removeFileIds` may name only this user's own avatar and banner files (their `avatarFileId` and `bannerFileId`).", "code": "user/invalid-remove-file-ids", "param": "removeFileIds", "invalidIds": ["9b2f…"] }
    ```
    A `removeFileIds` that isn't an array of file ids gets `400 user/invalid-body` instead.
  </Accordion>
  <Accordion title="Bundle Not Installed — 403">
    Returned when an avatar or banner is uploaded on a project without the files-images bundle. `missingTables` lists the tables that aren't installed and `bundleId` the bundle to install. While the bundle is still being installed, the response is `503 database/tables-provisioning` instead. See [Bundles](/v8/bundles).
    ```json
    { "error": "Avatar and banner uploads require the files-images bundle, which is not installed for this project.", "code": "database/tables-not-available", "missingTables": ["Files", "Images"], "bundleId": "files-images", "dashboardUrl": "https://…/<projectId>/database" }
    ```
  </Accordion>
  <Accordion title="Upload Refused — 400 / 413">
    A file was refused as the body was read: `user/unsupported-file-type` or `user/unexpected-file-field` (a file in another field, or a second file in `avatarFile` or `bannerFile`), with `param` naming the field when there is one. A body over 250 MB gets `413 request/body-too-large`; one that can't be read at all gets `request/invalid-multipart` or `request/field-too-large`. See [Upload errors](/v8/api-reference/getting-started#upload-errors).
  </Accordion>
</AccordionGroup>
