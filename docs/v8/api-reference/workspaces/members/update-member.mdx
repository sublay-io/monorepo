---
title: "Update Member"
api: "PATCH /v8/:projectId/workspaces/:workspaceId/members/:userId"
description: "Edit a member's access or profile fields, with two capability tiers"
---

Edits a member, with **two capability tiers by field sensitivity**:

- **Powerful fields** (`capabilities`, `permissions`, and rank — as either `rank` or `relativeRank`) require **`edit-member-access`**, plus the [rank rule](/v8/data-models/workspace-member#rank-semantics) and the [no-escalation](/v8/data-models/workspace-member#no-privilege-escalation) guard.
- **Cosmetic fields** (`title`, `metadata`) require only **`edit-member-profile`**.

This route edits **another** member. A member edits their **own `title`**, with no capability, through [`PATCH /workspaces/:workspaceId/members/me`](/v8/api-reference/workspaces/members/update-my-membership).

The workspace's **owner** is never a target here, for anyone, ancestor owners included: nobody outranks the owner, and the owner's `title` and `metadata` are theirs alone to set, through `PATCH /workspaces/:workspaceId/members/me`. Naming the owner as `:userId` gets `404 workspace/not-found`, whether or not they have set a title or metadata.

Rank moves in **either coordinate** — `rank` (absolute) or `relativeRank` (an offset from the actor) — and they are **mutually exclusive**; sending both is a `400`. Omitting **both** means **rank unchanged**: unlike [Create Invite](/v8/api-reference/workspaces/invitations/create-invite), this endpoint has no value default, so editing someone's capabilities never moves them on the ladder. See [choosing a rank](/v8/sdk/workspaces/overview#choosing-a-rank).

**Grant vs strip asymmetry:** you may only *add* a capability/permission you hold on the target node (resolved set, including via reach); *stripping* is governed by **rank alone**. **Cross-node rank is not compared** — the rank guard runs only when actor and target share a member row on the same workspace.

## Path Parameters

<ParamField path="workspaceId" type="string" required>
  The workspace UUID.
</ParamField>

<ParamField path="userId" type="string" required>
  The target member's user id. Must not be the acting user (`400 workspace/own-member-id`).
</ParamField>

## Body Parameters

All optional; the controller enforces which tier each touched field belongs to. At least one must be provided.

<ParamField body="capabilities" type="string[]">
  New capability set (powerful — `edit-member-access`).
</ParamField>

<ParamField body="permissions" type="string[]">
  New permission set (powerful — `edit-member-access`).
</ParamField>

<ParamField body="rank" type="number">
  New **absolute** rank, `0` – `2147483647` (powerful — `edit-member-access` + rank rules). Mutually exclusive with `relativeRank`. Omitting both leaves rank unchanged.
</ParamField>

<ParamField body="relativeRank" type="number">
  New rank expressed as an **offset from the acting user**: `1` = one rung below me. Must be `1` – `2147483647` — `0` (a peer) and negatives are a `400`. The **resolved** value is bounded too, so an in-range offset that overflows once anchored is a `400`, not a `500`. Mutually exclusive with `rank`, and with **no default**: omitting both leaves rank unchanged.

  Anchored on the actor's **own rank if they hold a member row on this workspace**, apex (one step above rank 0) otherwise — the anchor turns on the row, not on what kind of actor they are. Resolved to an absolute number at write time and stored absolute; it is a **snapshot** and does not follow the actor's own rank afterwards.

  Because an in-ladder anchor is `>= 0` and the offset is `>= 1`, a direct-member actor can never reach rank `0` this way — and neither can they by naming absolute `rank: 0`, which the assign rule below refuses for exactly the same reason (nothing is strictly below `0`). There is no separate rank-0 guard: rank `0` is effectively owner-only because the owner skips the rank block, not because a check names them. An actor with **no** member row here — an ancestor owner, or a cross-node reach holder — also skips it.

  A service key is **not** on that list. `actingUserId` is required, so a key is always *somebody*, and it faces exactly the floors that somebody faces. A key that names nobody gets a `400 workspace/missing-user-id`.
</ParamField>

<ParamField body="title" type="string">
  New cosmetic title (`edit-member-profile`). Nullable. Your own title is edited with [`PATCH /workspaces/:workspaceId/members/me`](/v8/api-reference/workspaces/members/update-my-membership).
</ParamField>

<ParamField body="metadata" type="object">
  New cosmetic metadata (`edit-member-profile`).
</ParamField>

<ParamField body="actingUserId" type="string" required>
  Service keys only — the **acting** user (sent in the body; the path `:userId` is the target). **Required for a key:** a key that names nobody is refused with `400 workspace/missing-user-id`. Every check below — the two capability tiers, the rank guard, the assign rule and no-escalation — runs against the named user. Act as the **owner** for an unrestricted edit.

  A user token always acts as its own user and must not send it (`400 workspace/acting-user-not-allowed`). See [Acting on behalf of a user](/v8/sdk/workspaces/overview#acting-on-behalf-of-a-user).
</ParamField>

## Response

Returns the updated [WorkspaceMember](/v8/data-models/workspace-member) object.

## Error Responses

<AccordionGroup>
  <Accordion title="Own Member Id — 400">
    ```json
    { "error": "`PATCH /workspaces/:workspaceId/members/:userId` acts on another member, not on yourself. Your own membership is at `/workspaces/:workspaceId/members/me`: GET to check it, PATCH to edit your title, DELETE to leave.", "code": "workspace/own-member-id" }
    ```
    `userId` is the acting user (the token's user, or the user named by `actingUserId`). This route acts on another member. Your own membership is [`GET /workspaces/:workspaceId/members/me`](/v8/api-reference/workspaces/members/fetch-my-membership) to read it, [`PATCH /workspaces/:workspaceId/members/me`](/v8/api-reference/workspaces/members/update-my-membership) to edit your title, and [`DELETE /workspaces/:workspaceId/members/me`](/v8/api-reference/workspaces/members/leave-workspace) to leave.
  </Accordion>
  <Accordion title="Unauthorized — 403">
    One message per tier, depending on which fields the request touched. Powerful fields (`capabilities`, `permissions`, `rank`, `relativeRank`):

    ```json
    { "error": "The 'edit-member-access' capability is required to edit access fields.", "code": "workspace/unauthorized" }
    ```

    Cosmetic fields (`title`, `metadata`):

    ```json
    { "error": "The 'edit-member-profile' capability is required to edit profile fields.", "code": "workspace/unauthorized" }
    ```
  </Accordion>
  <Accordion title="Insufficient Rank — 403">
    Two distinct messages share this code. The **act** rule, on the target:

    ```json
    { "error": "You may only manage members ranked strictly below you.", "code": "workspace/insufficient-rank" }
    ```

    …and the **assign** rule, on the rank you asked for — checked against the resolved absolute value, so `rank` and `relativeRank` face it identically. This is also what refuses `rank: 0` to anyone holding a row on this workspace:

    ```json
    { "error": "You may only set ranks strictly below your own.", "code": "workspace/insufficient-rank" }
    ```
  </Accordion>
  <Accordion title="Rank out of range — 400">
    ```json
    { "error": "The resolved rank (2147483648) is out of range — ranks are integers from 0 to 2147483647.", "code": "workspace/invalid-body" }
    ```
    Checked after the offset is resolved. Out-of-range `rank` / `relativeRank` input is refused earlier by the schema, with the same code.
  </Accordion>
  <Accordion title="Both rank coordinates supplied — 400">
    ```json
    { "error": "relativeRank: Provide either rank (absolute) or relativeRank (offset from you), not both", "code": "workspace/invalid-body" }
    ```
    A schema rejection, so the message is prefixed with the field it was reported against.
  </Accordion>
  <Accordion title="No Escalation — 403">
    The offending values are named. Capabilities:

    ```json
    { "error": "Cannot grant capabilities you do not hold on this workspace: edit-member-access.", "code": "workspace/no-escalation" }
    ```

    …and permissions:

    ```json
    { "error": "Cannot grant permissions you do not hold on this workspace: deploy.", "code": "workspace/no-escalation" }
    ```

    Only **added** values are checked — removing a capability or permission is governed by rank alone.
  </Accordion>
  <Accordion title="Missing Acting User — 400">
    ```json
    { "error": "A service key must send actingUserId: the user this request acts as.", "code": "workspace/missing-user-id" }
    ```
    A service key called this route without naming an `actingUserId`. Every gate on this route is measured against the editor's own standing, so the edit must be performed *as* somebody — act as the owner for an unrestricted edit.
  </Accordion>
  <Accordion title="Acting User Not Allowed — 400">
    ```json
    { "error": "actingUserId is only accepted with a service key. A user's own token always acts as that user.", "code": "workspace/acting-user-not-allowed" }
    ```
    A user token sent `actingUserId`, even naming its own user. Only a service key names the user it acts as; a user token always acts as its own user.
  </Accordion>
  <Accordion title="Wrong Location — 400">
    ```json
    { "error": "`actingUserId` goes in the request body on this endpoint.", "code": "workspace/wrong-location", "param": "actingUserId" }
    ```
    A field this endpoint reads from the body was sent in the query string. `actingUserId` and every body field go in the JSON body.
  </Accordion>
  <Accordion title="User Not Found — 404">
    ```json
    { "error": "No user with this actingUserId exists in this project.", "code": "workspace/user-not-found" }
    ```
    Returned when a service key names an `actingUserId` that isn't a user in this project.
  </Accordion>
  <Accordion title="Invalid Path Parameter — 400">
    ```json
    { "error": "Invalid workspace id: expected a UUID.", "code": "workspace/invalid-params" }
    ```
    Every path id on the workspaces bundle is checked for UUID shape before the route runs, so a malformed one is a plain `400` rather than a `500` from the database.
  </Accordion>
  <Accordion title="Not Found — 404">
    The workspace doesn't exist:
    ```json
    { "error": "Workspace not found.", "code": "workspace/not-found" }
    ```
    The target user isn't a direct member of the workspace, including when they were removed (or the workspace was deleted) while this request was being handled. The workspace's owner always gets this, since the owner is never a member:
    ```json
    { "error": "The target user is not a direct member of this workspace.", "code": "workspace/not-found" }
    ```
    A successful response always carries the member.
  </Accordion>
</AccordionGroup>
