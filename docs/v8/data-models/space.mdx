---
title: "Space"
description: "The shape of a Space object returned by the Spaces API and SDK"
---

A Space is a community container — a named area where users can post entities, discuss in threads, and interact under configurable membership and permission rules. Spaces support hierarchical nesting, customizable read/post permissions, and avatar and banner images.

The API returns three space shapes depending on context:

- **`Space`** — the standard shape, returned when fetching a list of spaces.
- **`SpaceDetailed`** — returned when fetching a single space by ID, shortId, or slug. A superset of `Space` with added permission and hierarchy context.
- **`SpacePreview`** — a minimal snapshot, never returned as a standalone response. Only appears embedded inside `SpaceDetailed` as the shape of `parentSpace` and each item in `childSpaces[]`.

## Space

| Property | Type | Description |
|----------|------|-------------|
| `id` | `string` | Unique space identifier (UUID). |
| `shortId` | `string` | Short human-readable ID for the space (URL-safe, generated automatically). |
| `projectId` | `string` | The project this space belongs to. |
| `slug` | `string \| null` | Optional URL-friendly slug. Unique per project when set. |
| `name` | `string` | Display name of the space (3–100 characters). |
| `description` | `string \| null` | Optional description (up to 1,000 characters). |
| `userId` | `string` | ID of the space creator/owner. |
| `avatarFileId` | `string \| null` | ID of the space's avatar image file. |
| `avatarFile` | `File \| undefined` | Populated avatar file object. Only present when `include: "files"` is requested. |
| `bannerFileId` | `string \| null` | ID of the space's banner image file. |
| `bannerFile` | `File \| undefined` | Populated banner file object. Only present when `include: "files"` is requested. |
| `readingPermission` | `"anyone" \| "members"` | Who can read content in the space: `"anyone"` who can read the space above it, or only its active members (`"members"`). Inherited by sub-spaces; see [Who can read content](#who-can-read-content). |
| `postingPermission` | `"anyone" \| "members" \| "team"` | Who can post entities in the space: `"anyone"`, its active members (`"members"`), or only its active admins and moderators (`"team"`). Commenting and reacting don't follow it; see [Who can post and take part](#who-can-post-and-take-part). |
| `visibility` | `"public" \| "unlisted" \| "private"` | Who can find and see the space — independent of `readingPermission`, which controls who can read the content. `public` (the default) is listed in the directory and search; `unlisted` isn't listed but is reachable by id, short id or slug; `private` is seen only by its active members, and answers `404` to everyone else. See [Visibility](#visibility) below. |
| `nsfw` | `boolean` | The space's **own** NSFW flag. `false` by default. Set by space admins on [create](/v8/hooks/spaces/use-create-space)/[update](/v8/hooks/spaces/use-update-space) or by a project admin from the dashboard. See [NSFW flagging](#nsfw-flagging). |
| `nsfwEffective` | `boolean` | **Denormalized, read-only.** `true` when this space's own `nsfw` is `true` **or** any ancestor space is NSFW. Maintained top-down on write and cascaded to descendants. This is the value the space `nsfwFilter` keys off, and it feeds each entity's live `nsfwEffective`. See [NSFW flagging](#nsfw-flagging). |
| `requireJoinApproval` | `boolean` | Whether joining requires moderator/admin approval. When `true`, new joins enter `pending` status. |
| `parentSpaceId` | `string \| null` | ID of the parent space, if this is a sub-space. |
| `depth` | `number` | Nesting depth (0 for root spaces, incremented for each sub-level). Maximum depth is 10. |
| `metadata` | `Record<string, any>` | Arbitrary key-value data attached to the space. Up to 1 MB. |
| `isMember` | `boolean \| undefined` | Whether the viewer is a member of this space. Only present when there is a viewer: the signed-in user, or the user a service key names in `actingUserId`. |
| `membersCount` | `number` | Computed count of active members. |
| `childSpacesCount` | `number` | Computed count of the direct sub-spaces the viewer can see that are `public` or that the viewer is an active member of — the same sub-spaces `childSpaces` and `parentSpaceId=<id>` list (see [Visibility](#visibility)). |
| `createdAt` | `Date` | Timestamp when the space was created. |
| `updatedAt` | `Date` | Timestamp when the space was last updated. |

## SpaceDetailed

Returned when fetching a single space by ID, shortId, or slug. Includes all `Space` fields plus the following:

| Property | Type | Description |
|----------|------|-------------|
| `memberPermissions` | `SpaceMemberPermissions \| null` | The viewer's resolved permissions in this space (the signed-in user, or the user a service key names in `actingUserId`). `null` if the user has no membership in this space. A pending, banned or rejected user gets it with `isMember: false` and their `status`. |
| `parentSpace` | `SpacePreview \| null` | Preview of the parent space. `null` for root-level spaces, and when the viewer can't see the parent (`parentSpaceId` still names it). |
| `childSpaces` | `SpacePreview[]` | Preview of up to 10 immediate child spaces, A–Z by name: the direct sub-spaces the viewer can see that are `public` or that the viewer is an active member of. |

## SpacePreview

A minimal space shape used only as an embedded reference — never returned directly by any endpoint. Appears as `SpaceDetailed.parentSpace` (the space one level up) and inside `SpaceDetailed.childSpaces[]` (spaces one level down).

| Property | Type | Description |
|----------|------|-------------|
| `id` | `string` | Space UUID. |
| `shortId` | `string` | Short identifier. |
| `name` | `string` | Display name. |
| `slug` | `string \| null` | URL slug. |
| `avatarFileId` | `string \| null` | Avatar file ID. |
| `readingPermission` | `"anyone" \| "members" \| undefined` | Reading permission level. |
| `visibility` | `"public" \| "unlisted" \| "private" \| undefined` | Listing/discoverability level. |
| `parentSpaceId` | `string \| null \| undefined` | Parent space reference. |
| `depth` | `number \| undefined` | Nesting depth. |

## SpaceMemberPermissions

Included in `SpaceDetailed.memberPermissions` for a viewer with a membership in the space, whatever its status.

| Property | Type | Description |
|----------|------|-------------|
| `isAdmin` | `boolean` | Whether the user is an active admin of this space. |
| `isModerator` | `boolean` | Whether the user is an active moderator of this space. |
| `isMember` | `boolean` | Whether the user has an active membership. |
| `status` | `"pending" \| "active" \| "banned" \| "rejected" \| null` | The user's membership status. |
| `canPost` | `boolean` | Whether the user can post entities in this space: they can read it, aren't banned in it or in any space above it, and its `postingPermission` lets them post. |
| `canModerate` | `boolean` | Whether the user can perform moderation actions (an active admin or moderator of this space). |
| `canRead` | `boolean` | Whether the user can read content in this space, following the reading rules of the spaces above it. |

### How permissions are calculated

- **`canRead`** — the user can see the space (see [Who sees a space](#who-sees-a-space)), and either is an active member of it, or its `readingPermission` is `"anyone"` and they can read the space above it. A top-level `"anyone"` space can be read by anyone who can see it. Reading is inherited: below a `"members"` space, every space is members-only too, even one set to `"anyone"`. Such a sub-space can be read by active members of the sub-space itself, of the `"members"` space above it, or of any space in between. A pending, banned or rejected user isn't an active member, so they read a space only where `"anyone"` reading reaches it.
- **`canPost`** — `canRead`, no ban in this space or in any space above it, and the space's `postingPermission`: `"anyone"` lets every user who can read the space post, `"members"` its active members, and `"team"` its active admins and moderators. A ban in a space above counts even when the user has no membership, or a pending one, in this space.
- **`isMember`, `isAdmin`, `isModerator`, `canModerate`** — come from the user's membership of this space only. An admin or moderator of a space above isn't an admin or moderator here.

## Visibility

`visibility` is a distinct axis from `readingPermission`. **Visibility governs who can find and see the space; reading permission governs who can *read the content* inside it.** You can have a `public` space that only members can read, or an `unlisted` space that anyone can read once they have the link.

| Value | Behavior |
|-------|----------|
| `public` | **Default.** Listed in the directory and search, and reachable by anyone who can see the space above it. |
| `unlisted` | Not listed in the directory ([Fetch Spaces](/v8/api-reference/spaces/fetch-spaces) across levels) or search, for anyone, and listed under its parent (sub-space lists and previews) only for its active members. Reachable by id, short id or slug by anyone who can see the space above it. Joining works as for a public space. |
| `private` | Seen only by its **active** members. To everyone else — users with a `pending`, `banned` or `rejected` membership, other users, signed-out callers, and a service key without `actingUserId` — it answers exactly like a space that doesn't exist (`404 space/not-found`), apart from the exceptions under [Where it applies](#where-it-applies). It can't be joined; its moderators and admins [add](/v8/api-reference/spaces/membership/add-member) its members. |

### Who sees a space

A viewer — the signed-in user, or the user a service key names in `actingUserId` — sees a space when they are an active member of it, **or** when it isn't `private` and they can see the space above it. A top-level space that isn't `private` is seen by everyone.

So a private space hides everything under it from non-members, whatever those spaces' own visibility. A member of a sub-space still sees that sub-space (and the non-private spaces under it) even when they can't see a private space above it; they don't see that private space.

Each space keeps its own `visibility`; nothing is changed or refused when you nest spaces. Visibility changes take effect immediately and are freely reversible.

### Where it applies

- **Single reads** of a space the viewer can't see answer `404 space/not-found` — [by id](/v8/api-reference/spaces/fetch-space), [short id](/v8/api-reference/spaces/fetch-space-by-short-id) and [slug](/v8/api-reference/spaces/fetch-space-by-slug) — and so do its [breadcrumb](/v8/api-reference/spaces/fetch-breadcrumb), [rules](/v8/api-reference/spaces/rules/list-rules), [members](/v8/api-reference/spaces/membership/list-members), [team](/v8/api-reference/spaces/membership/list-team), [join](/v8/api-reference/spaces/membership/join-space), [delete](/v8/api-reference/spaces/delete-space), the moderator and admin actions, creating a sub-space in it (`404 space/parent-not-found`), and creating an event in it (`404 event/space-not-found`). The `404` comes before any permission check, so it never confirms the space exists. [Check my membership](/v8/api-reference/spaces/membership/check-my-membership) is the exception: a user with any membership in the space gets it back.
- **Lists across levels** — [Fetch Spaces](/v8/api-reference/spaces/fetch-spaces) with `parentSpaceId` left out, `none` or `any`, and [space search](/v8/api-reference/search/search-spaces) — show a space only if it **and every space above it** are `public`, whoever asks.
- **Lists under one parent** — [Fetch Spaces](/v8/api-reference/spaces/fetch-spaces) with `parentSpaceId=<id>` and the `childSpaces` preview — show the direct sub-spaces the viewer can see that are `public` or that the viewer is an active member of. So an `unlisted` sub-space shows only to its active members, and a `private` one only to its active members. `childSpacesCount` counts exactly these sub-spaces, so it always matches what the viewer can list.
- **[User spaces](/v8/api-reference/spaces/fetch-user-spaces)** and **[mutual spaces](/v8/api-reference/spaces/fetch-mutual-spaces)** list only spaces the viewer can see. An active membership always counts; a `pending`, `banned` or `rejected` membership of a space the user can't see is left out.
- **Space chat** — [Get Space Conversation](/v8/api-reference/spaces/chat/get-space-conversation) is for active members only; anyone else gets `403`: `chat/not-a-member`, or `chat/membership-pending` / `chat/banned` for their own pending or banned membership. The chat routes that take a conversation id answer a space chat in a space the viewer can't see the way they answer someone who isn't in the conversation — including a former member, who otherwise keeps the history from before they left. It's also left out of the viewer's conversation list, unread count and chat-message search, their real-time connection isn't subscribed to it when it connects or joins the conversation, and they get no push notifications for its new messages. Reporting a message in it, or a reputation grant on one, answers them the same way it answers someone who isn't in the conversation.
- **Embedded spaces** — `parentSpace` on a space, the `space` included on events, and the `space` on your own drafts in [Fetch Drafts](/v8/api-reference/entities/fetch-drafts) — are `null` when the viewer can't see that space. The rest of the response is unchanged, and `parentSpaceId` / `spaceId` still name it. An entity or comment in a space the viewer can't see isn't returned at all (see Content below).
- **Content** — entities, the comments on them and their reactions follow [who can read content](#who-can-read-content), which includes seeing the space: content in a space the viewer can't see is never readable. Creating or publishing an entity in a space the caller can't see answers `404 entity/space-not-found` (see [Who can post and take part](#who-can-post-and-take-part)).
- **Reports and collections** — reporting an entity or comment the user can't read answers `404 report/target-not-found`, and saving such an entity to a collection `404 entity/not-found`, both like a missing target. A collection's entities list and its `entityCount` leave out entities the owner can't read.

<Note>
  [Search Content](/v8/api-reference/search/search-content), [Ask](/v8/api-reference/search/ask) and [Match Users](/v8/api-reference/match/match-users) don't filter entities and comments by a space's visibility or reading rules (chat messages in their results follow the Space chat rules above). Reputation, notifications and events in a space don't follow its reading rules either.
</Note>

## Who can read content

`readingPermission` decides who can read the content inside a space: its entities, the comments on them, and the reactions on both. A viewer — the signed-in user, or the user a service key names in `actingUserId` — reads a space's content when they can [see the space](#who-sees-a-space) **and**:

- they're an active member of the space, **or**
- the space's `readingPermission` is `"anyone"` and they can read the space above it (a top-level `"anyone"` space is read by everyone who sees it).

So reading is inherited: a `"members"` space keeps its content, and the content of every `"anyone"` space under it, from anyone who isn't an active member of it or of one of those sub-spaces. An active member of an `"anyone"` sub-space reads that sub-space even when they aren't a member of the `"members"` space above it. A space below another `"members"` space starts the rule again: only its own active members read it.

Only an **active** membership counts. A `pending`, `banned` or `rejected` user reads exactly what a non-member reads: a banned user still reads an `"anyone"` space they can see, and can't read a `"members"` one. Signed-out callers, and a service key without `actingUserId`, read only content in spaces where every space from the top down to this one is `"anyone"` and none is `private`. To read members-only or private content with a service key, name a member with `actingUserId`.

| Where | What a viewer who can't read the content gets |
|-------|----------------------------------------------|
| A single entity or comment (by id, short id or foreign id) and its reactions | `404` with the route's not-found code (`entity/not-found`, `comment/not-found`), exactly like an item that doesn't exist. |
| [Fetch Many Entities](/v8/api-reference/entities/fetch-many-entities) | The entity is left out, and `totalItems` counts only what the viewer can read. `spaceId` of a space they can't read is an empty page with `totalItems: 0`. |
| A comment thread ([Fetch Many Comments](/v8/api-reference/comments/fetch-many-comments)) | The empty page, as for an unknown `entityId` or `parentId`. |
| A user's comments ([Fetch Comments by User ID](/v8/api-reference/users/fetch-comments-by-user-id)) | Comments on entities in spaces the viewer can't read are left out, the user's own included. |

A comment is read through its entity's space. Content in no space is read by everyone.

## Who can post and take part

**Posting** — creating an entity in a space (a draft included), publishing a draft in it, and editing an entity in it — needs all three:

- reading the space's content ([who can read content](#who-can-read-content));
- no ban in the space or in any space above it, including spaces where the user has no membership;
- the space's `postingPermission`: `"anyone"` lets everyone in, `"members"` its active members, `"team"` its active admins and moderators.

A signed-out caller (allowed only while the project lets anonymous callers create entities without an author) posts only in an `"anyone"` space whose content signed-out callers can read. A service key without `actingUserId` creates app-owned entities in any space, private ones included, and edits them anywhere; reading that content back still needs `actingUserId` naming a member. A service key with `actingUserId` gets exactly that user's answer.

**Taking part** — commenting, replying, reacting to an entity or a comment, and editing your own comment — needs reading the content and no ban in its space or any space above it. `postingPermission` isn't consulted, so a `"team"` space still takes comments and reactions from everyone who reads it. A comment goes by its entity's space.

| Situation | Answer |
|-----------|--------|
| Creating or publishing an entity in a space the caller can't see (a ban in a `private` space hides it) | `404 entity/space-not-found`, the same as a space that doesn't exist |
| Creating, publishing or editing an entity in a space the caller can see but may not post in: can't read it, banned in it or above, or not let in by `postingPermission` | `403 space/posting-not-allowed` |
| Editing an entity, or commenting, reacting or editing a comment, on content the caller can't read (for example after being banned in a `"members"` space) | `404` with the route's not-found code (`entity/not-found`, `comment/entity-not-found`, `comment/not-found`) |
| Commenting, reacting or editing a comment on content the caller can read while banned in its space or above | `403 space/posting-not-allowed` |
| Deleting your own entity or comment | Allowed (`204`), also while banned or after losing read access |
| Removing your own reaction | Allowed while banned; `404` on content you can no longer read |
| Editing or deleting someone else's entity or comment you can't read | `404`, like a missing one, never `403` |

Every `space/posting-not-allowed` refusal has the same body, whatever the cause:

```json
{ "error": "You can't post or take part in this space.", "code": "space/posting-not-allowed" }
```

When a space response carries `memberPermissions`, its `canPost` is this posting rule for the viewer.

## NSFW flagging

NSFW is a separate axis from both `visibility` and `moderationStatus` — flagging a space (or entity) NSFW **labels** it, it does not hide or remove it. Every space carries its own `nsfw` boolean plus a denormalized `nsfwEffective`:

- **`nsfw`** — the space's own flag, defaulting to `false`. Toggled by space admins (via [create](/v8/hooks/spaces/use-create-space)/[update](/v8/hooks/spaces/use-update-space)) or by project admins from the dashboard.
- **`nsfwEffective`** — the denormalized rollup:

  ```
  nsfwEffective = own nsfw OR any ancestor space's nsfw
  ```

  It is maintained **on write**: creating a space under an NSFW parent inherits `nsfwEffective = true` even if its own `nsfw` is `false`, and toggling a space's own `nsfw` recomputes `nsfwEffective` top-down across its entire descendant subtree in the same transaction. A root space's `nsfwEffective` equals its own `nsfw`.

Because `nsfwEffective` folds in the whole ancestor chain, it is what an entity's live `nsfwEffective` reads from — flagging a space instantly cascades to every entity within it and its sub-spaces. See [Entity → NSFW flagging](/v8/data-models/entity#nsfw-flagging).

To filter a list by effective NSFW, pass `nsfwFilter` to [Fetch many spaces](/v8/hooks/spaces/use-fetch-many-spaces) (`include-all` default / `exclude` / `only`).

<Note>
  The space `nsfwFilter` keys off each space's own `nsfwEffective`, so `only` can return an NSFW child whose safe parent is omitted — results are **not** guaranteed to form a contiguous tree. Consumers building a tree from the result should not assume completeness.
</Note>

<Note>
  Sublay only **labels** and **filters** NSFW content. It does **not** blur, age-gate, add interstitials, or store a per-viewer "show mature content" preference — presentation is the consuming app's responsibility.
</Note>
